# 120. 서비스 검사 시작·종료 절차 공통화

작성일: 2026-11-27.

## 실제로 실패한 지점

Run `069b10fe-6bfc-4d24-b2bc-3d57b87b85ee`의 Security v3은 제품 보안 취약점을 확정한 것이 아니라 **검사 코드 준비에 실패**했다. `setUp()`에서 `TestClient(main.app)`만 생성하고 컨텍스트에 진입하지 않아 앱의 실제 lifespan이 실행되지 않았다.

첫 수정 요청은 `TEST_CLIENT_NOT_STARTED`였다. 수정 과정에서 출력 길이 제한도 발생했고, 마지막으로 다시 쓴 검사에도 같은 초기화 실수가 남았다. 기존 수정 한도 안에서 해결하지 못해 `LLM_VALIDATION_DRAFT_EXHAUSTED`로 종료됐다. 반복 횟수나 토큰 한도를 늘리거나 검사를 통과 처리하는 방식으로 해결하지 않는다.

같은 Run의 QA v3도 7개 중 5개만 통과했다. 서로 다른 두 원인이 있었다.

- **제품 구현의 계약 위반:** 기획서에는 `GET /`가 JSON 응답인데 실제 구현은 HTML을 반환했다. 시작 검사에서 이 차이를 놓쳤다.
- **검사가 만든 추가 조건:** 회원가입 성공 응답에 `email`이 반드시 있어야 한다고 검사했지만, 승인된 인터페이스에는 JSON과 상태 코드만 정해져 있었다. 실제 구현의 성공 응답 키는 `message`였다. 명시되지 않은 응답 키를 필수 조건으로 추가한 문제다.

## 수정한 동작

### 1. 앱 준비를 AI가 매번 작성하지 않도록 변경

일반 서비스의 HTTP 시험은 `_host_service_test.ServiceTestCase`를 상속하고 `self.client`를 사용한다. QA와 Security, 공통 런타임을 사용하는 Single·Multi 경로에 같은 안내를 제공한다.

공통 검사기는 **Sandbox 안에서** 검사마다 임시 `DATABASE_URL`을 설정한 다음 원래 `main.app`을 불러오고, 원래 lifespan에 진입한다. 검사 종료나 준비 실패 시 클라이언트·제품 모듈·환경·임시 폴더를 정리한다. 특정 `User` 모델이나 회원가입 경로를 가정하지 않는다.

제품의 테이블을 대신 생성하거나 의존성을 덮어쓰지 않는다. 실제 앱이 시작하지 못하거나 원래 초기화에서 테이블을 만들지 못하면 그대로 실패한다. 이 기능은 제품이 `DATABASE_URL`을 준수하도록 바꾸는 기능이 아니며, 실제 데이터베이스 동작은 제품과 Sandbox 검사가 확인해야 한다. SCN-001 전용 `AppTestCase` 계약은 유지한다. HTTP를 사용하지 않는 일반 단위 시험은 기존 `unittest.TestCase`를 사용할 수 있다.

### 2. 잘못된 준비·도구 사용을 실행 전에 교정

일반 서비스 시험에서 직접 `TestClient`를 만들거나 공통 준비 절차를 재정의하면 `TEST_SERVICE_FIXTURE_REQUIRED`로 실제 검사 파일 수정을 요구한다. 같은 잘못된 READY 응답만 반복해서는 진행할 수 없다.

출력 관찰 도구의 `sensitive`에는 요청에 실제 포함한 현재 검사의 합성 문자열을 전달해야 한다. 필드 이름 `"password"`, 리스트·딕셔너리, 잘못된 인자 형식은 `TEST_OUTPUT_ARGUMENT_INVALID`로 안내한다. 정적 분석으로 알 수 없는 잘못된 값은 실제 Host 도구의 실패 프레임이 확인될 때만 `NOT_RUN_FIXTURE_ARGUMENT_INVALID`로 구분하고 기존 한도 내 검사 수정 경로로 돌린다. **미실행은 PASS나 제품 결함 확정으로 처리하지 않는다.** 같은 오류 문구를 제품이나 검사에서 임의로 던져도 이 분류를 얻지 못한다.

### 3. API 형식과 검사 근거 보강

- `GET /`가 JSON으로 합의된 경우 시작 검사에서 실제 응답 형식을 확인한다. HTML이면 `SERVICE_JSON_REQUIRED`를 Developer에 돌려준다. 명백한 직접 HTML 반환도 실행 전 정적 점검에서 안내한다. 불확실한 구현은 실제 Sandbox 검사가 판단한다.
- 실제 Source의 단순한 성공 응답에서 확인되는 **키 이름만** `staticResponseFields`로 전달한다. 값이나 비밀정보를 포함하지 않으며 실행 결과·새 요구사항으로 취급하지 않는다. 명시되지 않은 `email`·`id`·`message` 키를 검사가 임의로 요구하지 않도록 안내한다. 승인 요구사항이 명시한 필드가 빠졌다면 실패 검사를 유지한다. 이 안내가 모델의 모든 잘못된 추론을 차단한다고 보장하지 않는다.
- 고정된 Host 시작 검사 프로그램만 AST로 정리해 기존 인자 길이 제한 안에 유지한다. 제품 Source를 실행하거나 명령 인자에 삽입하지 않는다. 119번의 기계 필드만 전달하는 규칙과 비밀값 차단은 유지한다.

## 확인한 범위

- 첫 관련 회귀 검사 **216개 통과**: 서비스 계약, 시작 검사, 테스트 수집·보고서, QA/Security 입력 및 실행 경로.
- 런타임 도구 오용 분류 수정 후 관련 검사 **99개 통과**.
- 마지막 준비 기능·오류 교정·기존 SCN-001 호환·초안 수정 한도 검사 **103개 통과**. 앞선 검사와 겹치므로 합산 수치가 아니다. 의도적으로 잘못된 비동기 시험을 실행하는 기존 검사의 경고 및 테스트 A2A의 event stream 경고는 별도로 남았다.
- 기존 승인 Docker 이미지에서 직접 작성한 작은 앱과 실제 검사 CLI로 **2개 통과**. 원래 앱 lifespan 실행, 서로 다른 임시 DB, 실제 응답·요청 로그 관찰을 확인했다. 네트워크 없이 실행했으며 유료 AI 호출이나 실제 생성 제품 실행은 하지 않았다.
- 실행 중인 Run·Step이 없음을 확인한 뒤 Host·Agent 4개에 적용했다. 프론트·제품·Host·Agent 4개 모두 실제 상태 경로에서 HTTP 200, Agent 4개는 `executionReady=true`를 확인했다. Host 조회는 토큰 없이 401, 기존 서비스 토큰으로 200이었다. 프론트·제품 서버·Docker는 재시작하지 않았고 기존 작업 기록과 인증·실행 제한을 보존했다.

새 유료 작업은 생성하지 않았고 기존 실패 Run이나 산출물을 성공으로 바꾸지 않았다. 서비스의 실제 완성 여부는 적용된 서버에서 **새 작업 1회**로 확인해야 한다. 종료된 실패 단계는 답변만으로 재개되지 않는다.
