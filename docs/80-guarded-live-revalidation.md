# 80번 — 실제 API 재검증·검토기 대조·최종 보고서

## 최종 결과와 범위

[75~80번 실제 통신 보완 보고서 PDF](reports/agent-communication-guarded-2026-11-13/guarded-natural-4cases-report.pdf)는 총 8쪽이다. 기존 PDF는 변경하지 않고 새 PDF만 추가한다.

실제 API는 **총 38회**였다. 자동 Retry·모델 교체 없이 전체 한도 40회 안에서 종료했다. 자연어 진단·검토기 대조를 수행했으며 제품 Host·실제 코드 생성·MCP·Docker·Build·보호된 QA/보안 검사·배포는 실행하지 않았다.

| 항목 | 관측 |
| --- | --- |
| 역할 답변 | 16회 — 초기 11 + 최종 회사 소개 5 |
| 파이프라인 의미 검토 | 13회 — 초기 8 + 최종 5 |
| 검토기 대조 | 9회 — 같은 대조 입력 3개 × 보강 단계 3개 |
| HTTP 200 | 38/38 |
| A2A 송수신·DB·metadata·역할 API 입력 대조 | 전송한 역할 응답 16/16 일치 |
| 초기 앞단 차단으로 후속 역할 미호출 | 9건. 전송 유실과 구분 |
| 입력 / 출력 토큰 합계 | 59,242 / 18,424 |
| 최종 회사 소개 인계 | 멀티 4역할 + 싱글 1역할, 5/5 허용 |

실제 회사 Agent 수가 늘어난 것은 아니다. 의미 검토는 별도 진단 API 처리이며 새 Agent Card·회사 역할을 만들지 않았다. 모델의 보조 검토는 사용자 승인이나 제품 성공을 의미하지 않는다.

## 1. 자연어 4개 초기 실행

기존 블로그·전자문서·추리게임 원문은 유지하고, 명확한 회사 소개 화면 요청을 추가했다. [입력 폴더](../src/diagnostics/communication/fixtures/natural)의 `04-office-page.txt`가 신규 요청이다. 전체 문장 4개와 설정·실행 순서는 PDF에 실었다.

모델은 기존 `gpt-4.1-mini-2025-04-14`, 온도 0, 역할 답변 상한 8,192 tokens다. 처음에는 역할 응답 최대 20회와 검토 최대 20회를 계획했으나 후속 차단으로 실제는 **역할 11회 + 검토 8회**였다.

| 초기 결과 | 설명 |
| --- | --- |
| 질문 대기 3건 | 블로그 멀티·싱글, 전자문서 멀티. 사용자 확인 전 진행 중단 |
| 구조 거절 3건 | 전자문서 싱글의 없는 인용 1건, 추리게임 멀티·싱글의 검사 연결 누락 2건 |
| 인계 허용 5건 | 회사 소개 요청의 멀티 4역할·싱글 1역할 |
| 후속 미호출 9건 | 초기 멀티 3요청의 Developer·QA·Security |

전자문서 싱글은 인용에서 원문의 “기간을”을 “기간를”로 바꿨다. 추리게임은 요구사항이 결과에 있었지만 일부 항목의 검사 연결이 빠졌다. 세 응답은 구조 검사에서 막혀 의미 검토 API를 추가 호출하지 않았다. 요구사항 전송 유실이나 전부 사실 환각으로 묶지 않는다.

## 2. 검토기 자체의 대조

`calibrate.py`는 실제 정상 응답 1개와 Host가 고의로 의미를 바꾼 응답 2개를 같은 검토 API에 보낸다. 기대 라벨·오류 주입 구분은 Host에만 있고 모델에는 원문·candidate만 제공했다. 고의 오류를 실제 사용자 실행에서 새로 발견한 오류 2건이라고 발표하지 않는다.

| 보강 단계 | 정상 응답 | 개인정보 확대 | 미승인 기능 확정 |
| --- | --- | --- | --- |
| 최초 | 모델 지지 | **잘못 지지·통과 가능** | 거절 |
| 필드별 근거 중간판 | 인용 필드 혼동으로 미검증 보류 | 모델은 지지했으나 근거 형식 오류로 보류 | 거절 |
| 최종판 | 지지·허용 가능 | **모델의 지지는 남았지만 Host 보조 규칙으로 미검증 보류** | 거절 |

최종 대조의 **예상 의미 판정 일치는 2/3**, 허용·보류 정책은 **3/3**이었다. 개인정보 오류를 모델이 정확히 판별했다고 바꾸어 쓰지 않는다. 보류는 실패를 안전하게 다루는 것이며 올바른 의미 이해와 동일하지 않다.

처음 실패한 결과·중간 실패·최종 결과는 각각 별도 JSON과 실행 당시 소스 사본으로 보존했다. 같은 응답을 몰래 보정하거나 성공할 때까지 자동 재호출한 것이 아니다. 명시적인 코드/계약 보강 단계별 관측이며 독립적인 새로운 평가셋이나 일반 검출률은 아니다.

## 3. 최종 회사 소개 재실행

마지막에는 **회사 소개 요청만** 새 계약으로 재실행했다. 멀티 4역할·싱글 1역할의 역할 답변 5회와 의미 검토 5회를 사용했다. 초기 4개 요청을 모두 최종판으로 다시 실행했다고 주장하지 않는다.

누적 근거 파일의 호출 수 28회와 새 실행 상한 10회를 합쳐 38회임을 호출 전에 검사했다. 마지막 실행의 원자료에도 이전 파일의 경로·해시·호출 수와 `combinedCallCount=38`을 기록했다.

| 역할 | 최종 Agent 처리 | 역할 API 교환 | 검토 API 교환 |
| --- | ---: | ---: | ---: |
| Planner | 11.204초 | 6.225초 | 4.891초 |
| Developer | 11.871초 | 6.251초 | 5.532초 |
| QA | 12.290초 | 5.778초 | 6.363초 |
| Security | 14.818초 | 6.867초 | 7.867초 |
| Single | 13.820초 | 6.235초 | 7.477초 |

최종 진단 실행 시간은 멀티 **38.281초**, 싱글 **13.915초**다. 각 역할은 표본 1개이며 API 교환에는 네트워크·서버 처리·본문 수신이 포함된다. 순수 추론 시간·구조 자체의 우열·장기 p95는 알 수 없다. 멀티의 병렬 QA·Security 시간을 단순 합산하지 않았다.

검토 근거를 늘리면서 비용과 지연이 추가됐다. 초기 차단 요청은 수행한 작업 자체가 적으므로 이전 대비 빨라진 비율로 계산하지 않는다.

초기 원자료 SHA-256은 `9c16655749ea8b4527fb0e5c4ac3df42d402a0c682df4f8eaad04b741912065a`, 최종 원자료는 `9c2f92db2ca46f14a219cc3f3ca6b671bce7d9298623f7e3bb17631eb987b1d1`이다. 다섯 원자료의 전체 해시는 PDF 마지막 쪽에 실었다.

실행 도중 선택 소스는 각 단계에서 `STABLE`이었다. 초기·중간·최종 코드 사본을 `execution-source*`에 남겨 이후 코드 변경과 구분한다. 현재 소스로 과거 버전의 실행을 그대로 재현했다고 주장하지 않는다. `.env`·키·인증 헤더·사용자 설정은 사본에 포함하지 않는다.

## 재실행과 보고서 출력

새로운 실제 실험은 아래 CLI로 실행한다. 명시된 새 폴더를 사용하고, 역할/검토 각 최대 20회를 합산한 비용이 발생한다.

```bash
PYTHONPATH=src .venv/bin/python -m diagnostics.communication.guarded \
  --model gpt-4.1-mini-2025-04-14 --out .data/diagnostics/guarded-new-run
```

`--case-id`로 등록된 입력을 선택할 수 있고 `--prior-run`을 반복 지정하면 이전 호출과 합산해 40회 상한을 검사한다. 사용한 Runtime·같은 출력 폴더를 재사용해 과거 결과를 덮어쓰지 않는다.

보고서 재출력은 `diagnostics.communication.guarded_reporting`이다. `--initial`, 세 개의 `--calibration`, `--final`, 임시 HTML `--out`만 받는 오프라인 모듈로, 모델 API를 호출하지 않는다. 임시 HTML을 A4 PDF로 출력했고 저장소 보고서 폴더에는 PDF만 남겼다.

## 개발정의서와 남은 작업

[79번](79-guarded-single-multi-regression.md)의 최종 관련 검사 **173개 통과**다. 제품의 동결 요구사항·A2A 공식 상태·metadata·Artifact·MCP ACL·인증·Sandbox·수정 최대 3회·Tool Retry 최대 2회를 변경하지 않았다. 실패·미검증·미호출·API 소비와 원자료를 보존했다.

다음 번호는 **81번 실제 실행 환경 가동**, **82번 실제 생성→빌드→QA·보안→실패 수정→재검증 흐름 확인**이다. Docker 준비가 필요하며 프론트 Trace 연결은 세화와, 정식 비교 실험은 석민과 함께 진행한다.

일반적인 의미 판정 정확도는 계속 보완·반복 검증해야 한다. 현재 보조 규칙은 제한된 단서 기반이고 오탐·미탐 가능성이 있다. 이번 배치의 구현·재실험·보고서를 완료한 것과 모든 자연어 할루시네이션을 제거한 것은 구분한다.
