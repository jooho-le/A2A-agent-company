# 직원 작업 확인·중단·추가 답변

## 사용 흐름

1. 작업을 시작하거나 내 프로젝트에서 `진행 보기`를 누른다.
2. 오피스의 직원 또는 작업 패널의 직원 사진을 누르면 해당 직원의 실제 상태·작업 내용을 확인한다. 팀장과 네 직원은 계속 화면에 남는다.
3. 확인을 기다리는 직원이 있으면 질문을 먼저 보여준다. 내용을 적고 `답변하고 이어가기`를 누르면 해당 직원의 기존 Task에 전달한다.
4. 패널 상단의 `작업 중단` → 확인창의 `작업 중단`을 누르면 현재 Run 종료를 요청한다. 서버가 직원들의 취소를 확인한 뒤 중단 완료를 안내한다.

질문이 있을 때 역할 설명과 중복 상태 설명을 접어 답변 입력을 우선한다. 작업 기록·식별자·카메라 설정은 보조 정보로 유지한다. 진행 상황 페이지에서도 같은 작업 패널을 사용한다.

## 입력과 중단의 의미

- **중단은 현재 실행의 종료다.** 이미 만든 결과를 삭제하지 않으며, 종료된 Run은 재개하지 않는다. 확인창에서 이 차이를 설명한다.
- **답변은 확인 대기인 직원 한 명에게 전달한다.** 기존 WorkflowStep·A2A Task·Context에 연결하며, 승인 요구사항·Configuration·예산을 바꾸지 않는다. 오래된 질문에 대한 답변은 상태 검증으로 차단한다.
- **진행 중 추가 의견은 메모다.** 이 브라우저의 계정·Run·직원별 임시 공간에 보관한다. 확인 질문이 도착하면 같은 직원의 답변 초안으로 이어진다. 진행 중인 LLM에 즉시 끼워 넣는 기능으로 표시하지 않는다.
- `NEW_RUN_REQUIRED`는 새 작업으로 안내하고, 인증 확인은 관리자 조치로 표시한다. 질문을 읽지 못하면 입력을 받는 것으로 추측하지 않는다.
- 근거 인용 재검증으로 보류된 경우 이를 사용자의 입력 누락이라고 표현하지 않는다. 답변 이후에도 기존 검증을 다시 통과해야 진행된다.

## 실제 API 연결

| 제품 API / Host API 공통 경로 | 역할 |
| --- | --- |
| `GET /api/v1/runs/{runId}/interaction` | 현재 질문·대상 직원·답변 가능 여부·revision 조회 |
| `POST /api/v1/runs/{runId}/commands` | 중단 또는 추가 답변 접수 |
| `GET /api/v1/runs/{runId}/commands/{commandId}` | 접수된 명령의 실제 처리 상태 조회 |

브라우저는 제품 JWT로 요청한다. 제품 서버는 프로젝트 소유권을 먼저 검사한 후 서버의 Host 서비스 인증으로만 중계한다. 브라우저에 Host 토큰·원격 주소를 넘기지 않는다.

POST에는 UUID4 `Idempotency-Key`와 `action`, `revision`을 보낸다. `RESUME`에는 `workflowStepId`, `clarification`이 추가된다. `CANCEL`은 해당 Run 전체를 중단하므로 직원 진행에 따른 revision 변경으로 막지 않는다. 승인 설정이나 임의의 실행 인자는 받지 않는다.

Host는 명령 접수 기록을 SQLite에 저장한 뒤 202로 응답하고, 기존 WorkflowControlService를 통해 처리한다. 추가 답변은 긴 실행으로 이어질 수 있어 제품 중계의 짧은 HTTP 대기와 분리했다. 재전송된 동일 명령은 접수 기록만 반환한다. 같은 키의 다른 내용은 충돌로 차단한다.

## 중복·오류·복구

- 처리 상태는 `QUEUED / RUNNING / SUCCEEDED / REJECTED / UNKNOWN`이다. 접수 성공을 작업 성공으로 표시하지 않는다.
- 더블 클릭은 브라우저와 Host 양쪽에서 막는다. 실행 중인 답변 명령이 있어도 별도의 중단 요청은 접수할 수 있다.
- 응답이 끊겼을 때 접수 식별자를 보존하고 GET으로만 확인한다. 화면 재진입 시에도 자동 POST를 하지 않는다.
- 브라우저의 명령 접수 응답은 10초까지만 기다린다. 시간 초과를 실행 취소·실패로 단정하지 않고 동일 접수의 상태 조회로 전환한다.
- Host가 재시작되어 기존 처리를 확신할 수 없으면 `UNKNOWN`으로 보존한다. 같은 동작을 새 키로 반복 실행하지 않으며 운영자 확인이 필요할 수 있다. 현재 영수증 처리는 Host 단일 프로세스를 전제로 한다.
- 현재 Run의 질문만 3초 간격으로 조회한다. 화면 이탈 시 조회를 중단하고 겹치는 조회를 정리한다. 프롬프트·Task history·Tool 원문은 공개 응답에 포함하지 않는다.

## 검증 및 적용

- Host 제어·질문·영수증 및 기존 취소·재개 테스트 17개 통과.
- 제품 서버 전체 테스트 86개 통과: 인증·프로젝트 소유권·허용 입력·타임아웃 오류 포함.
- 프론트 전체 테스트 199개, ESLint, 빌드 통과. 기존 대형 3D 번들 크기 경고는 남는다.
- 격리 브라우저에서 실제 패널과 입력 훅의 질문 표시, 특정 Step 답변, 더블 클릭 차단, 응답 유실과 화면 재진입 복구, 직원별 메모, 중단 확인·취소를 검증한다. 모든 HTTP는 테스트 응답이며 실제 유료 작업은 생성하지 않는다.
- 실제 Vite 화면에서 직원 5명, 질문 입력, 중단 확인창과 기본 초점, 진행 화면, 390px·320px 가로 잘림 및 런타임 예외를 확인했다. 시각 검증 중 실제 작업 명령은 0회다.
- 사용자 승인 후 제품 서버와 Host·4개 에이전트를 재시작해 적용했다. 프론트 5173, 제품 8000, Host 8002, 에이전트 8101~8104 리스너를 확인했다.
- 실제 기존 Run의 Host 질문 조회는 HTTP 200이었다. Planner가 `WAITING_INPUT`, `replyMode=ANSWER`이며 근거 재검증으로 보류된 질문 1개를 반환했다. 제품 OpenAPI에도 새 중계 경로 3개가 등록되었다.
- 실제 기존 작업의 답변 전달·중단은 사용자가 선택한다. 이번 적용 점검에서 유료 작업 생성·재개·취소는 하지 않았다.
