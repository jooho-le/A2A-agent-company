## 검증 강화

1. 송신 원본·직렬화 결과·서버 본문·접수 입력·실행기 입력·실행기 결과·최종 Artifact를 각각 기록하고 대조한다.
2. 값·라벨·개수·앞 단계 해시 외에 역할별 구조화 계약을 고정 참조와 비교한다. 요구사항 범위, 의존 관계, 합격 기준과 요구사항의 연결, 권한 대상, 정책값, 미결정 질문, `NOT_EXECUTED` 증거를 포함한다.
3. A2A 메타데이터와 Message·Task·Context ID를 수신측에서 관측한 실제 ID와 독립적으로 대조한다. ACK와 조회 결과의 Context를 함께 위장해도 정상으로 취급하지 않는다.
4. 정상 기준선의 기본 인위적 처리 대기를 **0ms**로 설정한다. fixture·payload 생성과 JSON/protobuf 직렬화, 실제 본문 바이트 수, 관측 콜백 비용도 따로 기록한다.
5. 지정한 오류가 기대 경계에서 잡혔는지와 비대상 역할이 불필요하게 실패하지 않았는지 함께 판정한다. 단순히 오류 배지가 하나 발생했다고 성공으로 세지 않는다.
6. 같은 Message ID 재전송·내용 충돌·다른 Run의 Context 사용·다른 역할의 Task 조회도 실제 A2A 경로로 확인한다.

역할별 목업 응답은 실제 받은 요청으로 만들며 정답 파일을 읽지 않는다. 정답 접근 금지·캐시 오염 방지·수신 자료로 기준을 재정의하지 못하는 조건을 회귀 검사로 확인했다.

## 시간·크기 해석

정상 기준선은 **3자료 × Planner·Developer·QA·Security·Single 각각 n=20**이다. 처리 p50·p95는 nearest-rank, 전체·본문은 중앙값을 보고한다. 구간 중앙값 합산이나 ACK 왕복의 중복 합산을 하지 않는다.

- 인위적 처리 대기 0ms여도 실제 목업 생성·계측·스케줄링 비용이 있다.
- 관측 콜백 비용은 일부 계측 비용의 참조값이며 총비용에서 빼서 순수 성능을 계산하지 않는다.
- 같은 프로세스·서로 다른 TCP 포트·공통 단조 시계를 사용한다. 원격 시계 차이·운영 성능·부하 한계를 검증한 것은 아니다.
- Single은 네 역할 계약을 한 결과로 만들며 Multi는 역할별로 만든다. 이 결과로 모델 속도나 구조 우열을 판단하지 않는다.
- **64KiB는 진단 서버의 JSON 본문 제한**이다. 공식 A2A 제한이 아니다. 자료 속 20MiB 파일 정책과도 다르며 실제 파일 업로드는 하지 않았다.

## 검증 한계와 개발정의서 범위

실제 프로젝트의 A2A 클라이언트·인증·Agent 서버·Task 저장소를 재사용한다. 업무 Orchestrator·실제 Agent 실행기·MCP·서비스·평가의 비즈니스 로직과 인증 정책을 변경하지 않았다. 진단의 `COMPLETED`는 진단 Task 완료이며 제품 `SUCCESS`나 QA/Security 합격이 아니다.

**이번 실험으로 실제 LLM의 할루시네이션이 없다고 말할 수 없다.** 자연어 의미 해석, 모델 응답, 코드 생성, MCP·빌드·제품 테스트·보안 검사·배포는 수행하지 않았다. 다음 실제 모델 검증에서는 같은 관측 경계에 실제 실행기를 연결하고 주장별 코드·도구 영수증·테스트 로그와 자연어 평가 기준을 준비해야 한다.

커밋 메시지 제안: `복잡한 사용자 요청 기반 Agent 통신 엄격 검증 및 결과 보고서 추가`
