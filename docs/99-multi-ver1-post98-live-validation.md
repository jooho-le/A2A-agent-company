## 남은 실패를 쉽게 설명하면

정상 이메일에 앞뒤 공백이 붙어 있으면, 먼저 공백을 지우고 이메일 형식을 검사해야 한다. 이번 제품은 공백이 포함된 문자열을 바로 이메일 검사 라이브러리에 전달해 `422`로 거부했다. 독립 최종 시험에서도 앞뒤 공백 변형 2개가 정상 가입의 기대 응답인 2xx 대신 422를 반환했다.

등록된 v1·v2의 `main.py::normalize_email`을 실행하지 않고 AST·Source로 확인했다.

- `email_validator.validate_email(...)`가 공백 제거 전에 호출된다.
- 해당 함수에 `.strip()` 호출이 없다.
- Source 주석에는 라이브러리가 공백 제거를 처리하므로 생략한다는 설명이 있다. 실제 시험 결과와 맞지 않는 구현 가정이다.
- 첫 수정은 `signup()`의 DB 예외 분기를 바꿨고, 실패 원인이 있는 `normalize_email()` 함수는 v1·v2에서 동일하다.
- 두 번째 수정 종료 시 작업 파일은 v2 Snapshot과 바이트가 모두 같았다. 실제 코드 변화 없이 수정이 완료됐다고 인정하지 않아 `LLM_DEVELOPMENT_NO_PROGRESS`로 중단됐다.

즉, **실패 피드백은 전달됐지만 에이전트가 고쳐야 할 함수와 처리 순서를 제대로 선택하지 못했다.** 통신 누락이나 DB 테이블 생성 실패로 해석하지 않는다.

QA의 중복 방지 검사는 같은 계정이 추가되지 않고 4xx로 거절되면 통과할 수 있다. 공백을 정리한 새 정상 이메일이 실제로 가입·저장되는지는 별도 Security 검사에서 실패했다. 따라서 QA-SIGNUP-003 PASS와 SEC-SIGNUP-003 FAIL은 모순이 아니다.

## 97·98번 보완의 확인 범위

- 실제 생성된 v1·v2 모두 시작 코드의 `Base.metadata.create_all(...)`와 앱 lifespan 연결을 유지했다. 실제 Build에서도 원래 `get_db()`의 DB에 사용자 테이블이 존재한다고 확인했다.
- 최종 코드에는 `RequestValidationError` 처리기가 있고, 제품 비노출 시험도 PASS다.
- 96번의 후보 미등록 상태와 달리 이번에는 Source 등록·Build·QA·Security·수정·재검증·독립 최종 시험까지 실행됐다.
- 다만 이번 한 표본으로 보완의 인과 효과나 성공률 상승폭을 확정하지 않는다. 에이전트가 원래부터 만든 이번 코드와 사람이 수정한 98번 복사본은 서로 다른 결과다.
