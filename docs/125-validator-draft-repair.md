# 125. 품질·보안 검사 준비 오류의 교정 안내 보완

작성일: 2026-11-27.

## 실제 실패 원인

사용자가 실행한 Run `25a59792-41b5-496c-914a-985ddec60e87`을 읽기 전용으로 조사했다. 개발 수정으로 만든 두 번째 Source는 빌드를 통과했지만, 해당 Source의 QA·Security 단계가 모두 `LLM_VALIDATION_DRAFT_EXHAUSTED`로 중단됐다. 최종 기록은 `FINISHED / UNVERIFIED`다.

| 단계 | 확인한 오류 | 의미 |
| --- | --- | --- |
| 품질 검사 | `TEST_IN_FILE_NOT_DECLARED` | 검사 파일에 작성한 메서드 중 일부가 제출한 검사 목록에서 빠졌다. 실제 파일에서는 9개 메서드를 정적으로 확인했다. |
| 보안 검사 | `GENERATED_TEST_SYNTAX_INVALID` | 새로 쓰려던 Python 검사 코드에 문법 오류가 있었다. 파일 저장 전에 차단됐고, 교정에서도 같은 오류가 반복됐다. |

품질 검사는 일부 도구를 이미 실행했지만 두 번째 Source의 최종 결과서는 생성되지 않았다. 보안 검사도 새 결과서를 완성하지 못했다. 따라서 이번 상태를 제품 전체 통과나 실제 제품 결함 확정으로 해석하면 안 된다.

당시 거절된 READY JSON과 보안 코드 원문은 저장되지 않았다. 어떤 메서드가 빠졌는지, 보안 코드의 정확히 어느 줄이 잘못됐는지는 과거 기록만으로 복구할 수 없다. 남아 있는 이전 보안 파일은 문제의 새 작성 시도와 구분한다.

## 수정 내용

### 1. 빠진 검사 식별자를 직접 전달

기존에는 `파일과 제출 목록이 다르다`는 사유와 전체 검사 카탈로그를 전달했다. 이제 거절된 READY와 최신 Host 카탈로그를 비교해 **빠진 검사 / 실제 파일에 없는 선언**을 각각 `testRepairTargets`에 명시한다.

- 도구·selector·정확한 testId를 기준으로 비교한다. `tests.` 접두사를 임의로 붙이지 않는다.
- QA의 `cases`와 Security의 `testCases` 규격을 구분한다. Security 결과서에 없는 `toolName` 필드를 추가하도록 요구하지 않는다.
- 각 목록은 최대 32개와 전체 개수를 전달한다. 동적 구조여서 발견하지 못한 검사 이름은 만들어내지 않는다.
- 요구사항 연결과 기대 결과는 에이전트가 기존 할당 범위에 따라 작성한다. Host는 이를 자동 추정하지 않는다.
- 필요한 검사 메서드를 지워 목록 길이를 맞추도록 안내하지 않는다. 결과나 PASS 판정을 대신 채우지도 않는다.

### 2. 문법 교정 위치와 종류 제공

`write_test_file` 실행 전 정적 검사에서 오류 종류와 줄·칸을 함께 제공한다. 따옴표 미종결, 괄호 미종결, 들여쓰기, 콜론 누락, 잘못된 문자, NUL 등을 구분한다. 따옴표·괄호·들여쓰기에는 구체적인 수정 방향도 제공한다.

예외 메시지나 문제 코드 원문을 교정 안내에 복사하지 않는다. Host가 문자열을 임의로 치환하거나 코드를 대신 고치지 않는다. 자격증명 검사·작업공간 권한·실행 격리는 그대로 유지한다.

### 3. 화면의 보안 오류 원인 누락 수정

문법 거절은 `TOOL_POLICY` 보고서인데 기존 화면 조회가 JSON 형식 검사 보고서로 읽으려다 세부 사유를 버렸다. 이제 한 기록의 형식이 다르더라도 다음 기록을 읽고, Host의 종료 기록에 남은 허용된 오류 코드를 복구한다. 기존 보안 실패도 `검사 코드의 Python 문법을 수정해야 합니다`로 설명할 수 있다.

기록의 임의 문장·코드 원문·알 수 없는 오류 코드는 화면에 보내지 않는다. 기존 Run·Task의 상태나 판정도 바꾸지 않는다.

## 검증 범위

- 실제 실패 DB는 `mode=ro`, `PRAGMA query_only=ON`으로 조회했다. 기록 변경과 생성 코드 실행은 하지 않았다.
- 실제 파일의 9개 메서드를 읽어 카탈로그를 구성했다. 거절된 READY가 보존되지 않아, 검사 하나를 의도적으로 누락한 **별도 합성 입력**으로 교정 목록 생성을 확인했다. 이를 당시 READY 원문 재현이라고 표시하지 않는다.
- 가짜 모델을 사용해 누락 안내 → 정확한 READY 제출 경로를 검사한다. 변경 없는 잘못된 제출은 기존 제한대로 중단해야 한다.
- 문법 오류의 안전한 위치 정보, QA·Security·Single 공통 전달, 거절된 도구 배치의 무실행, 민감한 코드 미노출을 검사한다.
- 미검증 종료·기존 결과 보존·화면 오류 조회 관련 회귀 검사를 수행한다.

| 검증 | 결과 |
| --- | --- |
| 누락 식별자·문법 교정·화면 원인 복구·기존 검사 흐름 회귀 | 223개 통과. 모두 오프라인·가짜 제공자 사용 |
| 실제 실패 기록에서 화면용 사유 복구 | QA `TEST_IN_FILE_NOT_DECLARED`, Security `GENERATED_TEST_SYNTAX_INVALID` 확인 |
| 실제 파일의 9개 메서드 + 별도 합성 누락 제출 | 빠진 항목 1개를 정확히 제시. 당시 READY 원문 재현은 아님 |
| 동일 오류 반복·교정 횟수 제한·거절된 배치 무실행 | 유지 확인 |
| 민감한 코드 원문·알 수 없는 오류 사유 미노출 | 확인 |

최소 재현 사실은 Git 제외 파일 `.data/diagnostics/validator-draft-repair-20261127.json`에 기록했다. 실제 DB 쓰기·유료 API 호출·새 Run 생성은 하지 않았다.

실행 중인 Run·Step이 없고 Host·Agent 포트의 소유 PID가 일치하는 것을 확인한 뒤 해당 프로세스만 재시작했다. 프론트·제품·Host·Agent 4개 모두 HTTP 200이며 Agent는 `executionReady=true`다. 제품 상태 확인 경로는 `/`, Host·Agent는 `/health`다. Host 인증은 토큰 없이 401, 기존 토큰으로 200이었다. 기존 실패 Run은 그대로 `FINISHED`이며 이어서 수정이 가능한 상태이고, 조회 API에서 품질·보안의 구체적인 오류 사유를 모두 확인했다.

제품·프론트·Docker와 기존 기록은 유지했다. 현재까지 확인한 것은 교정 안내·종료 처리·연결 상태이며, AI가 새 코드로 실제 서비스를 완성했다는 결과는 아니다.
