# 118. 서비스 검사·오류 전달·수정 흐름 보완

작성일: 2026-11-27.

## 확인한 실패와 수정 범위

최근 Run `b6515250-329f-4ce5-a5fb-9f38747c2f95`의 보존된 Source·검사 입력·실행 보고서를 대조했다. QA는 두 버전 모두 7개 중 1개 통과, 6개 실패였다. 성공·중복 검사 2개는 TestClient가 앱 lifespan을 시작하지 않아 `users` 테이블이 없었다. 잘못된 입력 검사 4개는 기획서의 400과 실제 제품의 422가 달랐다. Developer의 두 번째 수정은 엔드포인트 안에 빈 필드 검사를 추가했으므로, 요청 모델 검증에서 먼저 거절되는 경로를 고치지 못했다.

원본 실행 결과에는 원인이 있었지만, QAReport와 FixRequest에는 대부분 `MEASURED_FAIL / DETAIL_RECORD_MISSING`만 전달됐다. Security는 두 버전에서 생성 검사 사전 점검과 결과서 검증을 통과하지 못했다. 당시 정확한 잘못된 필드는 저장되지 않아 사후 확정하지 않았다. 마지막 Developer 호출은 OpenAI HTTP 500으로, 기존 한도에 따른 1회 재시도 후에도 실패했다.

이번 작업은 플랫폼·에이전트·검사 실행기·실패 안내를 수정한다. 기존 실패 Run, 동결 요구사항, 생성된 제품 Source와 과거 점수는 변경하지 않는다.

## 변경 사항

| 문제 | 변경 후 동작 |
| --- | --- |
| 실패 이유가 개발자에게 전달되지 않음 | 실행기가 예외 종류·발생 영역·파일 해시/줄·직접 관찰한 HTTP 상태 비교를 `failureDiagnostic`으로 기록한다. UnitReport → QA/Security 보고서 → 검증 피드백 → Developer의 활성 수정 요약까지 전달한다. |
| 검사 준비 오류가 제품 결함으로 흘러감 | TestClient lifespan, 문법, 잘못된 import 등 생성 검사 사전 점검 오류는 알려진 검사 파일 결함으로 다룬다. 수정 기회에는 `write_test_file`을 실제 호출해야 하며, 해결하지 못하면 검사 결과서를 수용하지 않고 기존 기술적 중단 경로로 종료한다. |
| 관련 없는 with 문이 lifespan을 시작했다고 오인 | 실제 TestClient 생성식·변수·enter_context·enterContext·직접 __enter__ 호출을 연결한다. 파일 읽기나 다른 객체의 문맥 진입은 통과 근거가 아니다. 동적·알 수 없는 코드를 Host에서 실행하지 않는다. |
| 요청 함수 내부만 고쳐 422가 반복됨 | SERVICE-WEB의 Sandbox 기동 검사에 제한된 빈 JSON 요청 검사를 추가한다. 명시적 필수 JSON body이고 승인된 거부 상태에 400이 있으며 422는 없는 경우에만 검사한다. 불일치하면 `SERVICE_INPUT_REJECTION_MISMATCH`와 RequestValidationError 처리 위치를 안내한다. |
| 검사 실패만으로 원인을 확정 | QA 실패 Issue의 `causeStatus`는 기본 UNKNOWN으로 둔다. 측정된 실패와 근본 원인 확정을 구분하고, Developer에 실제 진단과 확인 순서를 전달한다. |
| Security가 서버가 아는 대기 항목까지 반복 생성 | Host가 동결된 할당 ID의 누락된 `requirementReviews`를 `UNVERIFIED / HOST_TESTS_PENDING`으로 채운다. 모델이 제공한 잘못된 판단·참조는 여전히 거절한다. 테스트·발견 항목·소스 근거·PASS를 만들어주지 않는다. |
| 결과서 형식 오류의 필드가 사라짐 | 보안 wire 디코딩 오류도 필드 경로와 닫힌 원인 코드로 설명한다. 공통 검증 보고서를 복구 Trace와 실패 Task에 보존하고, 화면에서 안전한 진단만 표시한다. |
| 응답만 확인하고 로그 검사라고 부름 | `_host_test_data.check_http_output`이 실제 테스트 요청의 응답·헤더·Python 요청 로그를 관찰한다. 현재 시험에서 생성한 합성 비밀값이 요청에 있어야 한다. 원문 값은 내보내지 않고 CHECKED/EXPOSED/INCOMPLETE만 기록한다. |
| 관찰 없는 보안 PASS | 서비스 설계에 password/secret/apiKey/accessToken/refreshToken 입력이 명시된 경우, 응답과 로그의 실측 채널이 없는 생성 검사만으로 보안 PASS를 내지 않는다. 같은 Source·같은 검사 항목에서 기존 1회 검사 수정 기회를 사용하고, 이후에도 관찰이 없으면 UNVERIFIED로 남긴다. |
| 제공자 오류와 제품 불량이 혼동됨 | Agent가 꺼져 있어도 Host에 저장된 HTTP 상태·재시도 기록을 조회한다. 500 등 제공자 중단은 제품 불량으로 표시하지 않으며 작업 기록 보존과 제공자 확인을 안내한다. |
| 자동 수정 중에도 새 작업을 권함 | 현재 Run이 수정·재검사 중이거나 다른 직원의 답변을 기다리는 경우 이전 실패를 복구 진행 상태로 표시한다. 이 경우 과거 실패만으로 새 작업 버튼을 강조하지 않는다. |

## 데이터와 책임 경계

- 생성 코드와 테스트는 기존 승인된 Sandbox에서 실행한다. Host는 파일을 정적으로 분석하고, 실제 실행 영수증을 해석한다.
- 단위 검사 진단은 원문 예외, SQL, 로컬 변수, 비밀번호, 저장 해시, 응답 본문을 전달하지 않는다. 수치 비교는 검사 코드의 실제 HTTP `status_code` 비교를 확인한 경우에 한한다.
- 보호시험에는 새로운 기대 HTTP 상태 비교를 내보내지 않는다. 기존 허용된 관찰 정책을 유지한다.
- `DATABASE_TABLE_MISSING`은 관찰된 증상이다. 검사 시작 누락과 제품 초기화 결함을 이 코드 하나만으로 단정하지 않는다.
- API 경로·입력 형식·승인 응답은 동결된 serviceDesign을 따른다. 테스트를 422에 맞춰 낮추거나 Host가 제품 코드를 대신 고치지 않는다.
- 일반 HTTP 출력 보조 기능은 DB 저장 해시의 안전성, 권한 제어, 모든 파일 로그나 외부 로그를 증명하지 않는다. 해당 경계는 별도 Source 검토·실행 근거가 필요하다.
- Single과 Multi는 같은 실행기·검사·진단·Security 서비스를 사용한다. SCN-001 실험의 보호시험 정책, 독립 최종시험, 인증, MCP 경로 권한, 네트워크 차단, 동결 Source와 예산은 변경하지 않는다.
- OpenAI의 500을 없애는 수정은 아니다. 기존 제한된 재시도 정책을 유지하며, 실패 Task를 무한 반복하거나 예산을 초기화하지 않는다. terminal Task에 답변을 보내 재개할 수 있다고 안내하지 않는다.

## 검증 및 적용

서버, Docker, 유료 OpenAI 요청은 시작하지 않는다. 오프라인 가짜 제공자·실행 영수증과 고정된 무해한 검사 fixture로 회귀 검증한다. 제품 생성 Source를 Host에서 실행하지 않는다.

- 기존 기본 검사 묶음: 123개 통과.
- 공통 엔진·단위 검사 저장·피드백·QA 복구·제공자 오류 확장 묶음: 284개 통과. 다른 묶음과 중복되므로 합산하지 않는다.
- 마지막 서비스 실행 계약·수정 입력·Security·새 재현 검사 묶음: **139개 통과**. 이번 문제의 새 재현 검사 29개가 포함된다.
- 단위 검사 실행기·보고서 마지막 확인: **61개 통과**.
- 프론트 실패 응답 계약: **7개 통과**. 모두 모의 전송이며 서버나 OpenAI에 요청하지 않는다.
- 프론트 빌드 및 변경 파일 ESLint 통과. 기존 3D 장면 청크 크기 경고는 기능 오류와 구분한다.

실제 API를 사용한 새 회원가입 작업 성공, Docker 실행, 실제 브라우저에서의 전체 서비스 동작은 이번 작업에서 확인하지 않았다. 사용자가 다음에 서비스를 시작할 때 변경 코드가 적용된 프로세스를 사용해야 한다. 기존 실패 Run의 기록과 동결 산출물을 덮어쓰지 않는다.
