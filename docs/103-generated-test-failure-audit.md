# 103. QA·Security 자체 생성 시험 실패 원인 점검

작성일: 2026-11-23. 101번 Multi Ver1과 102번 Single Ver1의 기존 기록만 읽었다. **코드 수정·새 Run·유료 API·Docker 재실행은 모두 0회**다.

## 결론

**이번 자체 시험 실패 16건은 시험 코드의 사용법 오류로 확인됐다.** 실행된 코드와 현재 파일의 SHA-256을 대조했으며, 다른 시험이나 과거 파일을 잘못 읽은 것이 아니다.

| 실행 | 자체 QA | 자체 Security | 실제 실패 원인 |
| --- | --- | --- | --- |
| Single Ver1 · 102번 | 0/5 PASS | 0/3 PASS | 없는 보조 기능 사용 7건, 딕셔너리 반환값 오독 1건 |
| Multi Ver1 · 101번 | 0/5 PASS | 0/3 PASS | 없는 보조 기능 사용 7건, 딕셔너리 반환값 오독 1건 |
| 합계 | 10건 실패 | 6건 실패 | **14건 + 2건 = 16건** |

같은 제품의 독립 최종 9개 시험은 양쪽 모두 PASS다. 이 16건을 회원가입 제품의 결함 16개라고 해석하면 안 된다. 그렇다고 모든 `[origin=TEST]` 오류를 무조건 무시해서도 안 된다. 이번 분류는 실제 예외 내용·사용된 API·반환형·시험 Source를 함께 대조한 결과다.

근거 요약: [findings.json](reports/generated-test-audit-2026-11-23/findings.json).

## 확인된 원인 1 — 존재하지 않는 기능 사용, 14건

생성 시험은 `self.fresh_email` 또는 `self.fresh_email()`을 사용했다. 하지만 Host의 `AppTestCase`에는 이 속성·메서드가 없다. 실제 기록에도 다음 오류가 남아 있다.

```text
AttributeError: 'SignupTests' object has no attribute 'fresh_email' [origin=TEST]
```

Security 시험에서도 같은 오류가 발생했다. 정상 제품을 검사하기 전에 시험 자체가 중단되는 형태다.

현재 안내에는 **자신이 fresh_email 값을 생성하라**는 설명이 있다. 이것을 Host가 제공하는 `self.fresh_email` 기능으로 잘못 사용했다. 테스트 작성 Agent의 잘못된 API 가정이며, 현재 사전 검사도 이를 차단하지 못했다.

해결 방향은 없는 API를 있다고 취급하는 것이 아니다. 허용된 시험 데이터 생성 방식과 실제 Host 기능을 명시하고, 자체 시험에서 존재하지 않는 fixture 기능을 사용하면 작성 단계에 정확히 되돌려줘야 한다.

## 확인된 원인 2 — 딕셔너리를 튜플처럼 사용, 2건

`signup_email_state()`의 실제 반환값은 다음 구조다.

```python
{
    "totalRows": 실제_숫자,
    "exactEmailRows": 실제_숫자,
    "hasDirectEmailUniqueKey": 실제_bool,
}
```

생성 시험은 이를 다음처럼 받았다.

```python
total_rows, exact_email_rows, has_unique_key = self.signup_email_state(email)
```

딕셔너리를 이렇게 풀면 숫자가 아니라 키 이름이 들어간다. 실제 Single 기록은 `'exactEmailRows' != 0`, Multi 기록은 `'totalRows' != 0`의 AssertionError다. DB에 사용자가 잘못 저장됐다는 증거가 아니다.

이 경우에는 반환 객체에서 `state["totalRows"]`, `state["exactEmailRows"]`처럼 필요한 실제 값을 읽어 기존 요구사항을 검사해야 한다. 기대 결과를 느슨하게 만들거나 무조건 PASS로 바꾸는 수정은 필요하지 않다.

## 플랫폼에서 함께 놓친 부분

### 1. 보조 기능의 계약이 기계적으로 충분히 명시되지 않음

`test_guidance.py`에는 fixture·데이터 공장·일부 함수 설명이 있지만, 사용 가능한 모든 메서드와 반환형을 닫힌 구조로 선언해 사전 대조하는 수준은 아니다. `generated_tests_precheck.py`는 파일·선언 시험·기본 lifecycle 사용 등을 검사하지만, 이번 두 가지 사용법 오류는 통과했다.

**보완 대상:** 실제 Host API에서 가져온 속성·메서드·인자·반환형 안내와, 알려진 오용을 검사하는 보수적인 Source 사전 검사. 사용자 정의 helper나 불확실한 상속을 임의로 금지하지 않아야 한다.

### 2. 시험 본문 오류가 시험 수정 경로에 연결되지 않음

실제 runner는 예외 내용을 `[origin=TEST]`와 함께 보존했다. 그러나 시험 본문의 이 오류들은 `FAIL`로 기록됐다. 현재 `technical_reasons()`는 정해진 `SKIP/NOT_RUN` 원인을 대상으로 하므로, 이 오류들이 기존의 같은 단계 내 시험 수정 기회를 열지 못했다.

또한 `case_feedback()`은 세부 관찰이 없으면 `DETAIL_RECORD_MISSING`으로 전달한다. 원본 영수증에는 없는 fixture API 사용이나 잘못된 반환형 사용이 남지만, 모델의 간결한 피드백에는 제품 실패와 구별할 구조화된 원인이 충분히 연결되지 않는다.

**보완 대상:** 불변 시험 코드·실행 프레임·실제 fixture 계약으로 확인된 제한된 시험 작성 오류만 시험 수정으로 되돌리는 경로. 같은 시험 ID·요구사항·기대 결과·제품 Snapshot과 기존 예산을 보존해야 한다. 실제 HTTP·DB 동작의 assertion 실패는 계속 제품 실패로 남겨야 한다.

## 앞의 오류를 고친 뒤 드러날 수 있는 문제

다음은 Source에서 확인한 **정적 관찰**이다. 이번에 새로 실행해 실패를 재현한 것으로 집계하지 않는다. 현재 16건은 위의 두 원인에서 이미 중단됐다.

| 관찰 | 문제 |
| --- | --- |
| `self.new_password(...)` | 해당 fixture 메서드가 없다. 제공되는 것은 `_host_test_data.new_password(...)` 모듈 함수다. |
| `assertIn(200, status1)` | `concurrent_signup_statuses()`를 풀어 받은 `status1`은 정수다. 정수를 목록처럼 검사할 수 없다. |
| 정확히 200·400만 허용 | 승인 규격은 성공 2xx·거부 4xx다. 정상적인 201·409 등을 잘못 실패시킬 수 있다. |
| 이미 가입한 이메일로 동시 요청을 보내며 새 성공 요구 | 두 요청 모두 중복 거부되는 것이 정상일 수 있다. 새 계정의 동시 생성 시험과 기존 계정 중복 시험을 구분해야 한다. |
| 해시 측정 함수만 호출하고 결과 검사·서로 다른 두 계정의 salt 관찰 누락 | 함수 호출 자체와 승인된 해시 정책 검증은 다르다. |
| Single QA의 `password=[REDACTED]` | 실행 파일에 정의되지 않은 식별자가 있다. 현재 오류 뒤에 있어 이 줄의 실패는 관찰되지 않았다. 가림 표식이 유입된 경계는 보존된 원본 wire 기록만으로 확정하지 않았다. |

따라서 `fresh_email` 하나만 보완하고 곧바로 유료 Ver2 실험을 반복하는 것으로 해결됐다고 판단하지 않는다.

## Ver1은 왜 통과했는가

실행 전에 동결된 Ver1 정책은 같은 요구사항의 공통 보호시험 결과를 우선 반영한다. 공통 QA 6개와 Security 3개 검사는 통과했고, 별도 독립 최종 시험도 9/9 PASS였다. 자체 시험의 실패 기록은 삭제되지 않았다.

Ver2에는 이 공통 보호시험이 없다. 현재 코드 경로를 보면 잘못 작성된 시험의 FAIL이 제품 수정 요청으로 이어질 가능성이 있다. **이는 코드 점검에 따른 예상이며, 이 판본의 Ver2를 실행해 관찰한 결과는 아니다.**

## 근거와 점검 범위

- `unit_test_execution_records`의 원본 결과·Source Manifest·입력 파일 SHA-256을 읽기 전용으로 대조했다.
- Single·Multi의 QA·Security 총 4개 생성 scope에서 실행 당시 시험 해시와 현재 파일 해시가 모두 일치했다.
- 16개 FAIL 전부 실제 runner 예외의 `[origin=TEST]`와 해당 시험 구문을 확인했다. 다른 시험의 실패를 재사용하거나 추측으로 개수를 채우지 않았다.
- 실제 `AppTestCase` 제공 기능·반환형, 사전 검사, `TestFixRequired`와 `technical_reasons()` 경로, 모델 피드백 투영 코드를 함께 확인했다.
- Docker·제품 Source·생성 시험을 새로 실행하지 않았다. 비밀값·사용자 설정·`.env`·실험 데이터·플랫폼 코드를 수정하지 않았다.

## 최종 표까지의 계획 조정

당초에는 이 점검 뒤 Ver2 두 조건을 실행하려 했다. 이번에는 시험 코드 오류와 오류 전달의 공백이 확인돼, **Ver2 실행 전에 이 부분부터 보완하는 것을 권장한다.**

**다음 104번:** Agent에 제공하는 fixture API·반환형 계약, 확인된 오용의 사전 검사, 같은 시험을 보존하는 제한된 수정 피드백을 묶어서 보완한다. 유료 API 호출 없이 코드·회귀 검사로 진행한다.

공통 코드가 바뀌면 기존 Ver1 성공 표본은 이전 판본의 검증 기록으로 보존하고, 최종 4조건 표는 새로 동결한 같은 판본에서 맞춰야 한다. 기존 두 결과를 새 Ver2 결과와 몰래 같은 판본으로 섞지 않는다. 현재 103번에서는 코드를 변경하지 않았으므로 101·102번 결과의 판본과 값은 그대로다.
