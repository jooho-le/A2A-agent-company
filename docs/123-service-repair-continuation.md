# 123. 기존 작업을 이어받는 수정 실행과 실패 검사 전달

작성일: 2026-11-27.

## 해결한 문제

`새 작업 만들기`에서 “이전 오류를 수정해줘”라고 입력하면, 기존 코드나 실패 기록이 연결되지 않았다. 실제로 원래 회원가입 API를 수정하는 대신 `/complete` 기능을 새로 기획한 기록이 있었다. 이전 작업을 자동으로 추측하는 대신, 사용자가 프로젝트와 실행을 선택해서 이어받도록 바꿨다.

실패 검사 피드백도 보완했다. `assertIn(response.status_code, (400, 422))`가 실패했을 때 기존에는 `AssertionError`만 남을 수 있었다. 이제 실제 `200`과 허용 상태 `[400, 422]`를 구분해 전달한다. 원본 요청 본문·비밀번호·예외의 로컬 변수는 복사하지 않는다.

## 사용 흐름

1. 내 프로젝트에서 수정할 실행을 연다.
2. **이어서 수정·재시도**를 누른다. 추가 설명은 선택 사항이다.
3. 같은 프로젝트에 새로운 수정 Run을 접수한다. 이전 Run·산출물·실패 기록은 그대로 남는다.
4. 이전 코드와 원래 요구사항, 확정된 API 규격, 실패 관찰을 새 실행에 전달한다.
5. 새 실행의 기획·구현·검증을 진행한다. 과거의 PASS나 코드 복사 자체를 새 실행의 성공으로 사용하지 않는다.

진행 중인 실행을 동시에 복제하거나, 다른 사용자의 프로젝트·다른 프로젝트의 Run을 가져오지 못하게 했다. 원래 작업을 지정하지 않은 “이전 오류 수정” 요청은 모델 호출 전에 선택 안내를 반환한다. 실패한 terminal Task를 답변으로 되살리는 방식은 사용하지 않는다.

## 코드와 요구사항 보존

- 제품 POST의 선택 필드 `continuationOf`로 부모 Run을 지정한다. `projectId`도 필요하며, 제품 서버가 JWT 소유권과 프로젝트 소속을 Host 호출 전에 검사한다.
- Host는 SERVICE-WEB에만 연결을 허용한다. 실험용 SCN-001, 보호시험 조건, 승인 시작 코드·의존성 잠금·실행 환경이 달라지는 연결은 거절한다.
- 마지막 등록 Source가 있으면 검증된 아카이브를 사용한다. 등록 Source가 없으면 부모의 제한된 작업 폴더에서 초안을 동결하고 `DRAFT_CHECKPOINT`로 구분한다. 초안을 Build PASS로 표시하지 않는다.
- 연결 정보와 파일 바이트·해시를 자식 Run 생성 및 접수 영수증과 같은 트랜잭션에 저장한다. 부모 상태가 바뀌었거나 수정 실행이 이미 진행 중이면 자식 생성 전체를 취소한다.
- 자식 작업 폴더는 원래 승인 Git 기준을 유지하면서 동결된 파일로 준비한다. Developer는 이 파일이 동결본과 같은지 다시 검사한다. 상속된 코드만 그대로 제출하는 것은 수정 진척으로 인정하지 않는다.
- 원래 Requirement ID·검수 기준·정책을 유지한다. 원래 API와 다른 `/complete` 관리 서비스를 만드는 식의 규격 교체도 차단한다.

운영용 연결 원장은 `service_continuations`, `service_continuation_files`에 저장한다. 변경·삭제는 허용하지 않으며 제품 사용자 DB 구조는 변경하지 않았다.

## 실패 재현 자료

Developer의 Fix Request에 실제 Source·역할·검사 버전에 연결된 생성 검사 파일을 읽기 전용으로 추가했다. 현재 작업의 실패 영수증과 파일 해시가 맞는 경우만 제공한다. 변할 수 있는 작업 폴더의 검사 파일로 대체하지 않는다.

- 보호시험·다른 Run의 검사·Host 검사기 자체는 전달하지 않는다.
- 재현 코드 합계는 48 KiB로 제한한다. 초과한 파일을 잘라 실행 가능한 코드인 것처럼 전달하지 않는다. 저장된 검사 파일이 없으면 새로 만들어 원본인 것처럼 제공하지 않는다.
- 단순 `assertEqual`뿐 아니라 실제 `assertIn` 실패에서도 HTTP 상태를 기록한다. 보호시험의 숨겨진 기대값은 이 진단으로 공개하지 않는다.
- 재현 자료를 보내는 쪽과 Developer의 신뢰 입력을 재구성하는 쪽이 같은 자료를 확인한다. 이 경로에 있었던 리스트/객체 자료형 오류도 수정했다.
- 원래 실패 검사의 재검사와 전체 QA·Security 검증은 기존 Host 판정 절차를 유지한다. 형식 수정·검사 준비 오류를 제품 수정 성공으로 계산하지 않는다.

## 화면과 접수 복구

이전 접수 키가 남아 있으면 GET으로 결과부터 확인한다. 확인되지 않은 요청을 새 키로 다시 POST하지 않는다. 이전 접수가 확인돼도 사용자가 지금 선택한 프로젝트를 다른 프로젝트의 Run으로 바꾸지 않는다.

이어서 수정할 때는 현재 승인 설정을 새로 조회한다. POST 전 승인 조회 실패는 “접수 결과 불확실”로 처리하지 않는다. Host가 `CONTINUATION_ALREADY_ACTIVE` 등 알려진 거절을 미접수로 확정한 경우에는 한국어 원인과 다음 행동을 표시한다. 의미를 확인할 수 없는 충돌과 응답 유실은 계속 불확실 상태로 보존한다.

## 검증과 범위

오프라인 ASGI·임시 SQLite/Git·가짜 모델/컨테이너 영수증·독립 브라우저 테스트를 사용한다. 실제 사용자 작업 폴더의 코드를 Host에서 실행하지 않았으며 유료 OpenAI 요청이나 새 서비스 Run을 제출하지 않았다.

| 검증 | 결과 |
| --- | --- |
| Host·Agent·Source·상태·수정 흐름 | 237개 + 별도 73개 통과 |
| 마지막 코드 변경 후 Source 상속·수정 진척 재확인 | 44개 통과. 위 검사와 중복이므로 합산하지 않음 |
| 제품 API 소유권·접수·복구·제어 | 43개 통과 |
| 프론트 접수·복원·질문·이어서 수정 | 18개 통과. 브라우저는 임시 프로필과 목업 HTTP 사용 |
| 프론트 lint·프로덕션 build | 통과. 기존 3D 번들 크기 경고는 유지 |
| 승인 Host 설정·키 존재 확인 | 통과. 제공자 API 요청 성공을 의미하지 않음 |

실행 중인 Run·Step이 없음을 확인한 뒤 제품 서버와 Host·Agent에 적용했다. 프론트·제품·Host·Agent 4개는 모두 HTTP 200, Agent 4개는 `executionReady=true`다. Host 인증은 서비스 토큰 없이 401, 기존 토큰으로 200을 유지했다. 프론트·Docker·환경설정과 기존 Run 기록은 보존했다.

기존에 회원가입을 만들던 실패 Run은 `continuationAvailable=true`로 조회된다. 원래 작업이 연결되지 않은 채 “이전 오류 수정”으로 새로 만들어졌던 Run은 `false`로 구분해 원래 작업을 선택하도록 안내한다. 두 Run의 종료 상태나 실패 판정은 변경하지 않았다.

가짜 모델로 통과한 수정 흐름은 실제 모델의 제품 구현 성공을 보장하지 않는다. 실제 OpenAI 전체 실행은 하지 않았으며 새 서비스 Run을 제출하지 않았다. 제공자 500 오류도 코드만으로 없앨 수 없으므로 기존의 제한된 재시도와 원인 구분을 유지한다.
