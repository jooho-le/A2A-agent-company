작성일: 2026-11-23. 사용자의 마지막 보완·재실행 요청에 따라 먼저 코드를 고치고 오프라인 검사를 수행한 뒤, 동결한 코드로 네 조건을 각각 한 번 실행했다. **추가 Run·성공할 때까지 반복·실행 중 코드 변경은 하지 않았다.**

## 이번에 보완한 코드

### 1. 암호화 비교 helper의 반환 규격과 실제 시험 수정 연결

110번의 실패 시험은 `signup_hash_parameters()`를 두 번 부른 뒤 첫 번째 반환값에서 `distinctSalts`를 읽었다. 반환 딕셔너리는 조회 당시의 사본이므로 첫 결과에 나중의 비교 사실이 생기지 않는다.

- fixture V8에서 항상 있는 키와 선택적 키를 분리하고 **두 번째 반환값으로 서로 다른 두 계정의 salt를 검사**하는 사용법을 명시했다.
- 직접 호출·변경되지 않은 반환값·확인 가능한 순서에서 첫 반환값의 잘못된 접근을 AST 사전 검사로 찾는다. 생성 시험을 호스트 Python에서 실행하지 않는다.
- 실제 실행 프레임·해당 구문·변경되지 않은 Host helper·반환형과 없는 키를 대조한 `KeyError`만 기존 `NOT_RUN_FIXTURE_RETURN_MISUSED`로 분리한다. 예외 문구만 보고 제품 실패를 숨기지 않는다.
- 같은 Source·요구사항·시험 ID·기대 결과를 보존하는 기존 한 번의 시험 수정 경로로 전달한다. 재사용 salt, 실제 HTTP·DB assertion 실패, 변조한 딕셔너리, 불확실한 사용자 정의 helper는 계속 실패로 남긴다.
- 숫자 해시 정책은 공개 최소 기준에 대해 `>=`로 검사하도록 안내했다. 첫 결과 접근을 `.get(..., True)`나 상수·skip으로 대체하도록 안내하지 않는다.

직전 Single Ver2·Multi Ver2의 저장된 시험 파일에서도 새 사전 검사가 해당 오용을 찾았다. 원본 DB 해시는 읽기 전후 같았다. 이번 실제 실행에서 자체 시험을 수행한 Single Ver2의 Security는 **3/3 PASS**였고, 저장된 자체 시험 결과에서 이전 `distinctSalts` KeyError는 재발하지 않았다. 다른 세 조건은 해당 자체 시험까지 도달하지 않았으므로 그 조건의 동작까지 성공했다고 주장하지 않는다.

### 2. 파일 생성·교체와 충돌 뒤 복구

- `write_source_file`의 해시 생략은 **새 파일 생성만** 허용한다. 기존 파일 교체에는 현재 파일의 `expectedSha256`이 필요하다. 기존 호출자도 파일을 교체할 때는 최신 해시를 전달해야 한다.
- 새 파일의 부재 확인과 쓰기를 기존 잠금·CAS 트랜잭션 안에서 처리한다. 다른 파일이 먼저 생기면 덮어쓰지 않고 `WRITE_CONFLICT`를 반환한다.
- 쓰기 충돌 뒤 같은 경로의 읽기가 `FILE_NOT_FOUND`로 확정되면 같은 읽기를 반복시키지 않고 **그 경로만 생성하는 제한된 쓰기**를 제공한다. 이때 모델이 다른 경로나 임의 해시를 선택할 수 없게 한다.
- 여러 파일을 함께 처리하다 일부만 거절되면 완료한 쓰기를 재실행하지 않고 거절된 경로만 순서대로 복구한다. 권한 거절·결과 불명·시간 초과 쓰기는 반복하지 않는다.
- 도구 오류·출력 교정·모델/도구/토큰 예산·Run 마감은 늘리지 않았다.

이번 네 실행의 도구 기록에서 `FILE_NOT_FOUND`는 없었다. 다만 `WRITE_CONFLICT`·부분 수정 대상 불일치가 남았으며, 모든 코드 수정이 성공했다고 해석하지 않는다.

### 3. 같은 정책으로 비교하도록 고정

Host 정책에 fixture V8, 도구 오류 복구 V6, `sourceWritePolicy=HASH_FOR_REPLACE_ATOMIC_ABSENCE_FOR_CREATE_V1`을 반영했다. `fileIo`·MCP 도구 카탈로그 코드도 구현 해시 대상에 포함했다. Single·Multi 모두 같은 코드·규칙을 사용했다.
