# 4번 담당 상세 명세: Evaluation / QA / Security / 비교 실험

| 항목 | 내용 |
|---|---|
| 담당자 | 강석민 |
| 작성일 / 버전 | 2026-09-28 / 0.1.1 |
| 상태 | 팀 검수용 설계 초안. 구현·실험 완료 보고서가 아님 |
| 담당 범위 | 검증 시스템, QA·보안 평가 기준, 비교 실험, 결과 분석·발표 근거 |
| 첫 구현 대상 | 회원가입 우선 제안. 최종 시나리오는 팀과 확정 |

## 1. 목적

생성된 소프트웨어의 요구사항 충족 여부를 실제 실행 결과로 검증한다. 기능 오류와 보안 문제를 구분하고, 실패 발견 → 개발 수정 → 재검증 과정을 추적한다. Single-Agent와 Multi-Agent를 동일 조건에서 비교하여 정확도·시간·비용·수정 과정의 장단점을 분석한다.

Multi-Agent의 우수성을 전제하지 않는다. 동일 조건에서 공정하게 비교하고 결과의 원인을 분석한다.

### 1.1 확정 수준

- **요구사항:** 담당 범위의 목표와 책임.
- **설계 제안:** 이 문서가 제안하는 모듈·식별자·필드·상태·평가 정책. 검수 후 확정.
- **협의 필요:** API·도구·실행 한도 등 다른 담당과 정할 내용. 18절에서 관리.

별도 표기가 없는 구체적인 함수명·경로·JSON 구조·테스트 ID는 설계 제안이다. 실제 구현이 존재한다는 의미가 아니다. 누락된 요구를 임의로 확정하거나, 결과를 통과시키기 위해 평가 기준을 낮추지 않는다.

## 2. 담당 범위와 협업 경계

| 작업 | 4번 책임 | 연결 담당 및 경계 |
|---|---|---|
| QA 기준 | 요구사항별 기대 결과·경계값·독립 평가 테스트 | 2번 QA Agent의 테스트 생성과 병행 |
| 보안 기준 | 검사 대상·재현·적용 여부·판정 근거 | 2번 Security Agent의 분석·도구 사용과 연결 |
| 검증 실행 | 평가 코드·결과 정규화·보고서 | 실행기 구현 4번, MCP 래핑 2번으로 나누는 제안 |
| 최종 판단 | 항목별 결과와 전체 평가 권고 | 최종 상태·재시도·종료 결정은 1번 |
| 로그 | 검사 증거 생성·필드 정의·분석 | 전체 이벤트 저장·Task 상태 DB는 1번 |
| 대상 서비스 | API·DB·환경에 맞춘 검사 | 서비스·화면·인증·DB 구현은 3번 |
| 비교 실험 | 조건·반복 계획·공통 평가·집계 | Single/Multi 실행 진입점은 1·2번과 연결 |
| 발표 근거 | 실패·수정·재검증 사례·그래프·한계 | 팀 전체 발표 구성과 연결 |

4번은 A2A 서버, Agent 프롬프트 전체, MCP 서버 전체, 서비스 화면, Orchestrator를 중복 구현하지 않는다. QA·Security Agent는 제품 코드를 직접 수정하지 않고 결함을 반환한다. 테스트·판정 코드의 결함은 4번이 수정하고 기준 변경 이력을 남긴다.

### 2.1 담당 간 계약

| 담당 | 제공받을 정보 | 전달할 정보 |
|---|---|---|
| 1번 | run/task ID, 고정 코드 버전, 시간·반복 한도, 저장 규약 | 결과 스키마·종료 권고·증거·수정 회차 |
| 2번 | 기획 Artifact, Agent 검사 결과, MCP 호출·응답 형식 | 검사 진입점·입력 검증·정규화 규칙 |
| 3번 | API 규격, 기동·준비 확인·종료, 테스트 DB·계정·조회 수단 | 케이스·테스트 데이터·실패 재현 절차 |

실행기가 실제 시간·종료 코드를 기록하고, 모델 호출 담당이 사용량을 제공해야 한다. 4번이 Agent 설명으로 시간·토큰 수·실행 결과를 추정하지 않는다.

## 3. 구현 범위와 단계

### 3.1 초기 범위

1. 공통 검증 요청·결과 형식과 판정 규칙.
2. 회원가입 요구사항의 단위·통합 테스트와 대표 화면 흐름.
3. 비밀번호 저장·민감정보 노출 등 적용 가능한 보안 검사.
4. 실패 → 수정 → 같은 새 버전의 QA·보안 재검증 연결.
5. 첫 시나리오의 Single/Multi 공통 평가 및 비교.

### 3.2 확장 및 제외

전자문서와 추리게임은 공통 결과 형식에 시나리오별 검사기를 추가한다. 회원가입 → 전자문서 → 추리게임은 초기 구현 순서 제안이며, 모두 첫 구현에서 완료한다는 의미는 아니다.

대규모 부하 시험, 전체 화면 자동화, 침투 테스트 전체 범위, 별도 관측 플랫폼, 외부 배포는 초기 범위에서 제외한다. 보안 통과는 합의된 검사 범위의 충족이며 모든 취약점의 부재를 보장하지 않는다.

## 4. 검증 구조와 공통 평가

검증 대상은 두 종류다.

- **생성된 서비스:** 가입·문서 처리·게임 진행이 요구사항대로 동작하는지 검사.
- **협업 시스템:** 실제 도구 실행, 증거 전달, 수정 분기, 버전 일치, 중단 규칙 검사.

QA Agent의 요구사항 기반 독립 테스트와 팀의 공통 평가 테스트를 구분한다. Agent 테스트는 개발·수정에 활용하고, 비교 점수는 동일한 공통 평가 테스트로 산정한다. 공통 테스트가 Agent의 독립적인 테스트 생성 요구를 대체하지 않는다.

공통 요구사항·테스트는 버전과 해시로 관리한다. Developer는 평가 기준을 수정할 수 없다. 기준 자체의 오류를 고칠 경우 변경 사유·담당·이전 버전을 남기고 양쪽을 새 기준으로 다시 평가한다. 기존 점수를 덮어쓰지 않는다.

초기 제안은 공통 평가 피드백을 양쪽에 동일하게 제공하고 예산 내 수정을 허용하는 방식이다. 비공개 최종 테스트를 도입하면 공개 범위·수정 기회를 양쪽에 동일하게 적용하고 실험 조건에 명시한다.

## 5. 입력·출력 인터페이스

### 5.1 검증 요청

| 필드 | 형식·필수 여부 | 의미 |
|---|---|---|
| schema_version | 문자열, 필수 | 요청 구조 버전 |
| run_id / task_id | 문자열, 필수 | 실행과 A2A 작업 연결 |
| scenario_id | 등록된 문자열, 필수 | signup / document / game 등 |
| mode | single / multi, 필수 | 실행 구조 |
| artifact_version | 문자열, 필수 | 커밋 SHA 또는 불변 소스 스냅샷 ID |
| requirements_version | 문자열, 필수 | 요구사항 기준 버전 |
| suite_version | 문자열, 필수 | 공통 평가 테스트 버전 |
| attempt | 0 이상 정수, 필수 | 최초 생성 0, 이후 수정 회차 |
| suite | qa / security / pipeline, 필수 | 검사 종류 |
| requirement_ids / test_ids | 문자열 배열, 필수 | 평가 대상. 최종 판단 시 필수 항목 누락 불가 |
| target_ref | 승인된 참조, 필수 | 고정 코드·서비스·DB 설정 참조 |
| limits | 시간·출력 크기 한도, 필수 | 합의된 실행 제한 |
| previous_report_id | 문자열 또는 null | 재검증 시 이전 결과 |

임의 쉘 명령이나 외부 URL을 입력받아 실행하지 않는다. target_ref는 허용 목록으로 해석한다. 자격증명은 본문에 직접 넣지 않고 합의된 별도 참조로 전달한다.

입력 누락, 알 수 없는 시나리오, 허용 영역 밖 대상, 지원하지 않는 스키마는 실행 전 REQUEST_INVALID로 거부한다. 이는 제품 FAIL과 구분한다. 실험 요청 수락 전 오류는 실행 건수에 넣지 않고 별도 기록한다.

### 5.2 논리 모듈 제안

| 모듈 | 책임 |
|---|---|
| validation | 요청·결과 구조와 ID·버전 검사 |
| runner | 검사 실행, 준비 상태·시간 제한·정리 |
| adapters | 실제 도구 결과를 공통 형식으로 변환 |
| reporting | 결과·결함·증거·요약 생성 |
| evaluation | 요구사항 충족과 완료 권고 계산 |
| experiments | 실행 조건 저장, 반복 실험 집계 |

같은 검증 코드를 로컬 실행과 MCP 연결에서 재사용한다. API·CLI·함수명은 아직 확정하지 않는다. 미구현 명령을 실행 가능한 사용법으로 표시하지 않는다.

## 6. 실행 환경과 생명주기

1. 요청을 검증하고 요구사항·테스트·코드 버전을 고정한다.
2. 격리 환경·합성 데이터를 준비하고 이전 DB·파일 상태를 초기화한다.
3. 빌드·기동·준비 상태를 확인한다. 빌드 실패 결과를 보존하고 서비스 검사는 NOT_RUN 처리한다.
4. 고정 스냅샷에서 QA·보안을 실행한다. 병렬 실행은 DB·계정·파일 영역을 분리한다.
5. 종료 코드, 항목별 결과, 표준 출력·오류, 증거를 자동 수집한다.
6. ID·버전·필수 항목·증거를 검증하고 보고서를 생성한다.
7. 성공·실패·시간초과와 관계없이 자식 프로세스·서버·임시 데이터를 정리한다. 정리 실패도 기록한다.

환경 준비 실패는 ERROR이며 제품 결함으로 단정하지 않는다. 성능 요구가 없는 검사 시간초과는 ERROR/TIMEOUT이다. 명시된 응답시간 요구의 위반이 확인된 경우에만 해당 제품 요구의 FAIL로 판정한다.

OS·런타임·패키지·도구 설정·컨테이너 이미지 ID·fixture 버전을 기록한다. 준비 상태 확인, DB 검증 접근, 초기화, 시간 제한값은 협의 후 확정한다. 운영 계정·운영 DB는 사용하지 않는다.

### 6.1 도구 선정·오류 해석

Python 평가 실행기와 pytest·HTTP 클라이언트를 초기안으로 제안한다. 다른 언어의 단위 테스트 결과는 어댑터로 수집한다. 주요 사용자 흐름에는 브라우저 검사를 적용한다. 정적 보안 도구는 대상 언어·규칙 범위를 확인한 후 선정한다.

검사 0개 수집·결과 파싱 실패·필수 도구 부재는 PASS가 아닌 ERROR다. 종료 코드 0만으로 항목별 PASS를 생성하지 않는다. 도구별 테스트 실패·경고·실행 오류의 종료 코드를 구분한다. 모의 결과는 mock으로 표시하고 실제 실행 증거와 섞지 않는다.

## 7. 회원가입 QA 상세 기준

아래 REQ ID를 scenario_id=signup과 함께 사용한다.

| 요구사항 | 내용 | 연결 검사 |
|---|---|---|
| REQ-001 | 이메일·비밀번호 가입 | QA-SIGNUP-001 |
| REQ-002 | 잘못된 이메일 거부 | QA-SIGNUP-002 |
| REQ-003 | 중복 이메일 금지 | QA-SIGNUP-003 |
| REQ-004 | 비밀번호 최소 8자 | QA-SIGNUP-004, QA-SIGNUP-005 |
| REQ-005 | 비밀번호 평문 저장 금지 | SEC-SIGNUP-001 |
| REQ-006 | 가입 결과 반환 | QA-SIGNUP-006 |

공통 사전 조건은 테스트 서비스·초기화된 DB·확정 API 계약·데이터 정리 수단이다. HTTP 상태 코드·JSON 키는 3번 규격에 맞춘다.

| ID | 입력·사전 조건 | 절차 | 기대 결과 |
|---|---|---|---|
| QA-SIGNUP-001 | 미등록 user@example.com, 유효 비밀번호 | 가입 → 응답·DB 확인 | 계정 1개 생성, 성공 반환, 필드 일치 |
| QA-SIGNUP-002 | userexample.com, 나머지 유효 | 요청 전후 DB 비교 | 입력 거부, 신규 계정 없음, 정확한 오류 |
| QA-SIGNUP-003 | 동일 이메일 계정 1개 존재 | 같은 이메일 재가입 → 조회 | 거부, 기존 계정 유지, 계정 수 1개 |
| QA-SIGNUP-004 | 미등록 이메일, A1b2c3d(7자) | 가입 → 조회 | 길이 조건으로 거부, 신규 계정 없음 |
| QA-SIGNUP-005 | 미등록 이메일, A1b2c3d4(8자) | 가입 → 조회 | 다른 조건 충족 시 허용 |
| QA-SIGNUP-006 | 성공·실패 케이스 각각 | DB 결과와 API·화면 대조 | 실제 결과와 안내 일치 |

예시 비밀번호는 합성 데이터이고 실제 사용자 정보가 아니다. 증거에는 비밀번호 값을 저장하지 않는다. 각 케이스는 fixture 버전, 입력, 단계, 기대값, 증거, 정리 절차를 포함한다. 응답만으로 DB 저장 성공을 추정하지 않는다.

이메일 대소문자·공백 정규화, 유니코드 길이 해석, 필수 필드 누락·빈값·최대 길이·동시 중복 요청 정책은 협의 후 추가한다. 미정 정책을 실패 근거로 사용하지 않는다.

단위 테스트는 핵심 입력 검증 로직, 통합 테스트는 요청부터 DB·응답, 화면 테스트는 정상 가입과 대표 오류 안내를 담당한다. 내부 함수·DB 접근·UI 계약을 받은 후 구체 코드를 작성한다.

## 8. 보안 검증 기준

### 8.1 회원가입 검사

| ID | 검사 | 판정·증거 | 적용 |
|---|---|---|---|
| SEC-SIGNUP-001 | 비밀번호 저장 | 원문 비저장, 저장 경로·알고리즘 설정·검증 동작 확인 | REQ-005 필수, 해시 강도 정책은 협의 |
| SEC-SIGNUP-002 | 민감정보·오류 노출 | 응답·로그의 비밀번호·키·토큰·내부 오류 정보 확인 | 적용 가능한 응답·로그 |
| SEC-SIGNUP-003 | SQL Injection | 쿼리 구성 분석과 격리 환경 재현으로 의도 밖 조회·저장 확인 | SQL 사용 시 |
| SEC-SIGNUP-004 | XSS | 사용자 입력 출력 위치 분석, 브라우저에서 스크립트 비실행 확인 | 입력 출력 UI 존재 시 |
| SEC-SIGNUP-005 | 서버 입력 검증 | UI를 거치지 않아도 합의된 제약 유지 | API 필수 |
| SEC-SIGNUP-006 | 하드코딩 비밀정보 | 소스·설정 경고와 실제 비밀 여부 확인 | 대상 소스 |

비밀번호 평문 저장 금지와 추가 합의할 안전한 해시 정책을 구분한다. 원문과 저장값이 다르다는 사실만으로 안전한 저장을 선언하지 않는다. 단순 인코딩·가역 변환 등도 검토한다.

### 8.2 발견 사항과 완료 차단

발견 사항 상태는 suspected / confirmed / false_positive / resolved를 제안한다. 정적 경고만으로 취약점을 확정하지 않고 재현 결과 또는 명확한 코드 근거를 첨부한다. 재현하지 못했다는 이유만으로 오탐 처리하지 않는다.

심각도와 완료 차단 여부를 구분한다. 초기안은 필수 보안 요구 위반과 확인된 high/critical 결함을 차단하고, 필수 검사에 연결된 미확인 경고는 판단 보류한다. 심각도 산정과 medium/low 정책은 실험 전에 확정한다. 필수 요구 위반은 심각도가 낮아도 통과할 수 없다.

비대상은 기능 부재 등 근거와 사전 승인된 적용성 목록이 필요하다. 도구 미설치·시간 부족·재현 환경 부재는 NOT_APPLICABLE이 아닌 ERROR/NOT_RUN이다. 경고가 없다는 사실만으로 실제 재현 검사를 생략하지 않는다.

### 9.2 추리게임

확정 게임 명세의 시작 상태·합법적 행동·승리 조건·전이를 검사로 변환한다. 대표 클리어 경로, 진행 불가 상태, 필수 조건 우회, 잘못된 입력, 재시작·저장 복구(기능이 있을 때)를 검증한다. 검사한 경로와 전체 상태 공간을 구분하여 보고한다.

클리어 가능성은 QA이며 재미·이야기 품질은 별도 정성 평가다. 사용자 입력 출력, 외부 자원, 파일·설정 등 실제 공격 표면에 맞춰 보안 범위를 정한다. SQL·계정 기능이 없으면 비대상 근거를 남긴다. 게임 요구사항 확정 전 이 목록을 완료된 상세 테스트로 간주하지 않는다.

## 11. 결과 스키마와 판정

### 11.1 개별 상태

| 상태 | 정의 |
|---|---|
| PASS | 실제 실행, 합의된 기대값 충족 |
| FAIL | 실제 검사에서 요구 위반 확인 |
| ERROR | 환경·도구·증거 수집 오류로 유효 검증 미완료 |
| NOT_RUN | 예정된 검사 미실행 |
| NOT_APPLICABLE | 사전 승인된 적용 제외, 사유·결정 참조 필수 |

필수 ERROR·NOT_RUN이 남으면 완료 불가다. 필수 요구를 임의로 비대상 처리하지 않는다. 적용 대상 0개는 100%가 아닌 null과 사유로 표시한다.

### 11.2 보고서 구조

요청의 식별·버전 필드와 report_id, status, started_at, finished_at, duration_ms, tool, results, findings, evidence, summary, completion_recommendation을 포함한다. 날짜는 UTC ISO 8601, 소요시간은 단조 시계로 측정한다.

results에는 test_id, requirement_ids, required, status, expected, actual, error_code, evidence_ids, duration_ms를 넣는다. findings에는 finding_id, fingerprint, category, severity, status, requirement_ids, test_ids, reproduction, evidence_ids, first_seen_version, resolved_version을 넣는다.

증거는 evidence_id, 승인된 저장소 기준 상대경로, SHA-256, 종류, 생성 도구, 민감정보 제거 여부를 가진다. 파일 누락·해시 불일치는 필수 근거 누락으로 처리한다. 도구 종료 코드와 제품 판정은 분리한다.

### 11.3 합성 결과 예시

### 11.4 전체 판정

보고서의 status는 요청된 검사 집합에서 ERROR > FAIL > NOT_RUN > PASS 순으로 집계한다. 전부 승인된 비대상이면 NOT_APPLICABLE이다. 전체 completion_recommendation은 필수 보고서를 모두 취합하는 단계에서 계산한다. 단일 검사 예시의 NEEDS_REPAIR는 그 검사 범위의 권고이며 전체 평가 완료를 뜻하지 않는다.

평가 권고를 1번 상태 모델과 매핑하는 초기안이다.

1. 필수 보고서·버전·스키마·증거가 불완전하면 INCOMPLETE. 확인된 결함도 함께 보존한다.
2. 유효한 결과에서 필수 요구 실패 또는 차단 보안 결함이 있으면 NEEDS_REPAIR.
3. 전체 적용 필수 검사 PASS, 핵심 요구 충족, 차단 문제 해소, 같은 코드·기준 버전의 증거 확보 시 READY.

READY는 평가 권고이며 배포 승인이 아니다. 최종 workflow 상태·중단·인계는 Orchestrator가 결정한다. 관찰용 선택 검사는 별도 표시하고 필수 분모를 임의로 바꾸지 않는다.

## 12. 실패 전달과 재검증

실패 보고에 요구사항 ID, test/finding ID, 기대·실제값, 재현 절차, 코드 버전, 증거를 포함한다. 1번이 Developer Task로 전달한다. QA·Security는 제품 코드를 직접 수정하지 않는다.

최초 생성 attempt=0, 수정 결과 제출마다 1 증가를 제안한다. 수정 최대 3회는 설계 초안이며 팀 확정이 필요하다. 인프라 재시도는 수정 회차와 별도 집계하되 전체 시간·비용에 포함한다. 기존 실패 실행을 덮어쓰지 않는다.

수정 시 새 artifact_version에 QA·보안을 재실행한다. 실패 항목과 핵심 회귀 검사는 기본적으로 모두 재실행한다. 평가 기준이 바뀌면 requirements/suite_version도 올리고 비교 가능성을 재검토한다.

한도 도달·판단 불가·반복 결함은 미해결 요구·결함·버전·증거·중단 이유와 함께 인계한다. ERROR는 제품 수정 요청으로 무조건 넘기지 않고 환경 복구·검사 수정과 구분한다.

## 13. Single/Multi 비교 실험

### 13.1 통제 조건

| 조건 | 통제 방식 |
|---|---|
| 모델 | 같은 모델·버전·주요 설정, 값 기록 |
| 입력 | 같은 사용자 요구·완료 기준 |
| 초기 상태 | 같은 코드 골격·데이터·도구·환경 |
| 수정 기회 | 양쪽 모두 검사·수정 가능, 동일 총예산·피드백 정책 |
| 평가 | 고정 공통 테스트·보안 기준·종료 규칙 |
| 프롬프트 | 역할 차이는 허용하되 요구 정보와 책임 동등 |
| 사용량 | Multi의 모든 Agent·재시도 합계 |
| 실행 순서 | Single/Multi 교대, 캐시·모델 준비 상태 기록 |

동일 조건을 반복하고 모델 응답의 변동성을 인정한다. 최초 제안은 채택된 시나리오별 구조당 5회이며 파일럿 비용을 보고 확정한다. 회원가입은 6개 REQ와 검사 연결을 보존한다.

### 13.2 실험 종류

- 전체 개발: 같은 요구로 기획·생성·검증·수정 전 과정 실행.
- 오류 복구: 같은 결함·코드 버전을 제공해 발견·수정 비교.

experiment_type과 defect_origin(natural / injected)을 기록한다. 주입 결함과 자연 발생 결함을 섞지 않는다. 알려진 결함 수가 없는 자연 발생 실험에서 결함 발견 재현율을 임의 계산하지 않는다.

### 13.3 지표

| 지표 | 계산·기록 규칙 |
|---|---|
| 요구사항 충족률 | 연결 필수 기준을 모두 충족한 REQ 수 / 사전 확정 적용 REQ 수 |
| 공통 테스트 통과율 | PASS 수 / 사전 확정 적용 검사 수. ERROR·NOT_RUN도 분모 포함 |
| 전체 성공률 | READY 및 workflow 완료 충족 수 / 수락된 전체 실험 실행 수 |
| 보안 결과 | 확인된 고유 결함·해결·미해결·미확인 경고 각각 |
| 오류 발견 수 | 고유 fingerprint 기준. 같은 결함 재보고는 중복 제외 |
| 수정 횟수 | 최초 생성 제외, 수정 코드 제출 회수. 빌드·QA·보안 원인 구분 |
| 첫 실행 가능 시간 | 요청 수락부터 최초 빌드·기동 성공까지 |
| 검증 완료 시간 | 요청 수락부터 최종 필수 검증 완료까지의 실제 경과시간 |
| 총 소요시간 | 실패·취소·시간초과 포함 시작부터 종료까지 |
| 사용량·비용 | 입력·출력·캐시 토큰, 단가·기준일·통화, 전체 호출 비용 |

요구사항에 테스트가 여러 개여도 충족률에서는 한 번만 센다. 증거 없는 요구는 충족으로 세지 않는다. N/A는 사전 승인한 적용성 목록에 따라 양쪽에서 동일하게 제외한다. 분모 0이면 null이다.

결함 중복은 시나리오·요구사항·원인·위치·재현 증상으로 판단하고 규칙을 기록한다. 줄 번호 변화만으로 새 결함으로 세지 않는다. 발견 수가 많다고 품질이 우수하다고 해석하지 않고 생성 결함·해결률·미해결 상태를 함께 본다.

전체 경과시간과 Agent 누적 작업시간을 구분한다. 병렬 QA 10초·보안 10초를 전체 20초로 합산하지 않는다. 사람 대기·모델 로딩·큐 대기는 별도 기록한다. 초기안은 전체 시간에 포함하고 자동 처리시간을 보조 지표로 제공한다.

실패 실행의 검증 완료 시간은 null이다. 성공 건의 시간 중앙값·범위와 성공률·시간초과 수·전체 시간을 함께 보고한다. 수락 후 취소·환경 실패는 기본 전체 분모에 포함하고 유형을 표시한다. 재실험 시 이전 run을 삭제하지 않는다. 제외 분석을 추가하면 원래 전체 집계와 사유도 제공한다.

비용 누락은 0원이 아닌 unknown이다. 로컬 모델의 API 비용과 장비·실행시간 비용을 구분한다. 실제 정산과 실험 추정 비용도 구분한다. 토큰 단가 등 외부 값은 실험 시점에 확인하여 저장한다.

## 14. 로그·증거·안전 경계

1번의 전체 로그에 run → task → requirement → artifact_version → test/finding → repair attempt → 재검증을 연결한다. 4번은 필요한 이벤트·증거·분석 결과를 제공한다.

증거는 run/attempt/suite별로 분리하며 덮어쓰지 않는다. 비밀번호·키·토큰·개인정보는 기록 전에 제거한다. 초기 실험은 합성 데이터만 사용한다. 원시 증거의 공유 위치·접근 권한·보존 기간은 18절에서 확정한다. Git에서 원시 결과를 제외하더라도 검수자가 확인할 보고서·증거 참조를 제공한다.

허용 경로·명령·네트워크 대상으로 제한하고 생성 코드·검사를 격리한다. 임의 외부 사이트를 시험 대상으로 삼지 않는다. 외부 배포·실제 개인정보 전송·외부 계정 접근은 승인 경로를 사용하고 검사 PASS로 대체하지 않는다. 관련 제어 구현은 1·2번, 확인 기준은 4번과 분담한다.

## 15. 산출물과 제안 디렉터리

```text
docs/evaluation_spec.md          # 이 명세
evaluation/                     # 요청 검증·실행·결과 변환·평가 (예정)
tests/evaluation/               # 평가 코드 자체의 의미 있는 검사 (예정)
evaluation_suites/signup/       # 공통 평가·fixture (예정)
evaluation_suites/document/     # 확장 시 추가
evaluation_suites/game/         # 확장 시 추가
experiments/                    # 실험 설정·집계 절차 (예정)
docs/evaluation_examples/       # 합성 결과 예시 (예정)
```

팀 구조·스택 합의 후 확정한다. 위 구현 파일은 현재 존재하지 않는다. 가상환경·개인 IDE 설정·비밀정보·대용량 원시 증거는 커밋하지 않는다.

최종 제출물은 명세, 요구사항-검사 표, 실제 검사 코드·fixture, 실행·초기화 안내, 스키마, 실제 보고서·증거, 수정 이력, 실험 설정·원본 측정값·집계 코드, 그래프·발표 사례다.

## 16. 완료 조건과 자체 검증

| ID | 완료 조건 | 확인 |
|---|---|---|
| DONE-01 | 다른 팀원이 준비·실행·정리 재현 | 깨끗한 환경에서 절차 수행 |
| DONE-02 | 정상·기능 실패·보안 실패·환경 오류 구분 | 각 통제 fixture 결과 대조 |
| DONE-03 | 누락·0개 수집을 PASS 처리하지 않음 | 누락·빈 결과·파싱 실패 입력 |
| DONE-04 | 버전·실제 증거에 근거한 완료 권고 | 불일치·증거 누락·변조 확인 |
| DONE-05 | 실패 → 수정 → 회귀 검사 연결 | 대표 결함 전 과정 재현 |
| DONE-06 | 같은 기준으로 Single/Multi 집계 | 알려진 표본의 수기 계산과 대조 |
| DONE-07 | 실패·시간초과·비용 누락 표시 | 해당 실행이 포함된 보고서 |
| DONE-08 | 민감정보 제거·제한·정리 | 합성 비밀값·허용 밖 경로·timeout 확인 |

평가 코드 자체는 실제 오판 가능성이 있는 집계 분모, 버전 불일치, 필수 누락, timeout·cleanup을 검증한다. 샘플 JSON 파싱 성공만으로 평가 시스템 완료를 선언하지 않는다.

## 17. 구현 순서와 이번 검수 범위

1. 범위·첫 시나리오·입출력·미정 정책 검수.
2. API·Artifact에 맞춰 대응표와 결과 형식 확정.
3. 실행기·변환·판정 구현, 통제된 정상·실패·오류 확인.
4. 첫 서비스 실제 QA·보안 증거 확보.
5. 실패 전달·수정·재검증·중단 통합.
6. 파일럿 비용·시간으로 반복 횟수·예산 확정 후 본 실험.
7. 확장 시나리오와 발표 자료 보완.

이번 커밋은 상세 명세 초안이다. 테스트 코드·Agent 통합·비교 실험은 후속 구현이며 예시는 실행 성공 증거가 아니다.
