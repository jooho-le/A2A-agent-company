# 91. 보강 후 SCN-001 실제 API 비교 실행

실행일: 2026-11-22. [90번 보강](90-agent-quality-hardening.md) 이후의 코드로 실제 OpenAI API와 Docker를 사용한다. 과거 석민 담당자의 표나 89번 결과를 재사용한 수치가 아니다.

## 입력과 네 조건

입력 문장: **“이메일과 비밀번호로 회원가입 기능을 만들어줘.”**

| 조건 | 실행 구조 | 개발 중 공통 보호시험 |
| --- | --- | --- |
| Single Ver1 | 하나의 Context에서 기획·개발·QA·Security 순차 수행 | 제공 |
| Multi Ver1 | 역할별 에이전트, QA·Security 병렬 검증 | 제공 |
| Single Ver2 | 하나의 Context에서 기획·개발·QA·Security 순차 수행 | 미제공 |
| Multi Ver2 | 역할별 에이전트, QA·Security 병렬 검증 | 미제공 |

모든 조건에서 자체 QA·Security 검사를 수행한다. 독립 채점은 같은 `final` 시험지의 상위 검사 9개로 수행하며, 생성 코드와 모델에 최종 시험 입력을 전달하지 않는다.

## 고정 조건

- 모델: `gpt-4.1-mini-2025-04-14`, temperature 0.
- 시작 코드: 기존 실험 전용 기준 커밋. 새 기준 커밋을 생성하지 않는다.
- Docker 이미지와 의존성 Lock: 설치되어 있던 SCN-001 이미지·Lock을 모든 조건에 동일하게 사용한다.
- Run별 한도: 모델 200회, Tool 200회, 응답 8,192 tokens, 전체 2,000,000 tokens, 실행 20분.
- 출력 교정 2회, 질문 안내 1회, 안전한 Provider 재시도 1회. 제품 수정·도구 재시도는 기존 정책을 유지한다.
- 계획: 조건별 10회, 최대 40회. 반복마다 실행 순서를 반대로 하며 실험 Run끼리는 순차 실행한다.
- 운영 중단 기준: 검토·입력 대기로 3회 연속 멈추거나, 실행 환경 오류·구현 변경이 확인되면 신규 제출을 중단한다. 이 경우 완료한 횟수만 보고하며 40회 완료로 표시하지 않는다.
- 각 Run은 새 DB·Workspace·Context·중복 방지 키를 사용한다. 보류된 Run에 답하거나 재개하지 않는다.
- 실행 중 `src/`와 `schemas/`의 고정 파일 해시가 바뀌면 다음 신규 Run을 제출하지 않는다. 동일한 구현의 결과만 모은다.

`scripts/run_scn001_comparison.py`가 단일 진단 실행기를 재사용해 새 폴더에서 실행한다. 기존 로컬 설정·환경변수 파일·제품 DB·과거 원자료를 덮어쓰지 않는다. 키와 서비스 토큰은 자식 프로세스 환경에서만 전달하며 파일·표에 기록하지 않는다.

## 결과를 읽는 규칙

1. **요구사항 충족률:** 독립 보고서에서 충족된 제품 요구사항을 집계한다. 앱을 불러오지 못해 모두 미검증인 경우는 실제 0% 실패와 구분한다. 미채점 수와 미검증 수를 별도로 기록한다.
2. **통과 제품의 판정 시간:** 최종 9개 검사 전체 통과 제품 중 실제 Host 판정 시간이 있는 실행만 평균낸다. 없으면 `해당 없음`이며 종료·중단 시간으로 대체하지 않는다.
3. **전체 실행 소요 시간:** 실패·중단도 포함한 실제 종료 경과 시간으로 별도 제공한다.
4. **비용:** 실행 시 기록된 토큰과 설정된 가격표 기준 추정 USD다. OpenAI 청구서 확정 금액이라고 표시하지 않는다. 비용을 모르는 실행은 0으로 대체하지 않는다.
5. **수정 횟수:** Host가 기록한 제품 수정 시도다. 시험 초안 교정이나 Provider 재시도와 합치지 않는다.
6. **완제품 통과율:** 실제 실행한 횟수가 분모다. 계획 40회를 완료하지 못했다면 미실행을 실패로 넣거나 조건별 10회를 완료한 것처럼 쓰지 않는다.

개발 중 보호시험의 성공 여부와 독립 최종 시험의 성공 여부, Host의 최종 상태는 서로 구분한다. 검토 대기에서 마지막 Snapshot만 독립 통과한 경우에도 정상적인 Host 완료로 바꾸지 않는다.

## 최종 결과

**네 조건 각 10회, 총 40회를 완료했다.** 실행 중 에이전트·Schema 파일 해시는 바뀌지 않았으며, 40개의 서로 다른 Run ID와 계획 순서 1~40, 동일 시작 Commit/Snapshot·모델·한도·이미지·Lock을 대조했다. Ver1에는 보호 범위 2개, Ver2에는 0개가 들어갔고, 독립 채점은 모두 `final` 시험지를 사용했다.

| 지표 | Single Ver1 | Multi Ver1 | Single Ver2 | Multi Ver2 |
| --- | ---: | ---: | ---: | ---: |
| 실제 실행 | 10회 | 10회 | 10회 | 10회 |
| 제품 요구사항 충족률 하한~상한 | 70.0~80.0% | 57.1~81.4% | 48.6~84.3% | 61.4~81.4% |
| 독립 최종 9개 시험 전체 통과율 | 0% (0/10) | 10% (1/10) | 10% (1/10) | 0% (0/10) |
| 9개 통과 제품의 평균 Host 판정 시간 | 해당 없음 | 113.7초 (1건) | 399.0초 (1건) | 해당 없음 |
| 종료·중단까지 평균 경과 시간 | 362.7초 | 142.0초 | 260.7초 | 188.7초 |
| 가격표 기준 평균 비용의 확인된 하한 | ≥$0.2455 | ≥$0.1018 | ≥$0.1808 | ≥$0.1347 |
| 비용이 미확정인 실행 | 2/10 | 2/10 | 1/10 | 1/10 |
| 평균 개발 수정 시도 | 1.9회 | 0.5회 | 1.1회 | 0.8회 |
| Host 자체 SUCCESS 판정 | 0/10 | 0/10 | 0/10 | 0/10 |

**충족률 범위는 통계적 신뢰구간이나 예측치가 아니다.** 제품 요구사항 7개 × 10회에서 실제 PASS만 세어 하한을, 미검증 항목도 충족할 수 있다고 둘 때의 값을 상한으로 계산했다. 미채점 실행은 7개 모두 미확인으로 둔다. 미검증이지만 확인된 실패가 함께 있는 요구사항은 상한에 더하지 않는다. 미확인을 실제 FAIL로 둔 평균이나, 채점된 제품만 골라 낸 평균으로 바꾸지 않았다.

비용은 일부 호출 사용량이 없어 6개 Run의 총액이 미확정이다. 완전한 비용 또는 확인된 부분합을 더해 10으로 나눈 하한을 표시했다. 기록된 모델 호출은 1,354회이며, 가격표로 산정 가능한 비용 부분합은 **$6.6282500**이다. 청구서 확정 금액이나 정확한 총비용이 아니다.

### 통과 제품과 Host 판정의 차이

| 독립 시험 9개 PASS 제품 | Run ID | Host 자체 판정 | Host 판정까지 시간 |
| --- | --- | --- | ---: |
| Multi Ver1 10회차 | `f98710f8-7232-46ae-92fe-f2dd18b0db37` | UNVERIFIED | 113.675초 |
| Single Ver2 9회차 | `9eeb2fad-1274-4595-a71a-f2576ddad7e7` | UNVERIFIED | 399.006초 |

두 제품의 독립 최종 시험은 모두 PASS였다. 최종 보존 코드 기준으로 Multi Ver1은 필수 브라우저 파일 누락에 따른 `QA_DRAFT_CORRECTIONS_EXHAUSTED`, Single Ver2는 `QA_REPORT_BINDING_INVALID`로 중단됐다. Single의 이전 코드 버전에 초안 교정 소진 기록이 있었다는 사실을 최종 중단 원인과 혼동하면 안 된다. 위 시간은 각 UNVERIFIED 판정까지 걸린 시간이며, **자동 SUCCESS까지 걸린 시간이라고 발표하면 안 된다.** 이후 실행기의 성공 판정 시간 집계는 독립 전체 PASS와 Host SUCCESS를 모두 만족한 표본만 사용한다.

### 실제로 많이 남은 결함

| 독립 최종 검사 | 해당 검사 FAIL이 확인된 실행 수 |
| --- | ---: |
| SEC-SIGNUP-005 비밀번호·해시 노출 | 24회 |
| QA-SIGNUP-005 동시 가입 요청의 중복 생성 방지 | 12회 |
| SEC-SIGNUP-003 이메일 정규화 저장과 DB UNIQUE | 11회 |

서로 같은 실행에 여러 실패가 있을 수 있어 위 수를 합쳐 실패 제품 수로 쓰지 않는다. 중간 구두 설명에서 QA-SIGNUP-005를 비밀번호 경계값, SEC-SIGNUP-003을 해시 정책으로 잘못 연결한 부분은 원본 시험 제목대로 정정했다. 비밀번호 최소 길이는 QA-SIGNUP-004이며 이번 최종 검사에서 2회 FAIL이었다.

가입 경로 미발견·앱 import·시험 DB 조회·사전 가입 실패 등으로 일부 검사를 판정하지 못한 실행도 있었다. 모든 미검증을 실제 제품 실패로 바꾸지 않았다. 낮은 시간·비용에는 조기 중단이 섞여 있으므로 Multi의 효율 개선으로 단정하지 않는다. 이번 결과만으로 구조나 보호시험 정책의 우열을 확정하지 않는다.

### 남은 작업

다음 **92번**은 추가 반복 측정보다 실패 지점 보완이 우선이다. 오류 응답·로그의 비노출, canonical 이메일의 DB 제약·동시 가입 처리, 실제 제품이 독립 시험을 통과해도 검증 초안 오류로 멈추는 경로를 각각 재현하고 수정한다. 숨겨진 최종 시험을 모델 입력에 넣거나 통과 기준·권한을 낮추는 방식은 사용하지 않는다.

### 38회 종료 시 운영 중단과 남은 계획 슬롯

실행기는 36~38번의 검토 대기로 신규 제출을 멈췄다. Trace를 확인한 결과 36번은 보안 사전 안내 후 교정 반복, 37~38번은 `WRITE_CONFLICT`·`EDIT_TARGET_MISSING` 등 코드 수정 도구 오류였고, 해당 기록의 `resultUnknown`은 false였다. 인증·Docker 장애나 결과 불명의 전송을 새 요청으로 반복한 것이 아니다.

Ver2 두 조건은 이 시점에 각각 10회를 완료했다. 사용자 요청인 네 조건 각 10회를 맞추기 위해, 코드·Schema 해시와 미제출 상태를 대조한 뒤 **이미 등록된 Ver1 슬롯 39·40만** 원래 설정으로 실행했다. 기존에 멈춘 Run에는 입력·복구·재전송을 하지 않았다. 38회 당시 `results.json`은 `results-at-initial-stop.json`으로 별도 보존했으며, 최종 집계에도 중단 이력을 남겼다. 측정 중 에이전트 구현이나 한도·채점 기준을 변경하지 않았다.

최종 집계는 원자료를 읽는 오프라인 `continuation/summarize_comparison.py`로 산출하여 `analysis-summary.json`에 남겼다. 실험용 Host·Agent 포트 18002·18101~18104의 종료와 잔여 Docker 컨테이너가 없음을 확인했다. `git diff --check`를 통과했으며 프로젝트 커밋·푸시는 수행하지 않았다.

## 개발정의서 점검

기존 승인·인증·MCP 권한·Docker 격리·불변 Snapshot·보호시험을 유지한다. 통과 기준을 낮추거나 검사 실패를 성공으로 덮어쓰지 않는다. 이번 작업은 실행과 결과 수집이며, 측정 중 에이전트 구현은 변경하지 않는다. 프론트엔드·발표 HTML·Git 커밋·푸시는 변경하지 않는다.
