# 124. 실제 검사 자료의 전달 오류 수정

작성일: 2026-11-27.

## 실제로 발생한 문제

Run `3da09612-3099-4d6a-b15a-2fe36945d9a6`의 개발 수정 단계가 `DEVELOPER_CONTEXT_DENIED`로 중단됐다. 이후 이어서 수정 접수도 `CONTINUATION_UNSAFE_CONTEXT`에 해당하는 안내로 거절됐다.

두 경로의 공통 원인은 123번에서 추가한 검사 코드 원문이었다. Source 전용 검사를 통과한 정상 코드의 `password = ...`, 요청 본문의 비밀번호 필드 표현을 일반 문장용 민감정보 마스킹이 변경했다. Developer는 전달 자료가 변경됐다는 이유로 실행을 거절했고, 이어서 수정 접수도 같은 검사에 막혔다. 실제 승인 환경이 잘못됐다고 단정할 수 있는 오류가 아니었다.

읽기 전용으로 실제 기록을 확인했을 때 기존 Source·Issue·Task 연결 검사는 통과했고, 재현 자료 2개 scope의 파일 3개 중 코드 원문 2곳이 일반 마스킹에서 변경되는 것을 확인했다. 인증이나 실행 승인 검사를 무시하는 것으로 해결하지 않는다.

## 수정한 방식

- 검사 코드 원문을 Fix Request·A2A·새 Run의 계약 JSON에 통째로 넣지 않는다.
- 검증된 파일의 경로·SHA-256, 실패 test ID, 함수 위치, 제한된 정적 HTTP 요청 형태를 전달한다.
- 예를 들어 비밀번호 필드의 값은 보내지 않고 `fieldName=password`, `shape=EMPTY_STRING` 또는 `NULL` 같은 구조만 전달한다. 일반 마스킹을 우회하는 예외 키나 비밀정보 허용 규칙은 추가하지 않았다.
- 정적 분석 결과에는 `staticHintsAreExecutionEvidence=false`를 기록한다. 코드에 가능한 호출이 있다는 사실과 실제 실행 관찰을 구분한다. 실제 상태 코드와 판정은 기존 `failureDiagnostic`·`validationFeedback`이 근거다.
- 검사 원본은 기존 비공개 아카이브에 그대로 둔다. 원래 검사로 재검증하는 Host 경로와 파일 해시 검증은 유지한다. 보호시험과 다른 Run의 검사 파일은 계속 제외한다.
- `DEVELOPER_CONTEXT_DENIED` 안내를 “입력 자료를 확인하지 못했다”로 바꿨다. 형식·자료 전달 문제도 이 코드로 묶일 수 있으므로 승인 조건 불일치로 단정하지 않는다.

## 실제 실패 자료로 확인

실제 DB를 `mode=ro`, `PRAGMA query_only=ON`으로 열고 기록된 실행 정보를 메모리에서 재구성했다. 원래 Task의 상태나 예산은 수정하지 않았다.

| 확인 항목 | 결과 |
| --- | --- |
| 기존 Source·Issue·Task 연결 검사 | 통과 |
| 수정된 재현 자료와 민감정보 검사 호환 | 통과 |
| 실제 자료를 사용한 Developer 입력 재구성 | 통과 |
| A2A 메시지 직렬화 | 통과 |
| 같은 부모 Run의 이어서 수정 자료 구성 | 통과 |
| 유료 모델 호출·새 Run 제출·기존 Task 재개 | 하지 않음 |

이는 실제 장애 자료의 입력 처리 확인이며, AI가 제품 수정을 완료했다는 결과는 아니다. 이미 실패한 Task를 임의로 실행 중으로 돌리거나 성공으로 바꾸지 않았다.

## 회귀 검사와 적용

| 검사 | 결과 |
| --- | --- |
| 새 자료 전달·기존 이어받기·검증 피드백 | 55개 통과 |
| 최종 자료 크기 제한·서비스 역할·요청 규격 | 36개 통과. 위 검사와 일부 중복 |
| 원래 실패 검사 재실행·개발 수정 흐름·오류 안내·접수 | 17개 통과 |
| 실제 장애 자료의 읽기 전용 재구성 | 개발 입력·A2A 구성·이어받기 구성 모두 통과 |
| 자격증명 리터럴 차단·보호시험 제외 | 유지 확인 |

실제 장애 자료 재현의 최소 결과만 Git 제외 파일 `.data/diagnostics/service-repair-admission-20261127.json`에 남겼다. 코드 원문·비밀번호·토큰을 이 기록에 저장하지 않았다.

실행 중인 Run과 Step이 없는 것을 확인하고 Host·Agent만 재시작해 적용했다. 제품 서버·프론트·Docker와 기존 작업 기록은 유지했다. 일곱 서버 모두 HTTP 200, Agent 4개는 `executionReady=true`, Host 인증은 토큰 없이 401·기존 토큰으로 200이었다. 화면에 나온 기존 Run은 실패 기록을 보존한 채 `continuationAvailable=true`로 조회된다.

제품 백엔드·프론트 코드는 이번 수정에서 바꾸지 않았다. 유료 API 호출이나 새 Run 제출은 하지 않았다.

사용자는 적용 후 같은 프로젝트에서 **이어서 수정·재시도**를 사용할 수 있다. “무시하고 일치시켜” 같은 설명 없이 기본 수정 요청으로 진행하면 된다.

추천 커밋 메시지: `검사 코드 원문 전달 오류 수정 및 재현 자료를 안전한 참조 정보로 전환`
