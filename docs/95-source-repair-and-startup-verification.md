# 95. 코드 검토 경고의 실제 수정 연결과 앱 시작 검증

작성일: 2026-11-23. 1·2번 담당의 공통 LLM 실행기, Source 검토, Host 중단·평가 원인 분류, 새 SCN-001 실행 설정을 보완했다. 이번 작업에서 OpenAI API와 성능 비교 Run은 실행하지 않았다.

## 실제 실패에서 고친 부분

94번의 20회 기록에서 5·6·10·14·16번은 마지막 코드가 `LLM_SCHEMA_INVALID`였지만, 원래 중단 사유는 `READY_SIGNUP_QUALITY_REVIEW` 반복·교정 한도 소진이었다. 3개 제품은 앱 import가 실패했다. 이 두 경로를 실제 수정 대상으로 삼았다.

| 문제 | 변경 |
| --- | --- |
| 코드 수정 없이 READY 설명만 다시 제출 | Host가 지적한 파일의 새 읽기 → 관찰한 SHA-256에 맞춘 쓰기·편집 → 실제 변경 → Source 재검토 순서를 요구한다. 모델에 문장으로만 권고하지 않고 제시 도구와 실행 인자도 제한한다. |
| 수정 후 같은 경고 이름이 나오면 즉시 반복으로 처리 | 검토한 Source의 AST 지문을 함께 비교한다. 실제 코드가 바뀐 경우에만 남은 기존 교정 기회를 사용할 수 있고, 문구·줄 이동만으로 기회가 늘어나지 않는다. |
| 라우터의 위험을 보고 앱을 잘못 import해서 처리기 설치 | 위험이 관찰된 `sourcePath`와 실제 수정할 `repairSourcePath`를 구분한다. 기본 검증 오류 처리는 FastAPI 앱 진입 파일로 연결한다. |
| 입력 모델에 검증 함수가 있으면 보안 검토에서 제외 | Pydantic 필드 검증 함수가 있어도 평문 비밀번호 입력 모델의 기본 오류 응답 위험을 검토한다. 검증 함수만으로 입력 비노출이 증명되지 않는다. |
| `main.py`에서 아직 없는 `main.app`을 자기 자신에게서 import | Host에서 Source를 실행하지 않는 정적 검사로 `ENTRYPOINT_SELF_IMPORT`를 안내한다. 실제 앱 import·기동은 격리된 Build가 담당한다. |
| 과거 로컬 설정의 Build가 문법 검사만 수행 | 새 실험 설정의 정확히 알려진 `scn001-compile` 명령 두 형태를 기존 `scn001_build_argv()` 시작 검사로 교체한다. 기존 로컬 파일·승인된 Run·사용자 지정 Build는 변경하지 않는다. |
| 코드 검토 실패를 JSON 오류로 기록 | Source 수정 소진은 `LLM_SOURCE_REPAIR_EXHAUSTED`와 `MODEL_EXECUTION`으로 분리한다. Host 중단 코드와 평가 보고서에도 연결한다. |

여러 수정 파일은 같은 한 번의 교정 안에서 순서대로 처리한다. 각 파일은 새로 읽고 해시를 고정하며, 변경되지 않은 쓰기·범위 밖 경로·결과 불명 쓰기는 완료로 인정하지 않는다. 모델·Tool·토큰·시간·출력 교정·제품 수정 횟수 한도는 늘리지 않았다. 필요한 읽기·수정·완료 제출을 남은 한도로 수행할 수 없으면 중단한다.

Source 검토는 정적 경고다. 경고가 사라졌다고 QA·Security PASS를 만들지 않는다. 기존 Build·QA·Security·독립 최종 시험의 실제 근거가 계속 필요하다.

## 오류 해석과 기존 결과 보존

- 새 Source 수정 실패는 JSON 파싱·스키마 오류와 별도 코드로 남는다. 순수한 JSON 오류는 기존 분류를 유지한다.
- 과거 `LLM_SCHEMA_INVALID`도 같은 Task에 연결된 검증 완료 복구 기록의 마지막 STOP이 Source 검토인 경우만 원인을 정정한다. 기록이 없거나 불완전하면 추측으로 재분류하지 않는다.
- 94번 문서와 요약 JSON에는 해당 5개 실행의 원인 해석 정정만 추가했다. 20회 원본 Run, 후보, 채점, 비용·시간·수정 횟수는 바꾸지 않았다.

## 검증 결과

검사 묶음은 겹치는 항목이 있으므로 합산하지 않는다. 저장소 전체 검사나 실제 모델 성공률 측정으로 해석하지 않는다.

| 범위 | 결과 |
| --- | --- |
| Source 수정, 품질 검토, 출력 보호, 시작 계약, 설정, 기존 파일 충돌 경로의 첫 회귀 묶음 | 277개 통과 |
| Host·자동 중단·Single/Multi 수정 파이프라인·평가 원인·복구 근거 | 220개 통과 |
| 보강한 경고·설정·평가 원인·파일 충돌 관련 묶음 | 216개 통과 |
| 수정 경로·Source 위험·설정·과거 오류 재분류 최종 검사 | 66개 통과 |
| Source 수정 실패와 JSON 오류 분리 최종 검사 | 111개 통과 |
| 실제 Docker 재현·수정·동일 최종 시험·시작 검사 | 3개 통과 |

Docker 검사는 기존 합성 회원가입 서비스에 기본 검증 오류 보호 누락을 넣어 **비노출 시험 하나의 실제 FAIL을 확인**한 뒤, Scripted Provider가 공통 엔진의 강제 읽기·해시 고정 쓰기를 거치도록 했다. Single·Multi 양쪽에서 수정된 실제 파일에 동일한 공식 최종 9개 시험을 적용해 9개 모두 PASS했고, 앱 시작 검사도 통과했다. 별도로 자기 자신을 import하는 앱은 컨테이너 시작 검사에서 `SCN001_IMPORT_FAILED`로 실패함을 확인했다.

이때 모델 응답은 정해진 재현 입력이고 실제 파일과 Docker 실행·시험 결과를 사용했다. 실제 OpenAI 모델이 같은 수정을 자율적으로 성공했다는 의미가 아니며, 20회 성능 실험에 추가하지 않는다.

Docker 검증용 코드 작성 중 직접 unit 실행기를 선택한 구성 오류와 시험 ID 조회 인자 누락을 수정했다. 최종 검사는 제품 평가와 같은 replay 실행기·동일 시험지로 통과했다. 초기 오류를 제품 결함이나 성능 측정값으로 집계하지 않았다.

주요 재현 명령:

```bash
PYTHONPATH=src:tests .venv/bin/python -B -m pytest -q \
  tests/test_source_quality_repair_flow.py tests/test_signup_quality_precheck.py \
  tests/test_scn001_smoke.py tests/evaluation/test_recovery_evidence.py

# 기존 Docker 이미지가 준비된 환경에서만 실행한다. OpenAI API 호출은 없다.
A2A_DOCKER_REPAIR_TEST=1 PYTHONPATH=src:tests .venv/bin/python -B -m pytest -q \
  tests/test_source_quality_docker.py
```

SDK의 단일 프로세스 fixture에서 event_stream 미설정 경고가 있었다. 다중 replica 스트리밍 검증을 완료했다는 의미는 아니다.

## 개발정의서 점검과 남은 범위

- Orchestrator의 판정 책임, 역할별 MCP 권한, A2A·Artifact 계약, Source 동결과 수정 이력을 유지했다.
- 인증·격리·CAS·보호시험·최종 9개 기준을 완화하지 않았다. 결과 불명 쓰기와 인증·권한 오류를 자동 재전송하지 않는다.
- Single과 Multi가 같은 실행기·Source 검토·교정 한도를 사용한다. Ver1·Ver2의 보호시험 제공 차이를 유지했다.
- 새 Build 설정은 공개 연결 계약의 앱 시작 여부를 확인한다. 보호시험 코드·정답 구현을 Agent에게 제공하는 변경은 아니다.
- 프론트엔드, `.env`, 사용자 로컬 실행 설정과 과거 실험 폴더를 수정하지 않았다. 프로젝트 Git 커밋·푸시는 하지 않았다.

실제 모델이 불완전한 시험·보고서를 생성하거나 이메일 정규화·DB 제약을 잘못 구현할 가능성은 여전히 있다. 이번 검증은 확인된 수정 경로와 시작 검사 연결을 증명하며, 완제품 성공률 100%를 보장하지 않는다.
