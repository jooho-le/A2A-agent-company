## 2. Security 정적 판정이 보는 것 (REQ-003·005·006)

| 요구 | PASS 조건 | FAIL | UNVERIFIED |
|---|---|---|---|
| REQ-003 이메일 중복 | 가입으로 사용자를 저장하는 표(비밀번호 칸이 있는 표)의 이메일 컬럼 **하나**에 대한 UNIQUE 선언 + 검증기 반환값 또는 실제 저장 이메일과 연결되는 공백 제거·소문자 정규화. SQL은 실제로 실행하는 글자만 읽는다 | UNIQUE 없음(복합 제약만 있거나, 같은 줄의 다른 칸·보관용 같은 다른 표의 UNIQUE뿐인 경우, 문자열·주석 속 단어뿐인 경우 포함), strip/lower 없음(계산만 하고 버리는 경우 포함) | 이메일 컬럼을 못 찾음, 제약의 칸 목록·인덱스의 대상 표·가입에 쓰는 표를 코드로 확인할 수 없음(계산식 칸, 부분 인덱스, 읽을 수 없는 SQL 포함) |
| REQ-005 비밀번호 저장 | Argon2id를 쓰고 수치 기준 충족, 다른 값으로 덮이지 않은 승인 Argon2 해시 도구(와 바꿔치기되지 않은 해시 함수)로 **입력 비밀번호**를 해시한 값만 저장. 해시하는 값의 실제 출처(어느 입력의 어느 필드인지)가 비밀번호 필드여야 하고, 변수 이름만 password인 이메일 같은 경우는 인정하지 않음 | 원문 저장(`values()`·`setattr`·사전·SQL 포함), MD5·SHA 등, 수치 미달, 고정 salt | 설정이 상수가 아님(`**설정`·`*값`으로 펼친 경우 포함), 해시하는 값이 입력에서 나왔는지 증명할 수 없음(상수·상수 폴백·`*= 0`·잘라내기·입력을 버리는 함수 등), 진짜 난수라고 확인할 수 없는 salt, 해시 도구·해시 함수가 매개변수·재정의·데코레이터·덮어쓰기로 바뀔 수 있음, 저장 경로 확인 불가 |
| REQ-006 노출 없음 | 로그·응답·예외·검증 오류 응답에 비밀번호·해시 경로 없음. 검증 오류는 허용 키(`loc`·`msg`·`type`)만 옮기거나, **모든 항목에서** `input`을 확실히 지운 경우 | 노출 경로 발견(모델 통째 로깅, 변수에 옮겨 담았다가 출력(and·or·람다 포함), 파일·쿠키·헤더에 기록, `response_model=None`이거나 응답 객체를 직접 돌려줘서 걸러지지 않는 응답, 응답 키·값, `exc.errors()`·`str(exc)` 그대로 반환, 정리 전에 원본 사용 등) | 객체 전체를 응답에 펼침, `input` 삭제가 일부 항목에만 적용될 수 있음(`if` 안에서만 지움 등), 검증 오류 처리기를 소스에서 찾을 수 없음(람다 등) 같은 분석 불가 |

오탐 방지: 이름은 단어 단위로 본다(`passed`, `MIN_PASSWORD_LENGTH`, `PASSWORD_ERROR_MESSAGE`는 비밀번호 값이 아님). Bandit 경고는 코드 근거가 있을 때만 CONFIRMED(개발정의서 10절)이고 나머지는 SUSPECTED로 둔다.
정적 분석의 한계: 호출 흐름·동시성·런타임 설정은 보지 않는다. 특히 REQ-006의 PASS는 "지원하는 노출 경로를 찾지 못함"이지 노출이 없다는 증명이 아니다. 그래서 같은 요구를 실행 검사로 한 번 더 본다.

## 3. 결정 상태 (2026-10-28, 개발정의서·dev 정책·회의 기록 대조)

평가 기준·평가 방법은 4번 담당(개발계획, dev 45번 §7)이다. 기준 JSON에 들어가는 값은 승인 해시 등록 때 팀장 승인을 함께 받는다.

| 항목 | 상태 | 내용 |
|---|---|---|
| 이메일 정규화 | 이미 결정 | 앞뒤 공백 제거·전체 소문자·정규화 이메일 UNIQUE(정의서 1절, dev `emailPolicy`) |
| Argon2 수치 | 값은 이미 결정, 규칙은 4번 결정 | m=19456·t=2·p=1, **이상**이면 충족(정의서 "최소 19 MiB", "파라미터 충족") |
| 정적 PASS 범위 | 4번 결정 | 지원 패턴에서 증명된 코드 경로 기준으로만 PASS. 실제 응답·로그(SEC-SIGNUP-005)·동시성(QA-SIGNUP-005)·Trace 기록(D4)은 따로 확인. 근거가 부족하면 UNVERIFIED로 두고 PASS 기준을 낮추지 않는다. Run 최종 판정은 정의서 10-1(필수 UNVERIFIED 0)과 Orchestrator 정책에 따른다 |
| 실행 보안 검사·동시 가입 시험 | 4번 결정 | 최종 평가 전용(순환 안 PROTECTED는 QA 담당 요구사항만 연결 가능) |
| MEDIUM Finding | 판정 방법은 결정, 추가 차단만 팀 결정 | 경고만으로 CONFIRMED 아님, 근거가 있으면 CONFIRMED, 오탐 근거면 FALSE_POSITIVE, 명시 요구 위반은 차단(정의서 1절). 그 밖의 MEDIUM 차단 여부는 정의서 10-3 "팀 미결정" |
| 보호 테스트 위치 | 이미 결정 | B(순환 안)로 진행(10/12 팀장 합의). A 비교는 시간 여유가 있을 때 |
| 생성물 규격 | **팀장 결정 대기** | 세화 backend 구조를 가정하고 D2를 구현함(연결부 한 파일만 바꾸면 됨). 시작 코드(승인 저장소·커밋)와 표본 채택은 팀장 결정 |
| 팀 Python 버전 | 이미 결정 | `>=3.10`(pyproject·README·dev 45·46번). 평가 코드·보호 테스트는 3.10에서도 동작. dev 승인 함수가 3.11 전용 속성(`co_qualname` 등)을 써서 3.10 선언과 어긋나는 점은 1·2번에 전달 |

## 4. 4번이 팀장님께 요청하는 것 (우선순위 순)

| 순위 | 받을 것 | 이유 |
|---|---|---|
| 1 | 시작 코드가 서비스 웹페이지 저장소의 특정 커밋인지, 회원가입 자리만 비운 별도 틀인지, 그리고 승인 커밋. 개발계획의 "Developer 코드 → Git 반영 → 빌드 → 서비스 실행" 연결을 그대로 할지 | D2 연결부 확정, 순환 안 보호 케이스 등록. dev는 시작 Source(owned-source)가 없으면 Run을 못 돌림 |
| 2 | 최종 Snapshot tar·Manifest를 받는 경로, 기준·실행 Manifest를 누가 만들어 주는지, 평가에 쓸 이미지 | D5 채점기는 구현됨. 받는 경로만 정하면 바로 돌릴 수 있음(dev `/artifacts`는 소스 다운로드 API가 아님) |
| 3 | 승인 등록·Host 연결 일정(최종 코드·기준·Python 환경 고정 후 해시 재생성), wheel에 기준 JSON·보호 테스트 포함 여부 | D1·D2를 실제 순환에서 사용 |
| 4 | 같은 Run의 상태·configuration·events·issues·tool-attempts·usage·상세 검사 결과·최종 코드 식별 정보, 시연 영상·캡처와 Run ID | D4 실제 데이터 검증, 시연 자료 정리 |
| 5 | Single 실행 경로(`architecture` 확장) 협의 | D6 비교(후순위, 담당 4번) |

## 5. 현재 구현 상태 (사실만)

- Security 정적 판정기: dev 승인 로더(`load_approved_assessor`)를 통과. 정상 예제 1개 + 결함 변형 18개 + 정상 변형 9개 + 추가 코드 모양 15개 + 외부 점검 사례 12개(1차) + 63개(2차와 그 연장) + 60개(3차와 그 연장) + 64개(4차와 그 연장) + 35개(5차와 그 연장) + 96개(6차와 그 연장)로 판정 확인(합성 소스, 실제 생성물 아님). 입력 필드를 덮어쓰는 방법의 조합 시험(별칭 19가지 × 쓰기 20가지 등 약 1,100개 조합)과, 이상하게 쓴 코드에서도 시간 안에 끝나는지 보는 시험(36개 사례)도 있다. 분석을 한도 안에 끝내지 못하면 PASS를 만들지 않고 UNVERIFIED로 답한다.
- 독립 평가 보고서·집계·Manifest 모듈: 구현 및 스키마 검증.
- 회원가입 보호 테스트(D2): 순환 안 QA 5개 + 최종 전용 3개. 최소 회원가입 서비스와 변형 20개(읽기 전용 Snapshot)로 결함마다 해당 검사만 FAIL, 연결 실패는 미검증임을 확인. dev 보호 파일 설정·보호 QA 케이스 검증을 통과.
- Trace 검사(D4): Run 기록의 비밀번호·해시 노출, 요구→개발→검증→수정→재검증 연결. dev 파이프라인 테스트의 실제 Run 6개로 확인.
- 최종 독립 채점기(D5): Snapshot 확인 → 컨테이너에서 보호 테스트 + 정적 판정 → 독립 평가 보고서와 회의·발표용 요약. 받는 경로만 정해지면 실행 가능.
- 아직 안 한 것: 실제 생성물로 돌린 보호 테스트, 최종 Snapshot 인계, Single 실행기, 실제 LLM·Docker로 돌린 평가. 합성 예제 결과는 제품 성공의 증거가 아니다.
