## 2. Security 정적 판정이 보는 것 (REQ-003·005·006)

| 요구 | PASS 조건 | FAIL | UNVERIFIED |
|---|---|---|---|
| REQ-003 이메일 중복 | 가입으로 사용자를 저장하는 표(비밀번호 칸이 있는 표)의 이메일 컬럼 **하나**에 대한 UNIQUE 선언 + 결과가 실제로 쓰이는 공백 제거·소문자 정규화. SQL은 실제로 실행하는 글자만 읽는다 | UNIQUE 없음(복합 제약만 있거나, 같은 줄의 다른 칸·보관용 같은 다른 표의 UNIQUE뿐인 경우, 문자열·주석 속 단어뿐인 경우 포함), strip/lower 없음(계산만 하고 버리는 경우 포함) | 이메일 컬럼을 못 찾음, 제약의 칸 목록·인덱스의 대상 표·가입에 쓰는 표를 코드로 확인할 수 없음(계산식 칸, 부분 인덱스, 읽을 수 없는 SQL 포함) |
| REQ-005 비밀번호 저장 | Argon2id를 쓰고 수치 기준 충족, 다른 값으로 덮이지 않은 승인 Argon2 해시 도구(와 바꿔치기되지 않은 해시 함수)로 **입력 비밀번호**를 해시한 값만 저장. 해시하는 값의 실제 출처(어느 입력의 어느 필드인지)가 비밀번호 필드여야 하고, 변수 이름만 password인 이메일 같은 경우는 인정하지 않음 | 원문 저장(`values()`·`setattr`·사전·SQL 포함), MD5·SHA 등, 수치 미달, 고정 salt | 설정이 상수가 아님(`**설정`·`*값`으로 펼친 경우 포함), 해시하는 값이 입력에서 나왔는지 증명할 수 없음(상수·상수 폴백·`*= 0`·잘라내기·입력을 버리는 함수 등), 진짜 난수라고 확인할 수 없는 salt, 해시 도구·해시 함수가 매개변수·재정의·데코레이터·덮어쓰기로 바뀔 수 있음, 저장 경로 확인 불가 |
| REQ-006 노출 없음 | 로그·응답·예외·검증 오류 응답에 비밀번호·해시 경로 없음. 검증 오류는 허용 키(`loc`·`msg`·`type`)만 옮기거나, **모든 항목에서** `input`을 확실히 지운 경우 | 노출 경로 발견(모델 통째 로깅, 변수에 옮겨 담았다가 출력(and·or·람다 포함), 파일·쿠키·헤더에 기록, `response_model=None`이거나 응답 객체를 직접 돌려줘서 걸러지지 않는 응답, 응답 키·값, `exc.errors()`·`str(exc)` 그대로 반환, 정리 전에 원본 사용 등) | 객체 전체를 응답에 펼침, `input` 삭제가 일부 항목에만 적용될 수 있음(`if` 안에서만 지움 등), 검증 오류 처리기를 소스에서 찾을 수 없음(람다 등) 같은 분석 불가 |

오탐 방지: 이름은 단어 단위로 본다(`passed`, `MIN_PASSWORD_LENGTH`, `PASSWORD_ERROR_MESSAGE`는 비밀번호 값이 아님). Bandit 경고는 코드 근거가 있을 때만 CONFIRMED(개발정의서 10절)이고 나머지는 SUSPECTED로 둔다.
정적 분석의 한계: 호출 흐름·동시성·런타임 설정은 보지 않는다. 특히 REQ-006의 PASS는 "지원하는 노출 경로를 찾지 못함"이지 노출이 없다는 증명이 아니다. 그래서 같은 요구를 실행 검사로 한 번 더 본다.

## 3. 합의가 필요한 항목 (논의 순서)

| # | 질문 | 4번 초안 | 영향 |
|---|---|---|---|
| 1 | Argon2 수치를 "이상"으로 볼까 "정확히 일치"로 볼까 | **이상(AT_LEAST)**. registry는 m=19456·t=2·p=1이고 정의서는 "최소 19MiB"라고 표현. 기준 JSON에서 한 줄(`parameterRule`)로 바꿀 수 있음 | 라이브러리 기본값(m=65536·t=3·p=4)이 통과하는지 결정 |
| 2 | REQ-003·006의 Security PASS를 정적 근거만으로 인정할까 | 인정. 정적만으로 UNVERIFIED면 Run이 항상 HUMAN_REVIEW로 끝남. 실제 확인은 최종 실행 검사가 함 | 개발 순환이 SUCCESS에 도달할 수 있는가 |
| 3 | MEDIUM Finding 처리 | 지원 규칙만 CONFIRMED/FALSE_POSITIVE, 나머지는 SUSPECTED 유지. 정의서는 MEDIUM을 "명시 요구 위반이면 차단"이라고 함 | 정의서 10-3 팀 미결정 항목 |
| 4 | 보호 테스트(최종 시험지)를 개발 순환에 보일까 | 10월 12일 논의 기록(D0 기준): **B(순환 안)로 평가하고 A(최종에서만 채점)로도 실행해 비교**, B′는 4번 추가 제안. B는 순환용·최종용 시험지를 나눠야 함. 비교는 [single_baseline.md](single_baseline.md) 4절 | 에이전트가 시험 문제를 연습하는 셈이 되면 비교가 불공정 |
| 5 | 동적 보안 근거(SEC-SIGNUP-002·005)를 순환 안에 쓸까 | 쓰지 않음(최종 평가 전용). 쓰려면 1·2번의 Sandbox·증거 연결 확장이 필요 | 일정 |
| 6 | 생성물 규격(시작 코드·API·DB·로그 위치) | 세화 backend는 플랫폼 웹사이트 코드이므로 자동으로 정답·규격 취급하지 않음. 채택 여부 결정 필요 | QA 실행 검사를 붙일 수 있는 시점 |
| 7 | 팀 Python 버전 | **3.13**. 3.10은 dev 테스트와 Security 승인 함수가 실패, 3.14는 보안 승인 테스트 6개 실패 확인 | `pyproject.toml`의 `>=3.10`과 루트 `.python-version`은 팀 전체에 영향을 주는 파일이라 건드리거나 올리지 않음. 그동안은 `uv sync --frozen --python 3.13`으로 지정 |

## 5. 현재 구현 상태 (사실만)

- Security 정적 판정기: dev 승인 로더(`load_approved_assessor`)를 통과. 정상 예제 1개 + 결함 변형 18개 + 정상 변형 9개 + 추가 코드 모양 15개 + 외부 점검 사례 12개(1차) + 63개(2차와 그 연장) + 60개(3차와 그 연장) + 64개(4차와 그 연장) + 35개(5차와 그 연장)로 판정 확인(합성 소스, 실제 생성물 아님).
- 독립 평가 보고서·집계·Manifest 모듈: 구현 및 스키마 검증.
- 아직 안 한 것: 실제 생성물 실행 검사, 최종 Snapshot 인계, Single 실행기, 실제 LLM·Docker로 돌린 평가. 합성 예제 결과는 제품 성공의 증거가 아니다.
