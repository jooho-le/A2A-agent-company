### 1. 무엇을 평가하는가

회원가입 서비스를 만드는 한 번의 전체 실행(Run)을 평가한다. 같은 요구사항을 받은 Single과 Multi의 최종 생성물과 실행 기록을 같은 기준으로 비교한다. 구현 코드의 모양·줄 수·파일 구조는 점수가 아니다.

| 평가 축 | 질문 | 평가 자료 | 주 결과 |
|---|---|---|---|
| 정확도 | 같은 요구사항과 보안 기준을 만족했는가? | 최종 코드에 실행하는 공통 시험 9개 | 요구사항별 결과, 제품 통과 여부, 확인된 보안 위반 |
| 속도 | 결과를 얻는 데 얼마나 걸렸는가? | 실행 중 기록한 시각 | 판정까지의 시간, 보존 Snapshot 기준 최초 통과 시간 (v4), 결과 패키지 완성까지의 시간 |
| 비용 | 결과를 얻는 데 얼마나 썼는가? | 전체 호출의 사용량·단가 기록 | 입력·출력 토큰, API 비용, 제품 통과 1회당 비용 |
| 과정 | 어떤 오류와 수정을 거쳤는가? | 작업·전달·수정·검증 기록 | 수정·재계획·재시도, 충돌, 추적 가능성, 전달 오류 |
| 안정성 | 같은 조건에서 결과가 얼마나 일정한가? | 여러 Run의 결과 | 제품 통과율, 자동 완료율, 미검증·중단 비율, 점수·시간 분포 |

정확도만 시험 문제를 실행해 채점한다. 나머지 축은 같은 Run의 기록을 모아 계산한다. 다섯 축을 임의의 가중치로 합친 단일 총점은 만들지 않는다.

### 2. 이번에 준비한 범위와 상태

- 기존 구현 활용: 회원가입 실행 검사 9개, 공식 최종용 `exam_final.py`, 시범용 `exam_pilot.py`, 독립 채점기와 실행 기록 집계기.
- 이 문서에서 작성: 문제별 절차·기대 결과·증거, 다섯 축의 측정식, 미검증 처리, 공정 비교 조건, 평가 기록 양식.
- 측정 기준: 실행 종료 시점, 최종 제출물 선택, 수정 경로 계수, 통과 1회당 비용, 반복 결과 보고, Run 뒤 버전별 채점, 충돌 계수를 정한다. 기존 코드에 아직 없는 기록·계산은 23절 구현 대응표에서 구분하고, 정책 한도는 실험 등록표에 고정한다. 팀이 채택하기 전까지 기존 실행기 정책을 바꾼 것으로 간주하지 않는다.
- 공식 실행 전 필요: 시작 코드·연결 규격·평가 환경 확정, 새 경로의 기록 연결, 실제 생성물로 시범 실행. 본 문서 작성만으로 실제 Single/Multi 비교가 완료되는 것은 아니다.

### 3. 시험지의 사용 경계

공개 요구사항과 실행 계약은 두 구조에 동일하게 제공한다. 구체적인 시험 입력·검사 코드·정답 및 결함 예제는 평가 담당만 관리한다. 개발 중 QA·Security가 만드는 테스트와 이 최종 시험지는 별개다.

최종 평가 결과는 해당 Run에 돌려주지 않으며, 같은 공식 실험의 후속 Run을 위한 프롬프트·모델·수정 정책 조정에도 쓰지 않는다. 조정은 시범용 시험지로 끝내고 공식 설정을 동결한다. 공식 결과를 보고 시스템을 바꾸면 새 실험으로 분리한다.

평가기 버그를 고치면 원본 결과·수정 이유·버전 이력을 보존하고, 같은 제출물 전체를 동일한 수정 시험지로 다시 채점한다. 특정 결과에 맞춰 기준을 바꾸지 않는다. 요구사항 자체가 바뀌면 새 계약·새 실험으로 분리한다.

### 5. 이번 시험이 전제로 하는 정책

- 이메일: 앞뒤 공백 제거 후 소문자로 저장한다. Gmail의 점이나 +태그를 제거하지 않는다. 서로 다른 주소를 임의로 합치지 않는다.
- 비밀번호: 길이 기준을 검사한다. 계약에 없는 대문자·특수문자 필수 조건을 추가하지 않는다.
- 저장 정책: 현재 SCN-001의 Argon2id 정책을 사용한다. 파라미터 하한은 m=19456, t=2, p=1이며 계정별 salt를 사용한다. 이는 현재 프로젝트의 고정 정책을 시험하는 값이다.
- 정상 요청은 2xx, 입력 검증·중복 거부는 4xx여야 한다. 현재 시험은 정확히 400인지 422인지로 점수를 나누지 않는다. 관찰된 5xx는 해당 검사에서 실패 근거가 될 수 있다.

## 실행 계약과 증거

### 6. 연결 규격은 시험 내용과 분리한다

현재 연결부의 가정은 `main.app`, `database.get_db`, `models.User(email, password_hash)`, `POST /api/auth/signup`이다. 지원 범위는 FastAPI·동기 DB 의존성·SQLAlchemy 호환 모델·임시 SQLite DB이고, 비동기 DB와 다른 스택은 자동 지원하지 않는다. 최종 공개 계약과 연결부(`signup_link.py`)를 맞춘 뒤 시범 실행으로 확인하고, 두 구조에 같은 계약을 제공한다.

| 실행 전 고정할 값 | 기입할 값 |
|---|---|
| 시나리오·요구사항·외부 계약 버전과 해시 | 실험 등록표에 기입 |
| 시작 소스 커밋·Snapshot 해시 | 실험 등록표에 기입 |
| 앱 실행·DB 조회·로그 수집 방식 | 실험 등록표에 기입 |
| 실행 이미지 digest·의존성 lock 해시 | 실험 등록표에 기입 |
| 모델·설정·도구 범위·전체 자원 한도 | 실험 등록표에 기입 |
| 시간·비용·수정·재시도 한도 | 실험 등록표에 기입 |
| 반복 횟수·실행 순서·시험지 해시 | 실험 등록표에 기입 |
| Snapshot 보존 지점(두 구조 동일) (v4) | 실험 등록표에 기입 |

실험 등록표에는 계측 담당, 시간 초과·정리 정책, 평가기 실행 제한도 기록한다. 등록값이 빠졌거나 두 구조의 조건이 다르면 공식 비교를 시작하지 않는다.

한 시나리오를 비교하는 Single/Multi 쌍은 동일한 시작 상태를 사용한다. 시작 코드는 요구사항과 무관한 공통 골격이고, 시나리오마다 달라지는 것은 계약이다(설계정리 v9 2.2).

#### 입력과 증거의 재현 범위

이메일·비밀번호는 실행할 때마다 무작위로 만든다. 같은 시험이란 같은 검사 코드·입력 종류·개수·판정 정책을 뜻하며, Run마다 원문 문자열이 같다는 뜻은 아니다. 사례 ID·생성 정책·시험지 해시를 보존한다. 정확한 입력 재현이 필요하면 평가 담당 전용 자료로 따로 관리하고, 보고서에는 비밀값 원문을 넣지 않는다. 버전 사이 회귀를 확정하거나 반복 결과를 대조할 때는 같은 재현 입력을 쓴다(PROC-04, 17절). (v4)

| 구분 | 현재 지원과 사용 규칙 |
|---|---|
| 기본 판정 증거 | 검사 ID·결과·진단, 실행 보고서와 증거 ID, 코드·환경·시험지 해시. 신뢰된 검사 실행과 연결되면 기본 채점에 쓴다 |
| 상세 관찰 증거 | 개별 응답 상태·DB 전후 수치·해시 조건 등. 시험 중 확인하지만 모든 관찰값이 지금 자동 저장되지는 않는다 |
| 수집 제외 범위 | 파일 직접 쓰기, 별도 로깅 통로, 종료 뒤 스레드 출력은 지금 SEC-005가 모두 수집하지 못한다 |

각 문제의 ‘증거’는 평가기가 확인할 관찰 항목이다. 보고서에 저장되지 않은 상세값을 저장된 것처럼 표시하지 않고, 미수집 경로와 추가 확인이 필요한 범위를 결과표에 남긴다. 직접 관찰을 요구하는 재현 검토에는 별도 수집이 필요하다.

## 정확도 시험 A · 기능 검사 6개

현재 연결부는 검사마다 새 임시 DB를 만들고 생성물 앱 모듈을 다시 불러온다. 검사마다 새 프로세스·컨테이너를 만드는 것은 아니며, Run 사이 격리는 실행기의 별도 조건이다. 사전 조건이 필요한 검사는 정상 가입이 되는지 먼저 확인한다. 시험 입력은 공식 최종 시험지의 입력 종류·횟수를 따른다.

#### QA-001 · 정상 가입 / REQ-001

절차: 새 `DATABASE_URL`로 앱을 시작하고, 모양이 다른 유효 이메일 두 개로 각각 가입한다. 점·하위 도메인을 포함한 주소와 2글자 최상위 도메인 주소를 포함한다. 비밀번호는 현재 최종 시험지 기준 14자다. 모든 요청은 생성물의 원래 DB 연결을 사용한다. 평가기는 테이블을 대신 만들지 않으며 저장 결과만 별도 연결로 조회한다.

PASS: 각 요청이 2xx이고 사용자 수가 정확히 1명 증가하며, 해당 이메일의 계정이 1개 존재한다. DB 연결·초기화 오류로 정상 가입이 실패하면 FAIL, 성공했는데 지정한 임시 DB에 계정이 없으면 미검증(`DATABASE_URL_NOT_USED`)이다. 증거: 응답 상태, 요청 전후 사용자 수, 이메일별 계정 수.

#### QA-002 · 잘못된 이메일 거부 / REQ-002

절차: 정상 가입을 확인한 뒤 빈 값·공백만·@ 없음·로컬 없음·도메인 없음·@ 두 개·중간 공백의 7종류를 보낸다.

PASS: 모두 4xx이며 신규 생성과 기존 계정 변경이 없다. 증거: 입력 유형별 상태, 요청 전후 사용자 표의 동일 여부. 모든 요청을 거부하는 서비스는 사전 조건을 통과할 수 없다.

#### QA-003 · 동일 이메일 재가입 거부 / REQ-003

절차: 계정 하나를 만든 뒤 같은 주소, 대소문자 변경, 뒤 공백, 대소문자+앞 공백으로 재가입한다. 재가입 요청에는 다른 비밀번호를 사용한다.

PASS: 모두 4xx이며 계정은 1개로 유지되고 원래 계정의 값이 바뀌지 않는다. 증거: 응답, 정규화 이메일별 계정 수, 사용자 표 변경 여부. 기존 비밀번호를 덮어쓰는 동작도 실패다.

#### QA-004 · 비밀번호 경계 / REQ-004

절차: 길이 7·5자는 거부, 8·16자는 허용하는지 확인한다. 소문자만 11자, 숫자만 8자도 가입시킨다.

PASS: 짧은 입력은 4xx·DB 불변, 허용 입력은 2xx·사용자 1명 증가다. 증거: 길이·구성 유형별 상태와 DB 변화. 비밀번호 원문은 결과표에 쓰지 않는다.

#### QA-005 · 동시 중복 가입 / REQ-003

절차: 같은 이메일로 5개 요청을 동시에 전송한다. 새 이메일로 총 3회 반복한다.

PASS: 매 회 사용자 1명, 2xx 응답 1건, 나머지 4xx다. 증거: 요청별 상태와 회차별 최종 사용자 수.

FAIL과 미검증: 관찰된 5xx는 미검증이 아니라 FAIL이다. 아무 계정도 생기지 않고 모든 응답이 4xx이며 단독 가입까지 실패할 때만 요청 연결 문제로 보고 미검증(`CONCURRENT_SIGNUP_NOT_CREATED`)이다. 앱을 불러오지 못하는 등 연결·수집 자체가 실패해도 미검증이며, 다른 검사의 사전 조건 실패까지 한꺼번에 FAIL로 바꾸지 않는다. 기준은 `signup_qa_checks.py`의 판정과 같다.

#### QA-006 · 응답과 실제 결과 / REQ-007

절차: 정상 A → A 변형으로 중복 → B의 짧은 비밀번호 → B 정상 가입 → 잘못된 이메일 순으로 요청한다.

PASS: 성공 응답은 실제 1명 생성과 일치한다. 거부 응답은 신규 생성·기존 행 변경이 없고, 한 번 거부된 B는 정상 입력으로 다시 가입할 수 있다. 증거: 단계별 응답, DB 변화, 기존 행 변경 여부.

## 정확도 시험 B · 보안 검사 3개

#### SEC-002 · 비밀번호 저장 / REQ-005

절차: 같은 16자 비밀번호로 서로 다른 계정 두 개를 만든다. 저장된 해시의 형식·설정·salt를 확인하고, 가입한 비밀번호와 다른 비밀번호로 각각 검증한다.

PASS: Argon2id 형식, 현재 정책의 파라미터 하한 충족, 원문 미포함, 계정별 salt 상이, 가입 비밀번호 검증 성공, 다른 비밀번호 검증 실패를 모두 만족한다.

FAIL 예: 평문·일반 SHA 저장, 파라미터 미달, 고정 salt, 실제 가입 비밀번호로 검증 실패. 증거: 상세 증거를 남길 때는 조건별 참·거짓과 설정 수치만 기록한다. 지금 자동 저장되는 범위는 ‘실행 계약과 증거’를 따른다. 비밀번호·해시 원문은 보고서에 넣지 않는다.

#### SEC-003 · 정규화 저장과 DB 중복 방지 / REQ-003

절차: 대소문자·공백 변형 이메일을 신규 가입시켜 저장값을 확인한다. 앱을 거치지 않고 같은 이메일 행을 DB에 직접 추가한다. 점·+태그만 다른 주소 쌍은 각각 가입한다.

PASS: 앞뒤 공백 제거·소문자 저장, 이메일 UNIQUE에 의한 DB 중복 삽입 거부, 점·+태그만 다른 주소의 별도 계정 보존을 모두 만족한다.

증거: 저장 형식, 중복 삽입 거부 여부와 제약 대상, 별도 주소별 계정 수. 현재 연결부의 SQLite 오류 판독을 다른 DB로 바꿀 경우 연결부부터 검증한다. 다른 DB라는 이유로 제품 결함을 확정하지 않는다.

#### SEC-005 · 응답·로그 노출 / REQ-006의 앱 출력 범위

절차: 정상·잘못된 이메일·짧은 비밀번호·중복 요청, 본문 필드 누락·목록 본문·필드 이름 오타, DB 저장 오류를 시험한다. 앱 시작부터 정상 종료까지 응답 본문·헤더와 수집 가능한 표준 logging·stdout·stderr를 확인한다.

PASS: 시험 비밀번호와 저장 해시가 직접·base64·16진수 형태로 발견되지 않고, 해시 형태 탐지도 통과한다. 지원되는 앱 로깅 경로의 로그 수준과 정상 종료 때 출력도 포함한다. 파일 직접 쓰기, 앱보다 먼저 확보된 별도 로깅 통로, 종료 뒤 남은 스레드의 출력은 지금 자동 수집 범위 밖이다.

증거: 검사한 출력 범위, 수집 완료 여부, 노출 위치와 유형, 검사 결과. 발견된 비밀값 자체는 남기지 않는다. 수집하지 못한 출력은 ‘노출 없음’으로 처리하지 않는다. 인코딩 검사는 지정 형식을 길이·후보 수 제한(검사 텍스트마다 형식별 최대 2,000개) 안에서 한 번 풀어 보는 것이며, 임의 변환 전체를 검증하지는 않는다. (v4)

#### 제품 시험과 전체 시스템 검증의 구분

SEC-005만으로 REQ-006 전체를 충족했다고 선언하지 않는다. A2A 메시지·Artifact·Trace 등은 과정 평가의 출력 노출 점검으로 별도 확인한다. 기록이 이미 가려져 있다면 가리기 전 출력까지 검사했다고 주장할 수 없다.

| 보고할 결과 | 포함 범위 |
|---|---|
| 제품 보안 검사 결과 | SEC-002·003·005에서 실제 관찰한 범위 |
| 시스템 출력 노출 점검 | 수집한 A2A·Artifact·Trace·도구 출력 범위와 미수집 범위 |
| 전체 요구사항 검증 상태 | 제품 시험 + REQ-006 미검사 출력 + REQ-008 추적 검사 상태 |

이번 시험이 통과했다는 표현은 이 문서의 검사 범위를 통과했다는 뜻이다.

## 정확도 채점 규칙

### 7. 검사와 요구사항 판정

| 상태 | 적용 기준 |
|---|---|
| PASS | 필요한 관찰과 증거를 모두 얻었고 모든 기대 조건을 만족 |
| FAIL | 실행에서 기준 위반을 확인했고 그 증거가 있음 |
| UNVERIFIED | 실행·수집·연결·전제 조건 문제로 판단할 증거를 얻지 못함 |

이 시험의 9개 검사는 모두 필수다. Run마다 NOT_APPLICABLE이나 임의 적용 제외를 허용하지 않는다. 범위를 바꾸려면 계약·시험지 버전을 바꿔 두 구조에 똑같이 적용한다.

같은 요구사항에 필요한 모든 검사가 PASS일 때만 그 요구사항을 PASS로 센다. FAIL과 미검증이 함께 있으면 기존 집계 규칙에 맞춰 요약은 UNVERIFIED로 두되, 확인된 실패 목록을 별도로 반드시 보존한다. P·FAIL·UNVERIFIED는 서로 겹치지 않는 요구사항 요약 개수이고, 미검증 중 확인된 실패가 있는 요구사항 목록은 따로 낸다.

코드·실행 환경·시험지의 신분을 확인하지 못하면 점수를 만들지 않는다. 코드가 빌드되지 않거나 시험 실행이 시작되지 못한 Run도 삭제하지 않는다. 해당 Run의 제품 통과는 인정하지 않고, 원인·이미 쓴 시간·비용을 보존한다.

### 8. 주 지표

| ID | 지표 | 계산·판정 |
|---|---|---|
| ACC-01 | 제품 요구사항 완전 충족률 | 제품 검사 범위에서 전체 검사가 PASS인 요구사항 수 P / 7 × 100 |
| ACC-02 | 최종 제출물의 제품 시험 통과 | 같은 최종 코드·환경에서 필수 9개 검사 모두 PASS, 대상 신분 확인 완료 |
| ACC-03 | 제품 보안 검사 결과 | SEC 3개 각각의 PASS·FAIL·UNVERIFIED와 확인된 실패 ID |
| ACC-04 | 검사 판정 가능률 | PASS 또는 FAIL인 상위 검사 수 / 9 × 100. 하위 사례 실행 완료율과 다름 |
| ACC-05 | 전체 요구 검증 범위 | REQ-006의 미수집 출력, REQ-008 추적 검사와 그 결과를 따로 표시 |

ACC-01의 ‘7개’는 REQ-001~007의 제품 시험 범위다. REQ-006 전체 출력과 REQ-008까지 포함한 충족률로 부르지 않는다. REQ-003에 검사가 3개 있어도 요구사항 개수는 1개다.

미검증 요구사항 중 확인된 실패가 없는 것을 U라고 하면 ACC-01의 하한은 P/7 × 100, 상한은 (P+U)/7 × 100이고 단위는 둘 다 %다. 확인된 실패가 있는 요구사항은 다른 검사가 미검증이어도 상한에 더하지 않는다. 미검증을 제품 결함으로 단정하지도, 통과로 올려주지도 않는다. 상위 검사 FAIL이 모든 하위 사례가 실행됐다는 뜻은 아니며, ACC-04는 상위 9개 검사 기준이다. 비교 보고에는 P·FAIL·UNVERIFIED 개수를 함께 낸다.

### 9. 기존 부분점수와의 관계

기존 `exam_score`는 요구사항별 통과 검사 비율의 평균인 보조 부분점수다. REQ-003의 3개 검사 중 2개만 PASS라면 부분점수는 2/3을 줄 수 있지만 ACC-01에서는 완전 충족으로 세지 않는다. 두 값을 같은 이름으로 보고하지 않으며, 점수가 높아도 보안 실패가 사라지지 않는다.

### 10. 평가 오류와 제품 오류

- 연결 불일치는 먼저 기록하고, 제품의 계약 위반인지 평가기 오류인지 근거로 구분한다.
- 충돌은 기업 정의(질의응답 61번)대로 센다. QA는 통과로 봤는데 Security가 배포 불가로 본 경우와, 서로 다른 코드 버전의 결과물을 기준으로 작업한 경우가 충돌이다. 같은 조건·같은 항목에서 양립할 수 없는 판정은 그중 ‘판정 모순’으로 따로 표시한다. 충돌은 판정을 바꾸지 않으며 탐지·기록 대상이다(질의응답 64번, PROC-07). 같은 보고서 쌍의 충돌은 재전송·재탐지돼도 한 건으로 센다. (v4)
- 숨긴 시험 결과만으로 원인을 자동 확정하지 않는다. 공식 시험 결과는 구현 결함·검증 오류를 분류하는 근거로 쓰되, 외부 시험 PASS만으로 내부 검증 오류를 확정하지 않는다. 공식 시험 9개가 모든 입력과 상황을 검사하지는 않으므로, QA·Security가 다른 경계 조건에서 실제 결함을 찾았을 수 있다. 같은 Snapshot의 요구사항·입력·환경·실패 증거를 대조하고, 근거가 부족하면 ‘원인 미확정’으로 기록한다. 계획 문제 분류는 원인을 심어 둔 평가 사례로 잰다(설계정리 v9 3.6). (v4)

## 최종 제출물과 종료 처리

#### 채점할 코드의 선택

Run이 끝나면 실행기가 지정한 최종 제출 Snapshot 하나를 채점한다. 내부 판정이 성공·실패·미검증 중 무엇이든 같은 외부 시험을 적용한다. 담당자가 나중에 가장 잘 나온 중간 버전을 골라 바꾸지 않는다.

중단 때는 완전히 저장된 최신 Snapshot을 기본 제출물로 삼고, 중단 당시의 저장 안 된 변경과 다를 수 있음을 기록한다. 완전한 Snapshot이 없으면 NO_ARTIFACT로 남긴다. 이 선택 규칙은 실행 전에 고정한다. 버전별 채점(17절 6단계)은 사후 분석이며 최종 제품 점수를 대체하지 않는다.

#### 두 가지 통과를 나눈다

| 결과 | 조건 | 용도 |
|---|---|---|
| 제품 시험 통과 | ACC-02: 지정한 최종 제출물이 필수 9개 검사 모두 PASS | 생성물 품질, 제품 통과율, 제품 통과당 비용 |
| 자동 완료 통과 | 제품 시험 통과 + 내부 SUCCESS + 한도 안 종료 + 결과 패키지 완성 + Run 중 사람의 수정·판단 개입 없음 | 자동화된 전체 흐름의 완료율. 제품 시험 통과와 따로 집계 |

자동 완료 통과도 모든 보안 취약점이 없다는 뜻은 아니다. REQ-006 미검사 출력과 REQ-008 결과는 항상 함께 보고한다. 자동 완료 조건은 이 문서의 측정 기준이며 지금 실행기에 구현됐다고 가정하지 않는다.

#### 종료 상태별 처리

| 상황 | 외부 제품 시험 | 시간·비용 처리 |
|---|---|---|
| 정상 종료 | 지정한 최종 Snapshot 채점 | 판정·패키지 완료 시각, 전체 사용량 |
| 수정·시간·비용 한도 초과, 취소 | 보존된 Snapshot이 있으면 채점, 없으면 미검증 | 시작부터 중단까지의 경과 시간과 사용량 보존 |
| 사람 검토 이관 | 자동 실행 구간을 마감해 보존 | 이후 사람 보조 결과는 별도 구간·실험으로 표시 |
| 계속 실행 중 | 최종 결과로 집계하지 않음 | 관측 시각까지의 부분 기록만 표시 |
| 기록 소실·평가 환경 오류 | 미검증과 원인 기록 | 확인된 값만 보존, 성공이나 0으로 대체하지 않음 |

종료 사유, 내부 판정, 외부 시험 결과는 서로 다른 필드다. 예산을 넘긴 뒤 제출한 코드가 시험을 통과해도 자동 완료 통과는 아니다.

평가기 오류는 같은 제출물에 대한 평가 재시도로 처리하고 이력을 보존한다. 개발 Run을 새로 돌리면 별도 Run이다. 실패 Run을 지우고 재실행 성공으로 바꾸지 않는다.

## 속도 측정표

### 11. 속도

비교 실험의 시작은 고정된 요구사항·계약과 시작 코드를 준비한 뒤 기록하는 `RUN_STARTED`다. 서비스에서 계약 초안을 만드는 시간은 별도 준비 시간으로 기록하고, 한쪽에만 포함하지 않는다.

| ID | 지표 | 시작과 끝 | 누락 처리 |
|---|---|---|---|
| TIME-01 | 개발·검증 판정 시간 | Run 시작 → 최종 판정 확정 | 시작·판정·전체 사건의 완전성을 확인 못 하면 미측정 |
| TIME-02 | 결과 패키지 완료 시간 | Run 시작 → 최종 보고서와 결과물 저장 완료 | 패키지 미완성이면 미완료. 판정 시간으로 대체하지 않음 |
| TIME-03 | 첫 빌드 성공 시간 | Run 시작 → 첫 빌드 PASS | 빌드 성공 없음과 시각 누락을 구분 |
| TIME-04 | 제품 통과 Run의 판정 시간 | ACC-02가 통과인 Run들의 TIME-01 분포 | 통과 수/전체 수를 함께 제시 |
| TIME-05 (v4) | 보존 Snapshot 기준 최초 통과 산출 시간 | Run 시작 → 보존 대상 버전 중 필수 9개 검사가 처음 모두 PASS인 Snapshot의 고정 시각 | 그런 버전이 없으면 ‘통과 버전 없음’. 앞선 버전이 누락되거나 통과 가능성을 배제할 수 없는 미검증이면 ‘최초 여부 미검증’. 버전별 Snapshot이 없으면 미측정 |
| TIME-06 | 종료·중단 경과 시간 | Run 시작 → 정상 종료 또는 한도 초과·취소·자동 구간 마감 | 중단 Run도 보존. 실행 중이면 관측 시각까지의 부분값 |

초·밀리초 단위를 고정한다. 병렬 QA·Security의 시간을 더해 전체 소요 시간으로 삼지 않는다. 전체 시간은 실제 경과 시간이다. 역할별 시간 합계는 보조 분석으로만 표시한다.

공식 자동 비교는 사람 검토로 넘어가면 자동 구간을 마감한다. 이후 사람 대기·보조 실행은 별도 구간이다. 재개를 허용하는 서비스 실험에서는 전체 경과 시간과 사람 대기를 함께 보고한다. 실패·중단 Run의 시간도 보존하며, 통과 Run 시간만으로 전체 구조가 빠르다고 결론 내리지 않는다.

첫 인계가 재개 후에 이루어졌고 자동 구간의 원본 결과가 없으면 `QUARANTINED_ASSISTED`로 보관한다. 이후 최종 코드를 자동 정확도로 채점하지 않으며, 자동 시간·비용·과정 지표는 미확인으로 남긴다. 계획·실행 슬롯을 분모에서 없애거나 미시작으로 바꾸지 않는다. 사람 보조 구간이 섞인 원본 사용량은 별도 진단으로만 표시하며, 이미 보존한 자동 구간은 덮어쓰지 않는다.

TIME-05는 Run이 끝난 뒤 내보낸 버전별 Snapshot을 같은 공식 시험지로 채점해 구한다(17절 6단계). 두 구조의 Snapshot 보존 지점은 실행 전에 똑같이 정한다. Snapshot을 더 자주 저장한 구조가 통과를 더 일찍 관측하지 않게 하기 위해서다. TIME-05는 편집 도중 실제로 요구사항을 처음 충족한 순간이 아니라, 보존 대상 버전 중 처음 모두 통과한 Snapshot이 고정된 시각까지의 시간이다. 나중에 채점한 시각이 아니라 그 코드가 고정된 시각을 쓴다. 버전별 Snapshot이 없으면 이 시각을 추정해 만들지 않고 미측정으로 둔다. (v4)

시각은 같은 실행 제어기가 기록한 사건 시각을 기준으로 한다. 동기화되지 않은 여러 서버의 시계를 그대로 빼지 않는다. 시간대·단위·시계 기준·사건 누락 여부를 기록하고, 역전된 시각이나 불완전한 기록은 미측정으로 표시한다.

TIME-01은 최종 판정, TIME-02는 최종 보고서까지의 완료, TIME-06은 중단을 포함한 실행 구간의 끝이다. 기존 `totalMs`(시작 → 끝남·중단 사건)가 새 패키지 완료 사건을 포함하는지 확인하기 전에는 TIME-02에 그대로 연결하지 않는다.

제품 통과 Run만의 속도와 전체 실행의 통과율을 반드시 함께 제시한다. 대부분 실패한 구조의 드문 빠른 성공만으로 ‘더 빠르다’고 결론 내리지 않는다.

총토큰은 입력+출력이다. 현재 계측에서 캐시 읽기·쓰기 토큰은 입력의 부분집합, 추론 토큰은 출력의 부분집합이므로 총토큰에 다시 더하지 않는다. 사용량 요약과 개별 호출 기록도 중복 합산하지 않는다.

현재 단가 체계에서는 일반 입력(입력 − 캐시 읽기 − 캐시 쓰기)에 일반 입력 단가, 캐시 읽기·쓰기에 각 단가, 출력에 출력 단가를 적용한다. 단가가 100만 토큰 기준이면 합계도 100만으로 나눈다. 제공자별 정의가 다르면 수집 단계에서 같은 범주로 정규화하고 계산 버전을 남긴다.

실패·미검증·중단에 쓴 비용도 COST-03의 분자에 포함한다. 통과가 0회면 0원으로 표시하지 않고 ‘산출 불가: 제품 통과 없음’으로 기록한다.

COST-03의 통과는 ACC-02 제품 시험 통과다. 자동 완료 통과당 비용을 추가로 낼 때는 별도 이름과 분모를 쓴다. 실행·채점이 진행 중이면 잠정값으로 표시한다. 외부 제품 시험이 UNVERIFIED인 Run은 통과 수에 넣지 않고, 이미 쓴 비용은 분자에 넣는다.

사용량이나 단가가 누락되면 확정 총비용을 만들지 않는다. 확인된 금액은 부분합으로 표시하고, 실제 0과 미확인을 구분한다. 직접 계측하지 않은 도구·인프라·사람 비용은 API 비용에 섞지 않는다. 필요하면 별도 비용 항목으로 보고한다.

단가표 버전과 기준 통화를 보존한다. 두 구조의 단가가 다르면 달러 차이를 그대로 효율 차이로 해석하지 않고 토큰·호출 수를 함께 본다. 평가 시험 자체의 실행 시간·비용은 개발 Run 바깥의 평가 비용으로 따로 기록한다.

공식 비용 범위는 등록한 자동 실행 구간의 계획부터 결과 보고서까지다. 사람 검토로 넘어간 뒤의 보조 재개 비용은 별도 구간으로 나눈다. 시범·추가 탐색 실험의 비용도 공식 N개 Run과 섞지 않는다. 예산을 넘긴 직후 취소되지 못한 호출의 과금까지 포함하고 초과분을 표시한다. 보고서 작성·실패 호출 비용을 임의로 빼지 않는다.

수정 횟수가 적다는 이유만으로 우수하다고 판정하지 않는다. 아무것도 고치지 못하고 끝난 Run도 0회일 수 있다. 정확도와 함께 읽는다.

#### 수정 시도와 완료의 계수

수정 경로를 승인·시작할 때 시도 수를 1 늘리고 완료 수는 따로 기록한다. 수정 중 중단해도 이미 시작한 시도를 지우지 않는다. 최초 구현은 제외하고, 재계획 뒤 그 계획에 따른 구현·검증은 같은 주기로 센다. 파일 저장이나 테스트 실행 횟수로 세지 않는다. 설계정리 v9의 ‘수정·재계획·테스트 수정 합계 최대 3회’를 적용할지는 실험 등록표의 정책 값으로 고정하고, 적용한다면 이 한도는 `repairRoundCount`에 건다. 재계획 뒤 구현·재검증은 같은 주기로 세고 중복 합산하지 않는다. (v4)

`repairRoundCount`와 구현 수정·재계획·테스트 수정의 개별 횟수를 기록한다. 같은 전송을 중복으로 받았다고 두 번 세지 않는다. 기존 `fixAttempt`가 세 경로를 모두 포함한다고 가정하지 않는다. 도구·A2A·LLM 재시도 한도는 각각 따로 동결한다.

### 14. A2A 평가의 두 범위

| 범위 | 확인할 것 | 판단의 한계 |
|---|---|---|
| 전달 무결성 | 받아야 할 입력 목록, 보낸 내용, 실제 수신·읽은 내용의 ID·버전·해시·누락·중복, 구간별 대기 시간(보낸 시각 → 받은 쪽 작업 시작) | 서버에 저장됐다는 사실만으로 모델 입력에 사용됐음을 증명하지 않음 |
| 작업 반영 | 수신한 요구사항·Snapshot과 계획·검증·수정 결과의 연결 | 제품 시험 실패만으로 오해석 원인을 확정하지 않음 |

필수 입력·실제 읽은 Artifact 내용의 해시·코드 버전을 작업 전에 확인하고 종료 후 기록으로 재확인하는 것이 구현 요구다. 지금 기록이 그 범위를 증명하지 못하면 미검증으로 남긴다. 오해석은 근거가 있을 때만 표시하고, 전달 성공과 작업 성공을 별도 열로 둔다.

Single에도 요구사항 보존·입출력 연결·작업 결과 검사를 적용한다. 실제 에이전트 간 전송이 없는 항목은 ‘해당 없음’이며 자동 만점으로 바꾸지 않는다. 공통 과정 지표와 Multi 전용 A2A 진단 지표를 구분해 보고한다.

최종 시험은 관찰된 결함을 확인하는 자료다. 오케스트레이터의 원인 분류 정확도와 QA·Security의 결함 탐지율은 별도 역할 평가로 연결하며, 다섯 축의 결과에 중복 가산하지 않는다.

계획에는 있었으나 시작하지 못한 Run도 별도 행으로 남긴다. 이를 삭제해서 통과율 분모를 줄이지 않는다. 실행하지 않았음을 확인한 경우와 기록이 없어 실행 여부를 모르는 경우를 구분한다.

N은 해당 시나리오·조건·구조에 미리 배정한 실행 슬롯 수다. 시작하지 못한 슬롯은 실행 여부와 사유를 남기며, 평가 재시도나 같은 요청의 중복 기록을 새 Run으로 세지 않는다. 추가 개발 재실행은 별도 ID와 분석 묶음으로 남겨 원래 실패를 대체하지 않는다. STAB-02의 내부 상태와 외부 미검증은 겹칠 수 있으므로 합계가 100%인 단일 분할표로 다루지 않는다.

반복 횟수는 예산에 따라 사전 고정한다. 시범은 구조별 1회 이상, 본 실험은 구조별 5회를 우선 제안한다. 확정값은 아니며 n이 작으면 탐색적 결과라고 표시한다. 한두 시나리오 결과를 모든 서비스 요청으로 일반화하지 않는다.

## 비교 조건과 실행 절차

### 16. 비교 조건

- 같은 요구사항·계약·시작 코드·모델·설정·공개 역할 지침·도구 전체 범위·시험지 버전·한도를 사용한다. Single은 한 에이전트가 Run의 작업 문맥을 이어받아 계획·개발·QA·Security·수정·최종 보고를 순서대로 수행한다. 단계마다 독립 문맥으로 초기화하는 구성은 별도 실험 조건이다.
- 각 Run은 새 작업 공간·DB·상태로 시작한다. QA와 Security는 같은 불변 코드의 분리된 실행 공간과 DB를 검사한다.
- 전체 CPU·메모리·동시 실행 자원과 API 제한을 기록한다. ‘같은 이미지’를 ‘같은 자원 조건’의 증거로 대신하지 않는다.
- 순서는 Single→Multi, 다음 쌍은 Multi→Single처럼 교대한다. 캐시·예열·외부 서비스 지연 조건을 기록한다.
- 사람 검토에 도달하면 자동 실행 결과를 보존한다. 사람이 코드를 고친 결과는 같은 자동 비교 Run의 성공으로 덮어쓰지 않는다.

집계는 같은 시나리오·계약·시험지·모델·정책·자원 조건별로 한다. 서로 다른 조건을 구조 이름만으로 섞지 않는다. 여러 시나리오를 합친 값은 보조 요약이며 시나리오별 결과를 함께 낸다.

### 17. 실행 순서

1. 공개 계약·시작 코드·이미지·모델·한도·Snapshot 보존 지점·반복 계획을 실험 등록표에 기입하고 동결한다.
2. 정상 예제와 알려진 결함 예제로 시험지·연결부를 검증한다. 결함 하나가 여러 검사를 실패시킬 수 있으므로 예상 실패 집합과 대조한다. 같은 대상을 두 번 돌려 결과가 같아야 한다(동시성 검사 QA-005 포함). 반복 결과가 다르면 입력 생성·환경·대상 코드의 비결정성·평가기 오류를 구분하고, 평가기나 연결부 오류가 확인되면 고친 뒤 다시 검증한다. (v4)
3. 시범용 시험지로 실제 Single·Multi를 실행해 생성물·기록·독립 평가 연결을 확인한다.
4. 연결 문제가 해결되면 공식 시험지 해시와 설정을 고정한다. 시범 결과를 공식 결과에 섞지 않는다.
5. 공식 Run을 실행하고 끝난 코드·보고서·기록을 보존한다. 내부 검증 실패 Run도 보존한다.
6. 공식 최종 시험으로 지정한 최종 제출물을 채점하고, 내보낸 버전별 Snapshot도 같은 시험지로 채점한다(Run 종료 후에만). 버전별 결과는 TIME-05, PROC-04 회귀 후보, 개발 역할 평가(첫 버전 점수, 회귀 후보)에 쓰고 최종 제품 점수를 대체하지 않는다. 그다음 다섯 축을 집계한다.
7. 유효 표본 수·누락·확인된 실패·범위를 포함해 결과를 보고한다. 평가 결과를 해당 Run으로 되돌리지 않는다.

#### 공식 결과를 읽는 규칙

정확도 차이는 퍼센트포인트로, 시간·비용 차이는 단위와 기준 구조를 밝혀 쓴다. 기준값이 0이거나 미확인이면 비율 차이를 만들지 않는다. 결과에 따라 유리한 지표만 골라 주 지표로 바꾸지 않는다.

통과율과 미검증률은 계획 N을 분모로, 측정값의 분포는 실제로 계산 가능한 k개를 대상으로 한다. 둘을 함께 보고해 미측정 Run이 통과한 것처럼 보이지 않게 한다. 조건 불일치가 확인되면 공식 우열 결론을 유보하고 해당 Run·사유·비교 가능한 범위를 표시한다.

현재 비교는 문맥 분리·역할 분담·병렬 실행을 포함한 두 구성의 전체 효과다. 정확도가 높아졌다는 결과만으로 ‘문맥 독립성 하나가 원인’이라고 확정하지 않는다. 원인을 나누려는 추가 실험은 따로 계획한다.

### 21. 이번 작성에서 확인한 것

검사 정의와 요구사항 연결은 현재 로컬 저장소의 시험지·기준표·SCN-001 등록 정보를 대조했다. 기존 코드에 있던 시험 9개를 문서화했으며, 시험 입력·기대 결과를 임의로 바꾸지 않았다. QA-005의 FAIL·미검증 기준은 `signup_qa_checks.py`와 대조해 맞췄다.

최종본 작성 때 고친 평가 코드: 코덱스 검토가 짚은 두 경우(첫 버전만 있는 Run의 버전별 채점, 역전된 시각)를 재현한 뒤 고쳤다(23절). 새 시험 8개 중 오탐 방지용 1개를 뺀 7개가 고치기 전 코드에서 실패하는 것을 확인했고, 고친 뒤 관련 시험 6개 파일 255개가 통과했다(56초). 수정은 아직 커밋 전이다. (v4)

## 세부 관찰 결과 보고서 (suite 0.7.0)

동일한 최종 시험 실행에서 모든 QA·Security 세부 항목의 기대값·실제값·PASS/FAIL/NOT_RUN/UNVERIFIED를 수집한다. `check_details.json`과 `check_details.md`로 별도 저장하며, 요약에는 링크를 남긴다. 공식 검사 9개와 요구사항 7개의 판정·점수는 유지한다. 자세한 동작과 범위는 [상세 결과 기록](check_details.md)을 참고한다. 새 시험지 지문으로 실행하며 구형 기록의 세부 결과를 추정해 채우지 않는다.
