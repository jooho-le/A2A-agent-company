# QA·Security 세부 결과 기록

suite 0.6.0부터 최종 평가와 동일한 보호 시험 실행에서 상세 관찰 결과를 기록한다. 현행 0.7.0에서는 FAIL 이후에도 독립 항목의 검사를 계속한다. 모델 호출과 추가 채점 실행은 발생하지 않는다. 공식 검사 9개, 제품 요구사항 7개, 점수 산식은 유지한다.

## 저장 위치

`evaluation.workflow`와 `evaluation.experiment score`가 작성하는 실행 결과 폴더에 `check_details.json`과 `check_details.md`를 저장한다. `summary.md`는 상세표 링크를 제공한다. 이전 Snapshot도 평가하면 `version_details/vN/`에 각 버전의 상세 파일을 보관한다. `evaluate_final_snapshot`의 프로그램 반환값은 `checkDetails`에 같은 자료를 담는다. 참고용 practice 채점은 공식 최종 상세표에 섞지 않는다.

JSON에는 Run·채점 ID, 구조, 코드 Manifest, 시험지 버전·해시, 항목별 기대값·실제값·상태·사유, 기존 검사 판정, 기록 무결성 진단을 넣는다. Markdown은 목차, 실패·미실행·미검증 목록, 모든 검사별 상세표를 제공한다. 세부 사례 ID는 시험지 버전·범위와 함께 식별한다. 시험지 간 입력 순서가 달라질 수 있으므로 서로 다른 범위의 순번만 대조하면 안 된다.

## 상태 의미

| 상태 | 의미 |
|---|---|
| PASS | 관찰한 값이 등록된 조건을 만족 |
| FAIL | 관찰한 값이 조건을 위반 |
| NOT_RUN / 미실행 | 필요한 선행 조건이나 관찰 대상이 없어 해당 검사를 실행하지 못함. 의존 조건의 사유를 보존 |
| UNVERIFIED / 미검증 | 관찰 오류, 기록 유실, 실행기 오류, 코드·시험지 불일치 등으로 판정 불가 |

기록 자체가 없으면 해당 항목을 실행하지 않았다고 단정하지 않는다. 전체 계획을 복원해 미검증으로 표시한다. 실제값이 없으면 null이며 0·false·PASS로 채우지 않는다. 사전 정상 가입 실패는 준비 조건의 실패로 기록하지만, 기존 제품 검사에서는 종전대로 미검증이 될 수 있다. 준비 조건을 제품 점수에 추가하지 않는다.

현재 final·pilot에는 준비 조건을 포함해 139개 항목, practice에는 136개 항목이 있다. 순환용의 이메일 변형 수 차이 때문이다. 이 개수는 제품 정확도 분모가 아니다. `recordStatus=COMPLETE`는 상세 기록의 구조와 상위 결과가 일치한다는 의미이며, 제품 통과를 의미하지 않는다.

## 기록과 판정의 연결

검사 시작 전에 신뢰된 시험지에서 항목 계획을 만든다. 조건 비교 결과를 unittest 하위 검사와 상세 기록이 공유한다. FAIL은 상위 검사에 보존하면서 독립 항목은 계속 관찰한다. 응답 코드 실패 후에도 DB 증가량·기존 행 불변을 확인하며, 이메일 정규화 실패 후에도 DB UNIQUE 검사를 수행한다. 이후 PASS가 앞선 FAIL을 덮어쓰지 않는다.

해시 검사는 계정별로 진행한다. 한 계정의 가입·해시 확보에 실패해도 다른 계정의 검사를 계속한다. 응답이 실패 상태여도 저장된 해시가 있으면 관찰하되 가입 사전조건의 실패는 유지한다. 해시를 해석할 수 있으면 m·t·p·비밀번호 검증을 독립적으로 수행한다. Argon2i처럼 알고리즘 정책을 위반해도 값을 해석하고 검증할 수 있으면 나머지는 계속 검사한다. 해석할 수 없는 형식의 종속 항목은 `HASH_FORMAT_REQUIRED`, 해시 값이 확보되지 않은 경우는 `HASH_VALUES_REQUIRED`로 미실행 처리한다. salt 개수 비교에는 비교 대상 해시가 모두 필요하다. 이 사유는 최종 정리 시 일반적인 중단 사유로 덮어쓰지 않는다.

최종 평가에서는 별도 실행 결과 프레임을 `unittest-v1` 보고서와 같은 실행에서 수집한다. 최종 평가의 공용 보고서는 기존 필드를 유지한다. 순환용 Host 실행 보고서는 선택 필드로 기대조건 없는 관찰값을 전달하며 [개발 에이전트 피드백](loop_validation_feedback.md)에 연결한다. 기존 0.6.0보다 실패 이후에 관찰하는 항목과 입력이 늘 수 있으므로 새 시험지 버전·지문으로 구분하며, 이전 입력 기록을 새 시험지에 재사용하지 않는다.

Host는 현재 시험지로 기대 항목을 다시 구성하고 목록·기대값·형식·결과 일치를 검사한다. 손상되거나 누락된 기록은 미검증으로 만든다. 상위 판정과 모순되면 `PARENT_DETAIL_MISMATCH`를 명시하며 기존 공식 판정을 몰래 덮어쓰지 않는다. 세부 증거가 불완전하면 `DETAIL_OBSERVATIONS_INCOMPLETE`를 표시한다. 해시는 일관성 확인용이며 적대적 프로세스에 대한 서명 인증은 아니다.

## 보안과 범위

관찰값은 제한된 정수·불리언·상태 코드 목록만 저장한다. 비밀번호·salt·해시·이메일·응답 본문·로그 원문·예외 메시지는 저장하지 않는다. 형식·일치 여부와 파라미터·계정 수 등으로 표시한다. 시험 원문과 최종 세부 결과는 평가자 자료이며 개발 에이전트에게 전달하거나 시작 코드에 포함하지 않는다.

SEC-005는 요청 종류별 응답과 앱 시작~종료의 전체 로그·출력을 구분한다. 로그는 요청별 귀속을 추정하지 않는다. 응답이 포착되지 않은 사례는 미검증이며, 별도 파일 쓰기·별도 로깅 통로·종료 뒤 출력 등 기존 수집 밖의 경로까지 안전하다고 표시하지 않는다.

전달할 보호 파일은 AST가 동일한 공백 압축 사본을 사용하여 Host 설정의 기존 64 KiB 제한을 유지한다. Python 버전에 따라 코드 표현이 달라지는 재작성 방식은 사용하지 않으며, Python 3.10과 3.13에서 같은 파일이 전달되는지 확인한다. 검사 조건이나 제한을 완화하지 않는다. 시험지 해시는 실제 전달하는 사본과 0.7.0 버전에 맞춰 갱신한다. 과거 0.5.2 결과는 세부 관찰값을 소급 생성할 수 없고 새 시험과 혼합하지 않는다.
