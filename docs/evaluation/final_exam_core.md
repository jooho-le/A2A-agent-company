# SCN-001 최종 평가 시험지 · 핵심본

Single·Multi 비교 — 정확도 · 속도 · 비용 · 과정 · 안정성

2026-11-09 · 원문: [최종본 v4](final_exam.md)의 핵심 요약, 시험 내용은 원문과 같음 · 시험 묶음 suiteVersion 0.2.0 · 작성 4번 강석민

평가 담당용 · 시험 입력은 에이전트에게 공개하지 않음 · 자세한 증거 범위·측정식·기록 양식은 원문 참고

### 한 장 요약

- **무엇을:** 회원가입 서비스를 만드는 한 번의 실행(Run)을 평가한다. 같은 요구사항을 받은 Single과 Multi의 최종 생성물과 실행 기록을 같은 기준으로 비교한다. 코드 모양·줄 수·파일 구조는 점수가 아니다.
- **정확도:** Run이 끝나면 최종 제출 Snapshot 하나에 숨긴 시험 9개(기능 6, 보안 3)를 실행한다. **9개가 모두 PASS면 제품 시험 통과**다.
- **나머지 네 축**(속도·비용·과정·안정성)은 같은 Run의 기록으로 계산한다. 다섯 축을 합친 단일 총점은 만들지 않는다.
- **지키는 것:** 시험지는 에이전트에게 공개하지 않고, 결과를 Run에 돌려주지 않는다. 조정은 시범 시험지로 끝내고 공식 설정을 동결한다.
- **지금 상태:** 시험 9개와 채점기는 준비됐다(자체 시험 통과). 공식 실행 전에 외부 계약·시작 코드·평가 이미지를 확정하고 시범 실행을 해야 한다(9절).

## 1. 다섯 평가 축

| 축 | 질문 | 주 결과 |
|---|---|---|
| 정확도 | 같은 요구사항과 보안 기준을 만족했는가? | 요구사항별 결과, 제품 시험 통과 여부, 확인된 보안 위반 (숨긴 시험 9개로 채점) |
| 속도 | 결과를 얻는 데 얼마나 걸렸는가? | 판정까지의 시간, 보존 Snapshot 기준 최초 통과 시간, 결과 패키지 완성까지의 시간 |
| 비용 | 결과를 얻는 데 얼마나 썼는가? | 입력·출력 토큰, API 비용, 제품 통과 1회당 비용 |
| 과정 | 어떤 오류와 수정을 거쳤는가? | 수정·재계획·재시도, 충돌, 추적 가능성, 전달 오류 |
| 안정성 | 같은 조건에서 결과가 얼마나 일정한가? | 제품 통과율, 자동 완료율, 미검증·중단 비율, 점수·시간 분포 |

## 2. 채점 흐름

```text
Run 종료 → 최종 제출 Snapshot 1개 → 숨긴 시험 9개(기능 6·보안 3) → 검사 판정(PASS·FAIL·UNVERIFIED)
        → 요구사항 7개 판정: ACC-01 완전 충족률(하한·상한), ACC-02 제품 통과 = 9개 모두 PASS ─┐
Run 기록(사건 시각·사용량·작업/전달/수정 기록) → 속도·비용·과정·안정성 ────────────────────┴→ Single·Multi 비교표(축별, 단일 총점 없음)
```

정확도만 시험을 실행해 채점하고, 나머지 네 축은 같은 Run의 기록으로 계산한다.

범위 밖: 로그인·OAuth·이메일 인증·비밀번호 찾기·프로필 관리. 짧은 검사명 QA-001·SEC-002는 기존 ID QA-SIGNUP-001·SEC-SIGNUP-002를 뜻한다.

### 전제 정책

- **이메일:** 앞뒤 공백 제거 후 소문자로 저장. Gmail 점·+태그는 지우지 않고, 다른 주소를 합치지 않는다.
- **비밀번호:** 길이만 검사. 계약에 없는 대문자·특수문자 조건을 더하지 않는다.
- **저장:** Argon2id, 파라미터 하한 m=19456·t=2·p=1, 계정별 salt.
- **응답:** 정상 2xx, 입력 오류·중복 4xx. 400인지 422인지로 점수를 나누지 않는다. 관찰된 5xx는 실패 근거가 될 수 있다.

### 연결 규격 (시험 내용과 분리)

- 지금 연결부의 가정: `main.app`, `database.get_db`, `models.User(email, password_hash)`, `POST /api/auth/signup`.
- 지원: FastAPI·동기 DB 의존성·SQLAlchemy 호환 모델·임시 SQLite.
- 최종 공개 계약과 연결부를 맞춘 뒤 시범 실행으로 확인하고, **두 구조에 같은 계약**을 준다.
- 시작 코드는 요구사항과 무관한 공통 골격이고, 시나리오마다 달라지는 것은 계약이다.

## 4. 시험 9개

검사마다 새 임시 DB를 쓰고, 이메일·비밀번호는 실행할 때마다 무작위로 만든다. "같은 시험"이란 같은 검사 코드·입력 종류·개수·판정 정책이라는 뜻이다. 비밀번호와 해시 원문은 보고서에 쓰지 않는다.

| 검사 | 요구 | 무엇을 하나 | PASS 조건 |
|---|---|---|---|
| 기능 검사 6개 |  |  |  |
| QA-001 / 정상 가입 | 001 | 모양이 다른 유효 이메일 2개(점·하위 도메인 주소, 2글자 최상위 도메인 주소)로 각각 가입. 비밀번호 14자. 이어서 생성물의 원래 `get_db`로 한 번 더 가입 | 각 요청 2xx, 사용자가 정확히 1명씩 증가, 이메일별 계정 1개. 원래 `get_db` 가입도 2xx이고 임시 DB에 있음(실패 응답이면 FAIL, 다른 DB면 미검증) |
| QA-002 / 잘못된 이메일 | 002 | 정상 가입을 확인한 뒤 7종류(빈 값·공백만·@ 없음·로컬 없음·도메인 없음·@ 두 개·중간 공백) 전송 | 모두 4xx, 새 계정 생성·기존 계정 변경 없음 |
| QA-003 / 같은 이메일 재가입 | 003 | 계정 1개를 만든 뒤 같은 주소·대소문자 변경·뒤 공백·대소문자+앞 공백으로 재가입(다른 비밀번호) | 모두 4xx, 계정 1개 유지, 원래 값 불변 (비밀번호를 덮어써도 실패) |
| QA-004 / 비밀번호 경계 | 004 | 7·5자는 거부, 8·16자는 허용 확인. 소문자만 11자, 숫자만 8자도 가입 | 짧은 입력은 4xx·DB 불변, 허용 입력은 2xx·사용자 1명 증가 |
| QA-005 / 동시 중복 가입 | 003 | 같은 이메일로 5개 요청을 동시에 전송. 새 이메일로 3회 반복 | 매 회 사용자 1명, 2xx 1건, 나머지 4xx. **5xx는 FAIL** |
| QA-006 / 응답과 실제 결과 | 007 | 정상 A → A 변형 중복 → B 짧은 비밀번호 → B 정상 → 잘못된 이메일 순서로 요청 | 성공 응답 = 실제 1명 생성, 거부 응답은 DB 변화 없음, 한 번 거부된 B는 정상 입력으로 다시 가입 가능 |
| 보안 검사 3개 |  |  |  |
| SEC-002 / 비밀번호 저장 | 005 | 같은 16자 비밀번호로 계정 2개 생성. 해시 형식·설정·salt 확인, 맞는 비밀번호와 다른 비밀번호로 각각 검증 | Argon2id, 파라미터 하한 충족, 원문 없음, 계정별 salt 다름, 맞는 비밀번호 검증 성공·다른 비밀번호 실패 |
| SEC-003 / 정규화·DB 중복 방지 | 003 | 대소문자·공백 변형 이메일 가입 후 저장값 확인. 같은 이메일 행을 DB에 직접 추가. 점·+태그만 다른 주소 쌍은 각각 가입 | 공백 제거·소문자 저장, UNIQUE로 DB 중복 삽입 거부, 점·+태그만 다른 주소는 별도 계정 유지 |
| SEC-005 / 응답·로그 노출 | 006 | 정상·잘못된 이메일·짧은 비밀번호·중복, 필드 누락·목록 본문·필드 이름 오타, DB 저장 오류를 시험. 앱 시작부터 정상 종료까지 확인 | 응답 본문·헤더·logging·stdout·stderr에서 비밀번호·해시가 직접·base64·16진수로 발견되지 않고, 해시 형태 탐지도 통과 |

**미검증으로 두는 경우:** QA-005는 계정이 하나도 생기지 않고, 모든 응답이 4xx이고, 단독 가입까지 실패할 때만 요청 연결 문제로 보고 미검증이다. 앱을 불러오지 못하는 등 연결·수집이 실패해도 미검증이다. SEC-005에서 수집하지 못한 출력(파일 직접 쓰기, 별도 로깅 통로, 종료 뒤 스레드 출력)은 “노출 없음”으로 처리하지 않는다.

SEC-005만으로 REQ-006 전체를 충족했다고 선언하지 않는다. A2A 메시지·Artifact·Trace의 노출은 과정 평가(PROC-06)에서 따로 확인한다. "이번 시험 통과"는 이 문서의 검사 범위를 통과했다는 뜻이다.

## 5. 판정 규칙

| 상태 | 기준 |
|---|---|
| PASS | 필요한 관찰과 증거를 모두 얻었고, 모든 기대 조건을 만족 |
| FAIL | 실행에서 기준 위반을 확인했고 그 증거가 있음 |
| UNVERIFIED | 실행·수집·연결·전제 조건 문제로 판단할 증거를 얻지 못함 |

- **9개 모두 필수다.** Run마다 적용 제외(NOT_APPLICABLE)를 허용하지 않는다.
- **요구사항 PASS** = 그 요구사항에 필요한 검사가 모두 PASS. FAIL과 미검증이 섞이면 요약은 UNVERIFIED로 두되, **확인된 실패 목록은 따로 보존**한다.
- 코드·실행 환경·시험지의 신분을 확인하지 못하면 점수를 만들지 않는다. 빌드 실패나 시험 미시작 Run도 삭제하지 않고, 제품 통과로 인정하지 않는다.

| ID | 주 지표 | 계산·판정 |
|---|---|---|
| ACC-01 | 제품 요구사항 완전 충족률 | 검사가 모두 PASS인 요구사항 수 P / 7 × 100. 하한 P/7, 상한 (P+U)/7 (U = 확인된 실패가 없는 미검증 요구사항) |
| ACC-02 | 제품 시험 통과 | 같은 최종 코드·환경에서 필수 9개 검사 모두 PASS, 대상 신분 확인 완료 |
| ACC-03 | 제품 보안 검사 결과 | SEC 3개 각각의 PASS·FAIL·UNVERIFIED와 확인된 실패 ID |
| ACC-04 | 검사 판정 가능률 | PASS 또는 FAIL인 검사 수 / 9 × 100 |
| ACC-05 | 전체 요구 검증 범위 | REQ-006의 미수집 출력, REQ-008 추적 검사 결과를 따로 표시 |

ACC-01의 7개는 REQ-001~007의 제품 시험 범위다. REQ-003에 검사가 3개 있어도 요구사항은 1개로 센다. 기존 부분점수(`exam_score`)는 보조 지표라 ACC-01과 같은 이름으로 보고하지 않는다.

## 6. 무엇을 채점하나

- **최종 제출 Snapshot 하나**를 채점한다. 내부 판정이 성공·실패·미검증 중 무엇이든 같은 시험을 적용한다. 나중에 잘 나온 중간 버전으로 바꾸지 않는다.
- **중단된 Run**은 완전히 저장된 최신 Snapshot을 채점하고, 없으면 NO_ARTIFACT로 남긴다.
- **버전별 채점**(Run 종료 뒤 모든 버전을 같은 시험지로 채점)은 TIME-05와 회귀 후보(PROC-04)용 사후 분석이며, 최종 점수를 대체하지 않는다.

| 두 가지 통과 | 조건 |
|---|---|
| 제품 시험 통과 | ACC-02: 최종 제출물이 필수 9개 검사 모두 PASS. 생성물 품질·통과율·통과당 비용에 쓴다 |
| 자동 완료 통과 | 제품 시험 통과 + 내부 SUCCESS + 한도 안 종료 + 결과 패키지 완성 + Run 중 사람의 수정·판단 개입 없음. 제품 시험 통과와 따로 집계한다 |

| 종료 상황 | 외부 시험 | 시간·비용 |
|---|---|---|
| 정상 종료 | 최종 Snapshot 채점 | 판정·패키지 완료 시각, 전체 사용량 |
| 한도 초과·취소 | 보존된 Snapshot이 있으면 채점, 없으면 미검증 | 시작부터 중단까지의 시간·사용량 보존 |
| 사람 검토 이관 | 자동 실행 구간을 마감해 보존 | 이후 사람 보조 결과는 별도 구간 |
| 기록 소실·평가 환경 오류 | 미검증과 원인 기록 | 확인된 값만 보존, 성공이나 0으로 대체하지 않음 |

종료 사유·내부 판정·외부 시험 결과는 서로 다른 칸이다. 예산을 넘긴 뒤 낸 코드가 시험을 통과해도 자동 완료 통과는 아니다. 평가기 오류는 같은 제출물을 다시 채점하고, 실패 Run을 지우고 재실행 성공으로 바꾸지 않는다.

## 8. 비교 조건과 실행 순서

### 비교 조건

- 같은 요구사항·계약·시작 코드·모델·설정·역할 지침·도구 범위·시험지·한도.
- Run마다 새 작업 공간·DB·상태로 시작한다.
- 순서를 교대한다(Single→Multi, 다음 쌍은 Multi→Single).
- CPU·메모리·API 제한 같은 자원 조건을 기록한다.
- 사람이 고친 결과로 자동 비교 Run의 성공을 덮어쓰지 않는다.
- 반복: 시범은 구조별 1회 이상, 본 실험은 구조별 5회를 제안한다(확정 아님).

### 실행 순서

1. 계약·시작 코드·이미지·모델·한도·Snapshot 보존 지점·반복 계획을 실험 등록표에 적고 동결
2. 정답·결함 예제로 시험지 검증 (예상 실패 집합과 대조, 같은 대상 2회 실행 결과 일치)
3. 시범 시험지로 실제 Single·Multi 실행
4. 공식 시험지 해시·설정 고정 (시범 결과는 섞지 않음)
5. 공식 Run 실행, 실패 Run 포함 보존
6. 최종 제출물 채점 + 버전별 채점
7. 유효 표본 수·누락·확인된 실패와 함께 보고

**결과 해석:** 정확도 차이는 퍼센트포인트, 시간·비용은 단위와 기준 구조를 밝힌다. 유리한 지표만 골라 주 지표로 바꾸지 않는다. 이번 비교는 문맥 분리·역할 분담·병렬 실행을 합친 전체 효과이며, 하나의 원인으로 단정하지 않는다.

## 9. 사용 경계와 지금 상태

- **공개하는 것:** 공개 요구사항과 실행 계약만 두 구조에 똑같이 준다. 시험 입력·검사 코드·정답과 결함 예제는 평가 담당만 관리한다.
- **돌려주지 않는 것:** 최종 시험 결과는 해당 Run에도, 같은 공식 실험의 프롬프트·모델·정책 조정에도 쓰지 않는다. 공식 결과를 보고 시스템을 바꾸면 새 실험이다.
- **평가기를 고치면:** 원본 결과·수정 이유·버전 이력을 보존하고 같은 제출물 전체를 다시 채점한다. 요구사항이 바뀌면 새 계약·새 실험이다.
- **참고(11.9 확인):** 순환 안 연습 시험(Ver1)은 이 시험과 검사 함수가 같고 입력만 다르다. Ver1을 쓰면 그 최종 점수는 "같은 검사로 연습한 뒤의 점수"로 따로 보고한다(Ver1·Ver2 정리 문서).
