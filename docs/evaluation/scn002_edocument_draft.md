# 전자문서(SCN-002) 등록 초안

작성: 2026-11-14 · 4번 · 상태: **초안(범위·연결 규격 결정 전)**

dev 시나리오 등록부에 넣을 수 있는 형식으로 전자문서 시나리오의 요구사항을 정리했다. 근거는 팀 시나리오 문서의 "전자문서 제출·조회 기능 개발 및 검증" 절(F-01~F-07, S-01~S-05)이다. 11.5 중간점검에는 "전자문서 편집"으로 적혀 있는데, 시나리오 문서는 문서 수정을 제외 범위에 넣었다. 그래서 **범위부터 정해야 하고, 이 초안은 "제출·조회"를 따른다.**

- 계약 초안: [`examples/evaluation/scn002-edocument.contract.draft.json`](../../examples/evaluation/scn002-edocument.contract.draft.json)
- 검사: [`tests/evaluation/test_scn002_draft.py`](../../tests/evaluation/test_scn002_draft.py)
  - dev `ScenarioDefinition.from_contract`가 받고, 다시 꺼낸 Planner 계약이 같은지 본다.
  - Run 설정에 동결했을 때 dev 승인 원장(`freeze_requirement_authority`)이 받는지 본다.
  - 회원가입 정책이 기본값으로 섞이지 않는지 본다.

## 요구사항 대응

dev 승인 원장은 요구사항 키로 `REQ-001` 형식만 받는다. F/S 번호는 이 표에서만 대응시킨다. 요구사항마다 완료 조건 문장은 하나다. 최신 dev는 QA·Security가 만든 시험의 기대값이 이 문장과 글자 그대로 같아야 받기 때문이다.

| 키 | 시나리오 문서 | 검증 담당 | 완료 조건(초안) |
|---|---|---|---|
| REQ-001 | F-01 정상 제출 | QA | 정상 PDF 한 개와 등록된 담당자로 제출하면 제출 건 1건과 원본 파일이 저장되고 성공 응답 |
| REQ-002 | F-02 잘못된 요청 거부 | QA | 잘못된 제출 요청은 오류 응답이며 제출 건으로 저장되지 않음 |
| REQ-003 | F-03 크기 경계 | QA | 10,485,760바이트 이하 PDF는 저장되고 10,485,761바이트 이상은 거부 |
| REQ-004 | F-04 처리 결과 안내 | QA | 성공은 성공으로, 거부는 실패와 그 이유로 응답 |
| REQ-005 | F-05 같은 이름 보존 | QA | 내용이 다른 같은 이름 PDF 두 개가 각각 저장되고 각 제출 건에서 해당 원본이 내려받아짐 |
| REQ-006 | F-06 목록 정확성 | QA | 제출자 목록과 담당자 목록의 파일명·제출자·담당자·제출 시각이 제출 건과 일치 |
| REQ-007 | F-07 원본 일치 다운로드 | QA | 제출자와 지정 담당자가 내려받은 파일의 SHA-256이 제출한 원본과 일치 |
| REQ-008 | S-01 미인증 거부 | Security | 로그인하지 않은 등록·목록·다운로드 요청은 거부되고 문서 정보가 노출되지 않음 |
| REQ-009 | S-02 타인 접근 차단 | Security | 무관한 사용자에게 다른 사람 문서의 목록 정보와 파일 내용이 제공되지 않음 |
| REQ-010 | S-03 식별자·제출자 조작 | Security | 식별자·제출자 값을 바꾼 요청으로 타인 문서 접근과 타인 명의 제출이 모두 불가 |
| REQ-011 | S-04 경로 조작 | Security | 경로를 조작한 파일명으로 저장 영역 밖 파일이 생성되거나 조회되지 않음 |
| REQ-012 | S-05 형식 위장 | Security | 확장자나 Content-Type만 PDF로 바꾼 비허용 파일은 거부 |
| REQ-013 | (공통) 추적 | Orchestrator | Trace를 통해 전체 연결 관계 복원 가능 |

REQ-013은 SCN-001의 REQ-008과 같은 공통 추적 요구다. 시나리오 문서의 12개에는 없다.

- **제외 기능:** 심사·승인 절차, 담당자 변경, 문서 수정·버전 관리, 전자서명, OCR, AI 내용 분석, 악성코드 탐지(시나리오 문서 4절)
- **보안 정책 칸:** 크기 한도, PDF만 허용, 서버가 내용으로 형식 판별, 제출자·담당자만 접근, 제출자는 서버가 로그인 계정으로 기록, 서버가 만든 식별자로 저장 영역 안에만 저장
- **이메일 정책 칸:** 비워 둔다. 비워 두지 않으면 회원가입 정책이 기본값으로 들어간다.

## 아직 정해야 할 것

1. **범위:** "편집"인지 "제출·조회"인지. 편집이면 요구사항을 새로 써야 한다.
2. **연결 규격:** 로그인 방식(세션·토큰), 등록·목록·다운로드 경로와 요청 형식, 저장 위치 환경 변수, DB 모델 이름과 칸, 시험 계정(A 제출자, B 담당자, C 무관)과 담당자 목록을 시작 코드에 어떻게 넣을지. 숨긴 시험지 연결부는 이것이 정해져야 만든다.
3. **PDF 판별 방법과 시험 파일:** 정상 PDF, 형식 위장 파일, 크기 경계 파일. 시나리오 문서도 실행 전에 확정하라고 적고 있다.
4. **시작 코드:** 로그인이 있는 기본 프로젝트라서 회원가입보다 골격이 크다.
5. **dev 등록:** 시나리오 등록부에 넣는 일은 주호님 dev 작업이다. 이 초안의 UUID를 그대로 써도 된다.

정해지면 4번 몫은 다음과 같다: 숨긴 시험지(연습·pilot·final 세 벌)와 연결부, 검사 대응표, 합성 정상·결함 서비스로 시험지 검증. Agent별 평가표·지표·비교 집계는 Run이 고정한 시나리오 계약을 읽으므로 그대로 쓴다.
