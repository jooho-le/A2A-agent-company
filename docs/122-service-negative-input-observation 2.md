# 122. 빈 입력 검사 허용 및 실제 제품 결함 분리

작성일: 2026-11-27.

## 이번 Run의 실패

Run `c78b956d-c3c5-4bb3-bb4b-0520eeffa4a9`는 Build PASS, QA 5/5 PASS 이후 Security가 `LLM_VALIDATION_DRAFT_EXHAUSTED / TEST_OUTPUT_ARGUMENT_INVALID`로 종료됐다. 121번의 클라이언트 중복 전달 문제와는 다른 원인이다.

Security는 빈 비밀번호 거절 시험에서 `check_http_output(..., sensitive="", json=payload)`를 사용했다. 실행 전 검사는 모든 상수를 거절했고 실제 도구도 8자 이상 합성 문자열만 허용했다. 모델은 같은 빈 입력 호출을 반복해 수정 기회를 소진했다. 당시 이 시험은 제품에 요청하기 전에 막혔다.

도구를 고쳐 실제 요청을 보내자, **원본 API가 빈 비밀번호에도 201을 반환**하는 제품 결함이 드러났다. 기획서는 비밀번호 존재 검증과 오류 시 400을 명시하고 있었고, 원본 Security 시험도 400을 기대했다. 이 기대값이나 원본 시험은 바꾸지 않았다.

## 수정

1. 공통 HTTP 관찰 도구가 빈 문자열·빈 합성 데이터·`sensitive=None`을 받아 실제 요청을 보낸다. 정상 입력용 보안 관찰 도구를 빈 입력 시험에도 사용했을 때 준비 단계에서 막히지 않는다.
2. 요청의 성공·실패와 관찰 증거를 분리했다. 빈 값과 None은 `NO_SAMPLE`로 기록한다. HTTP 상태에 대한 검사는 실제 응답대로 PASS/FAIL을 결정하지만, `NO_SAMPLE` 자체는 비밀값 미노출 증거가 아니다.
3. 비어 있지 않은 짧은 합성 값과 손실·잘림·응답 미확인은 계속 `INCOMPLETE`다. 정상 합성 값으로 실제 관찰한 `CHECKED`가 있어야 보안 관찰을 충족하며, 다른 실제 `INCOMPLETE`가 있으면 통과시키지 않는다. 인코딩된 비밀번호 해시 노출은 빈 입력 시험에서도 `EXPOSED / FAIL`이다. 관찰용 길이 기준은 제품 비밀번호 최소 길이 규칙이 아니다.
4. Host 보고서 파서·수정 피드백·진척 판단에 새 상태를 연결했다. `NO_SAMPLE`을 수정 성공으로 계산하거나, 이전 `EXPOSED/CHECKED` 근거를 대체하는 용도로 인정하지 않는다. 공통 검사기와 Host 파서는 함께 적용해야 한다.
5. 서비스 Agent 지침과 Developer 수정 입력에 누락·빈 문자열의 차이를 추가했다. Pydantic의 `password: str`만으로는 빈 문자열이 거절되지 않는다. 실제 관찰된 `201 → 기대 400`을 제품 수정 대상으로 전달하고, 검사 데이터를 정상 값으로 바꾸거나 성공 기대값으로 완화하지 않도록 했다.

기존 Source·Run·Artifact 기록은 바꾸지 않았다. 인증·Sandbox·실행 승인·수정 예산과 SCN-001 전용 준비 기능도 유지했다.
