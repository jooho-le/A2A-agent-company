# 107. 106번 보완 후 4조건 실제 API 단회 비교

작성일: 2026-11-23. 106번까지 반영한 코드에서 **Single·Multi × Ver1·Ver2를 각각 한 번씩 실제 실행**했다. 요청은 네 조건 모두 **“이메일과 비밀번호로 회원가입 기능을 만들어줘.”**다.

새 Run 제출은 정확히 **4건**이다. 실행 도중 구현 변경, 생성 Source의 수동 수정, 실패 후 Run 재제출은 하지 않았다. 기존 실험의 결과는 합산하거나 덮어쓰지 않았다.

## 결과표

**회원가입 최종 9개 시험은 Single Ver2 한 건이 전부 통과했다. Host의 전체 자동 작업까지 성공한 실행은 없었다.** Multi 두 조건은 등록된 Source가 없어 품질을 채점하지 못했다.

## 조건별 확인 내용

### Single Ver1 — 제품 보안 결함이 남고 마지막 수정은 공급자 오류

등록된 v1·v2·v3은 모두 시작 규격 Build를 통과했다. 공통 보호시험에서는 세 버전 모두 QA 6개가 통과했으나, Security의 `SEC-SIGNUP-005` 비밀번호·해시 비노출 항목 하나가 실패했다. 두 번의 수정 완료 후 세 번째 수정을 시도했지만 새 Source를 등록하지 못하고 보류됐다.

독립 최종 시험도 **8 PASS·1 FAIL**이다. 세부 결과는 `malformed_list / password_exposed / EXPECTATION_MISMATCH`다. **일반적인 객체가 아닌 목록 형태의 요청을 처리하는 오류 응답에서 비밀번호 노출이 확인됐다.** 이번 실패를 이전 실험의 DB 오류 로그 해시 노출과 같은 경로로 단정하지 않는다.

최종 실패 Task 상태의 코드는 `LLM_PROVIDER_ERROR`다. 공급자 오류 이벤트는 모델 시도 36·61·62번에 기록됐다. 자체 생성 시험도 모두 정상은 아니었다. QA는 각 v1·v2·v3에서 6 PASS·1 FAIL이었고 Security에는 FAIL·SKIP과 시험 수정 이력이 함께 남아 있다. 원본 기록을 PASS로 바꾸지 않았다.

### Multi Ver1 — 개발 복구 후 진전 없음으로 중단

Planner는 완료했으나 Developer가 `LLM_DEVELOPMENT_NO_PROGRESS`로 실패했고, Run은 `DEVELOPMENT_NO_PROGRESS_EXHAUSTED`로 ABORTED 됐다. 등록 Source·Build·QA·Security 결과가 없어 독립 제품 평가는 수행할 수 없었다.

도구 기록에는 `write_source_file`의 `WRITE_CONFLICT` 한 건이 있고 `resultUnknown=false`다. 알려진 쓰기 거절과 이후 진전 없음 중단을 확인한 것이며, 전송 데이터 유실이나 모델 성능 점수 0%로 해석하지 않는다. 어떤 교정 응답이 진전 조건을 만족하지 못했는지는 후속 복구 경로 점검 대상이다.

### Single Ver2 — 회원가입 최종 시험은 통과, 시작 규격에서 실패

v1의 독립 최종 시험은 **9 PASS·0 FAIL**, 요구사항은 **7/7**이다. 평가 Manifest도 일치했다. 사람이 다른 파일로 바꾸어 채점한 결과가 아니다.

그러나 Host의 Build는 exit code 1, `SCN001_READY_ENDPOINT_REQUIRED`로 실패했다. **별도의 `GET /` 실행 준비 응답 계약을 만족하지 못한 것**이다. 회원가입 9개 시험과 시작 규격의 검사 범위가 다르므로 두 결과는 함께 성립할 수 있다.

Host가 수정을 요청했지만 Developer가 `LLM_EXECUTION_TIMEOUT`으로 끝나 v2는 등록되지 않았다. QA·Security 단계에 진입한 기록도 없다. 따라서 이 실행을 전체 개발 절차의 성공으로 보고하거나 436.272초를 Host 성공 판정 시간으로 표시하지 않는다.

### Multi Ver2 — 기획 단계의 공급자 오류

Planner의 모델 호출 두 시도 모두 `LLM_PROVIDER_ERROR`로 끝났다. Developer·MCP 도구 실행·등록 Source가 없어 최종 제품은 미평가다.

현재 보존된 오류 코드는 HTTP 상태·공급자의 세부 오류 유형을 구분하지 않는다. **할당량 부족, 요청 제한, 서비스 오류 중 무엇인지는 이번 기록만으로 확정할 수 없다.** 이를 토큰 잔액 부족이나 무료 호출로 단정하지 않는다. 추가 호출로 재확인하지 않았다.

## 개발정의서 점검·다음 작업

Orchestrator의 성공·실패·보류 판정, A2A Task·Artifact, 불변 Snapshot, Single Context, MCP 권한·인증·CAS·승인·Sandbox, 보호시험과 독립 최종 시험을 유지했다. 시작 규격이나 보안 기준을 낮추어 성공을 만들지 않았다. `.env`·사용자 설정·기존 보고서·구현 파일도 수정하지 않았다. 프로젝트 Git 커밋·푸시는 하지 않았다.

원본은 `.data/experiments/scn001-four-post106-20261123/`에 보존했다. 이전 101·102·105번 등 다른 구현 판본과 표본을 합치지 않는다. 실행 순서·캐시·네트워크 변동 및 공급자 오류가 있어 이번 한 표본씩으로 Single·Multi의 일반적인 우열을 결론 내릴 수 없다.

**다음 108번은 추가 유료 반복 실행보다 아래 실패 경로의 코드·수기 재현 검증을 먼저 진행한다.**

1. 쓰기 충돌 뒤 교정 결정과 실제 순변경 결과를 대조해 개발 진전 없음 중단의 원인을 좁히기. CAS나 쓰기 보호를 완화하지 않기.
2. 비정상 JSON 구조의 입력 검증 오류에서도 비밀번호를 오류 응답에 반사하지 않도록 Developer 검토·수정 경로 보완.
3. 회원가입 기능을 추가할 때 기존 실행 준비 응답 계약을 보존하고 Build 실패를 고치도록 보완.
