# 126. 서비스에서 코드 변경 없는 개발 제출 허용

작성일: 2026-11-27.

## 사용자 요청과 원인

사용자는 `개발 직원이 실제 코드 변경 없이 완료를 제출해 실행을 종료했어요`가 반복되어, 기존 코드 그대로 제출해도 다음 단계로 진행하도록 요청했다.

최근 서비스 Run `f499358c-dc01-49e4-8a6c-b08f2ef41f66`과 `e452b550-d45d-4181-853d-33c2e56b2b25`에서 `LLM_DEVELOPMENT_NO_PROGRESS`를 읽기 전용으로 확인했다. 두 Run 모두 서비스 규격이 적용된 실행이다. 기존의 변경 강제 규칙은 모델의 READY 응답과 Git 작업물 저장 단계에 각각 있었으므로, 응답 검사만 바꾸면 저장 단계에서 다시 실패하는 구조였다.

이번 변경은 **사용자 요청에 따른 서비스용 제출 계약 변경**이다. SCN-001 성능 실험의 기존 변경 강제 규칙은 유지한다.

## 변경한 동작

| 항목 | 적용 후 |
| --- | --- |
| 서비스용 싱글·멀티 개발 단계 | 현재 코드가 그대로여도 유효한 READY를 제출할 수 있다. 최초 구현·수정 단계 모두 적용한다. |
| 변경 내역 | 실제 변경만 기록한다. 변경이 없으면 `readyReview.edits`는 빈 배열이다. 파일 변경도 없으면 `fileChanges=[]`를 허용한다. |
| Source 저장 | 기존 부모 또는 검증된 이어받기 기준의 바이트와 일치하면 해당 실제 Git 객체를 재사용한다. 빈 커밋이나 가짜 변경을 만들지 않는다. |
| 검사 | 현재 제출을 위한 새 Source Artifact와 새 Build 실행 근거를 만들고 QA·Security로 넘긴다. 이전 PASS를 새 결과로 대신 사용하지 않는다. |
| 최종 완료 | 기존 요구사항·빌드·QA·보안 판정 규칙에 따라 결정한다. 변경이 없다는 사실 자체로 프로젝트 성공을 만들지 않는다. |

이어받기 첫 제출은 원래 승인된 시작 코드와 이전 작업의 코드가 다를 수 있다. 이 경우 `fileChanges`에는 시작 코드 대비 실제 파일 차이가 남을 수 있고, `readyReview.edits=[]`는 이번 개발 단계에서 추가 수정이 없었다는 뜻이다. 두 기준을 섞어 변경을 꾸미지 않는다.

## 구현 위치와 일관성

- `development_check`와 Git 체크포인트에 Host 전용 무변경 허용 옵션을 추가했다. 서비스의 동결된 계약에서만 활성화하며, 모델·사용자 JSON으로 이 옵션을 받지 않는다.
- 멀티 Developer와 싱글 IMPLEMENTING/FIXING에 같은 정책을 연결했다.
- Change Report의 JSON Schema와 도메인 모델에 빈 변경 배열을 허용했다. 빈 파일 변경 보고서에는 Host의 `readyReview`가 필수다.
- 출력 수신기는 서비스 실행인지 확인하고, 무변경 제출의 Source commit과 working base가 같은지 검증한다. 실제 변경이 없는데 특정 경로를 고쳤다고 주장하는 보고서는 거절한다.
- 서비스 Prompt에서 `무조건 파일을 수정해야 한다`는 지시를 제거하고, 무변경 사유를 사실대로 요약해 새 검증을 요청하도록 안내했다.
- 실행 정책 식별자를 `HOST_NET_DIFF_WITH_SERVICE_REVALIDATION_V8`로 갱신했다. 이전 실패 기록이나 실행 설정을 덮어쓰지 않는다.

## 유지한 규칙

인증·작업공간 접근·동결 요구사항·의존성 Lock·Snapshot 무결성·실행 격리·호출 예산은 유지한다. 이미 확인된 시작 오류·의존성 불일치·잘못된 결과서도 기존대로 검사한다. 무변경 허용은 이 검사들을 건너뛰는 옵션이 아니다.

이미 실패하거나 취소된 Task를 임의로 성공으로 바꾸지 않는다. 같은 프로젝트의 이어서 수정 접수는 기존 기록을 보존한 새 Run이며, 사용자가 직접 시작한다.

## 검증

실제 ASGI·Git·SQLite 경로와 가짜 모델·가짜 Docker 영수증을 사용하는 오프라인 회귀 검사를 수행한다. 생성 앱 실행과 실제 API 호출은 하지 않는다.

- 멀티에서 도구 쓰기 없이 READY → 같은 commit의 Source → 새 Build 근거 생성.
- 멀티 수정에서 기존 Build FAIL 뒤 무변경 재제출 → 새 Source 버전·새 Build 실행 ID 생성. 이전 결과를 재사용하지 않음.
- 싱글의 최초 구현·수정에서 무변경 READY 허용.
- 이어받은 코드 그대로 제출할 때 검증된 기준 객체 재사용. 가짜 추가 커밋 없음.
- 빈 변경 보고서의 Host 관찰 필수, 잘못된 working base 거절, SCN-001의 무변경 거절 유지.
- 서비스에서도 의존성 Lock 변경과 다른 필수 검사 오류는 계속 거절.

| 확인 | 결과 |
| --- | --- |
| 개발·수정·Git 저장·Artifact·싱글 파이프라인·서비스 연동 확장 검사 | 182개 중 181개 최초 통과. 나머지 1개는 아래의 시험 준비 코드를 수정한 뒤 통과 |
| 최종 집중 회귀 | 10개 통과. 위 검사와 중복되며 합산하지 않음 |
| 무변경 수정 후보의 Host 접수 | 새 Source 버전·새 Build 근거가 등록되고 QA·Security 재검사 단계가 생성됨 |
| 원래 실패한 서비스의 적용 대상 여부 | 실제 두 실행 모두 서비스 정책에 해당함을 읽기 전용으로 확인 |
| 유료 API·새 서비스 Run | 실행하지 않음 |

확장 검사에서 기존 우선 수정 시험의 두 번째 쓰기가 첫 번째 파일 생성 전에 구성되어 `expectedSha256` 없이 제출되는 문제가 드러났다. 테스트의 두 번째 호출을 실제 첫 번째 쓰기 이후의 바이트에 연결하도록 수정했다. 운영 코드의 충돌 검사나 파일 쓰기 권한을 느슨하게 바꾸지 않았다.

진행 중인 Run·Step이 없고 Host·Agent 다섯 포트가 기록된 PID의 소유임을 확인한 뒤 Host·Agent만 재시작해 적용했다. 프론트·제품·Host·Agent 4개 모두 HTTP 200, Agent는 `executionReady=true`, Host 인증은 토큰 없이 401·기존 토큰으로 200이었다. 기존 실패 Run은 `ABORTED` 기록을 유지하며, 조회 API에서 `continuationAvailable=true`를 확인했다.

제품·프론트·Docker·기존 작업 기록은 유지했다. 사용자는 화면 새로고침 후 같은 프로젝트의 **이어서 수정·재시도**로 새 제출을 시작하면 된다. 이번 확인은 무변경 제출과 검증 연결의 회귀 검사이며, 실제 AI 서비스의 최종 통과 결과는 사용자의 다음 실행에서 확인한다.
