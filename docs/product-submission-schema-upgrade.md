# 제품 요청 접수 DB 보완

## 확인한 원인

2026-11-23 로컬 서비스에서 승인 설정 조회는 성공했지만 Run 생성과 접수 조회가 503을 반환했다. 현재 ORM은 `run_submissions.manual_retry_claimed_at`을 읽는데, 기존 `backend/app.db`에는 이 컬럼이 없었다. 실제 읽기 오류 `no such column: run_submissions.manual_retry_claimed_at`을 확인했다.

오류는 접수 행을 조회하는 첫 단계에서 발생했다. 문제 요청의 제품 접수 행은 없었고, 연결된 Host DB에도 이날 새 Run이 생성되지 않았다. 따라서 이번 장애에서는 에이전트 작업과 OpenAI 호출이 시작되지 않았다. 이는 이번 DB·기록을 대조한 결론이며 일반적인 404를 미접수 확정으로 바꾸는 규칙은 아니다.

## 변경

- `create_project_tables()`의 기존 최초 생성 역할은 유지한다.
- 로컬 준비 CLI에서 `upgrade_project_tables()`를 호출한다. 기존 SQLite에 누락된 컬럼이나 미접수 키 기록 테이블이 있으면 `.data/backups/product-schema/`에 SQLite backup API로 백업하고 권한을 600으로 설정한 뒤, nullable 컬럼·새 기록 테이블을 추가한다.
- 백업 실패 시 컬럼 추가도 중단한다. 이미 컬럼이 있으면 반복 적용하지 않으며 기존 `manual_retry_claimed_at` 값을 초기화하지 않는다.
- FastAPI 기본 lifespan에서 자동 마이그레이션하지 않는다. 계정·문서·프로젝트·Run 연결·접수 행을 삭제하거나 재작성하지 않는다.

실행은 [서비스 연결 문서](office-service-integration.md)의 명령을 사용한다. 제품 서버와 Vite의 연결 옵션을 각각 명시해야 하며, 비밀키를 프론트엔드에 전달하지 않는다.

## 남은 접수 잠금의 원인과 복구

임시 SQLite 검사 8개가 통과했다. 기존 접수 행 보존, 백업 내용·권한, 재실행 시 재시도 기록 보존, 백업 실패 시 무변경을 포함한다. 실제 로컬 DB도 변경 전후 5개 테이블의 기존 컬럼 값·행 수를 비교했고 모두 동일했다. SQLite 무결성을 확인하고 제품 서버를 재시작했다.

DB를 보완한 뒤에도 브라우저는 앞서 저장하지 못한 동일 접수 UUID를 복원하고 있었다. 기존 GET의 404는 접수 미생성 확정이 아니므로 자동 잠금 해제를 하지 않았고, 사용자가 입력 화면으로 돌아갈 경로가 없었다. 전송기는 이 404를 Run 조회 오류로 표시하고 있었다. 새 탭을 안내하는 방식 대신 실제 복구 경로를 추가했다.

화면에서 **이전 요청 확인하고 다시 입력**을 누르면 `POST /api/v1/submissions/{requestId}/retire`에 빈 객체를 보낸다. JWT 인증은 기존과 같다. 이 API는 Host를 호출하거나 Run을 생성·취소하지 않는다.

| 응답 | 의미와 화면 동작 |
| --- | --- |
| `outcome=RETIRED` | 제품 접수 행이 없는 키를 계정별 영속 기록에 폐기했다. 해당 보류 표시만 해제하고 입력으로 돌아간다. 다음 Run 생성은 사용자가 다시 시작 버튼을 눌러야 한다. |
| `outcome=EXISTING` | 기존 접수 영수증을 그대로 반환한다. CREATED는 기존 Run으로 연결하고 PENDING·UNKNOWN은 잠금을 유지한다. |

제품 SQLite의 접수 생성과 키 정리는 같은 쓰기 잠금을 먼저 획득한다. 새 Run은 접수 행을 커밋한 뒤에만 Host에 전송한다. 정리된 키는 `retired_submission_keys`에 계정별로 남기고, 늦게 도착한 같은 키의 Run POST는 `409 SUBMISSION_KEY_RETIRED`로 차단한다. 따라서 단순한 조회 404를 성공이나 미접수로 바꾸지 않는다. 기존 접수·프로젝트·Run·JWT·입력 초안은 삭제하지 않는다. 현재 제품 접수 원장을 유지하는 SQLite 서비스가 적용 범위다.

접수 GET의 404 문구도 **이전 요청의 접수 기록을 찾지 못했어요**로 구분했다. 조회만으로는 잠금이 풀리지 않는다.

## 검증

후속 서버 검사 42개와 격리된 브라우저 화면 검사 4개가 통과했다. 미접수 키 정리의 반복 호출, 늦은 동일 키 생성 차단, 기존 CREATED·UNKNOWN 보존, 계정 분리·JWT 요구, 생성 중인 트랜잭션과의 동시 실행, 입력 초안·JWT 보존, 명시적인 다음 클릭 전 새 생성이 없음을 확인했다. 실제 접수 DB·Host에 새 Run을 생성한 실험은 아니다.

이 보완에서 실제 Run 생성 POST나 유료 OpenAI 실험은 수행하지 않았다. 새 작업 실행은 사용자의 ‘만들기 시작’으로 진행한다.
